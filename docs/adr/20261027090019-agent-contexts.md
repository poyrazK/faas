# ADR-20261027090019 · Agent contexts: declared, versioned context attached to runs and sessions

- **Status:** proposed (owner decision D19, 2026-10-19, roadmap item 4).
- **Date:** 2026-10-19
- **Amends (when accepted):**
  - ADR-20261027090010 §3: a run that names a context gets its repository and dependencies from context drives, not a per-run checkout. The raw input drive keeps the prompt, the event and step files.
  - ADR-20261027090013 §2: a session's manifest may name a context instead of `gitRepo`.
  - ADR-20261027090015 §1: preset snapshots carry two empty context drive slots.
- **Builds on:**
  - ADR-20261027090016 (capability gateway) and ADR-20261027090017 (tenant connections), for dynamic sources;
  - ADR-003 (builds in builder microVMs) and the `pkg/rootfs` layer pipeline;
  - ADR-101 (image-layer secret scan), ADR-207 (builder cache affinity), ADR-791 (build VM limits);
  - ADR-590 (point-in-time environment clones), ADR-1237–1242 (management MCP);
  - githubd, `pkg/gitfetch` and `pkg/sourcedelta`;
  - ADR-1350 (included object storage).
- **Decision:**
  1. **A context is customer intent owned by apid.** It is a named, declared bundle of **sources**, **permissions** and a **build recipe**, referenced by runs and sessions (`context: "shop"`).
  2. **Static sources are built into images.** Code, dependencies and documents become two immutable, content-addressed images per **context version**, each a read-only ext4 drive:
     - a **source image** per commit, small, built from a delta;
     - a **dependency image** per lockfile digest, which changes rarely.

     Builder microVMs fetch and install. imaged assembles the ext4 with the same pure-Go, no-mount pipeline as app layers.
  3. **Attaching is a bind mount plus an overlay.** vmmd binds the two images read-only into the jail, with no copy. guest-init mounts them as the lower layers of a per-run copy-on-write overlay at `/work`, or at `/workspace` for sessions.
  4. **Dynamic sources are fetched on demand** through the capability gateway, pinned to the run:
     - a Gregale app's deploys, logs and errors;
     - databases, as point-in-time clones only;
     - S3 prefixes, connections and customer MCP servers.
  5. **Images are per account,** cached on agent-node NVMe, placed by affinity, and prebuilt on push.
- **Why:**
  - **Context preparation dominates time to useful work.**
    - A warm restore takes about 0.4 s.
    - A checkout of vite took 5.6 s to fetch and 2.6 s to unpack, before any install. Installs take tens of seconds to minutes.
    - In the economic plan, a run that reinstalls dependencies (the tool-heavy profile) costs about 14× a light run.
  - **Multi-agent work repeats the same setup.** A hundred agents on one repository need one copy of the code and dependencies, not a hundred.
  - **Sellers build this plumbing themselves today:** cloning, caching, credentials, data access. Removing it is the product (D19).
  - **Gregale-native context is a differentiator.** An agent that can read its own app's deploys, logs and errors needs no connectors when the app runs on Gregale.
- **Consequences:**
  - New `contexts` tables, a context build job in builderd, two new read-only drive roles, an overlay mode in guest-init, a node cache in vmmd, and placement affinity in agentd and schedd.
  - Context storage counts against the plan's included object storage.
  - Restoring a preset snapshot with context slots must be proven on metal before the warm path is on (§3).
- **Rejected alternatives:**
  - **A checkout and install per run** (the status quo): slow, costly, and repeated for every agent.
  - **A shared writable workspace for many agents:** concurrent-write consistency, with no isolation between runs.
  - **Sharing host directories into guests (virtiofs or 9p):** forbidden by the security rules. Guests get block devices only.
  - **A lazily fetched block device over object storage in this release:** it adds a network block device to every read. Reconsider for monorepos too large to prebuild.
  - **Deduplicating images across accounts:** it would reveal whether another tenant holds the same content.
  - **Building images on the host:** dependency installs run untrusted scripts, so they belong in builder microVMs (ADR-003).

## Context

D19 put contexts fourth in the capability roadmap: after the capability gateway (ADR-20261027090016), which carries dynamic access, and tenant connections (ADR-20261027090017), which are one source kind. The memory experiment and the economic plan measured why it matters. Start-up work, not the VM, is what an agent waits for and what a run pays for.

## Decision

### 1. Objects and API

| Table (owner) | Holds |
|---|---|
| `contexts` (apid) | Account, name, sources, permissions, build recipe, refresh policy |
| `context_versions` (agentd) | Version digest, resolved source revisions, image keys and sizes, build status (`building`, `ready`, `failed`, `retired`), each with a CHECK |
| `context_pins` (agentd) | The dynamic-source pins a run used: log window end, database clone point, S3 listing time |

```bash
gregale context create shop --git github.com/acme/shop@main --deps "npm ci" \
  --app shop-web --env production --read deploys,logs,errors --db pitr-clone \
  --connection github --deliver pr:agent/*
```

```bash
gregale run debugger --context shop --task "Investigate the latest failed deployment"
```

API:
- `POST /v1/contexts`, `GET`/`PATCH`/`DELETE /v1/contexts/{name}`;
- `GET /v1/contexts/{name}/versions`;
- `POST /v1/contexts/{name}:build` for a manual rebuild.

Runs and sessions take `context: "<name>"` or `"<name>@<version>"`.

**Source kinds:**

| Kind | Static or dynamic | Notes |
|---|---|---|
| `git` | static | A repository at a branch, tag or SHA, with an optional path filter. Fetched through githubd with the installation token. No git history and no credentials in the image |
| `deps` | static | A command run in the builder VM. The image is keyed by the digests of the declared lockfiles |
| `files` | static | Uploaded documents and data |
| `gregale_app` | dynamic | An app and environment: deploys, logs, errors and configuration names (never secret values), through the management MCP |
| `database` | dynamic | A managed Postgres database. Reads go only to an ADR-590 point-in-time clone made on first use and deleted at run end |
| `s3` | dynamic | A bucket prefix, read through the gateway |
| `connection` | dynamic | An ADR-20261027090017 provider and scopes, for the run's tenant |
| `mcp` | dynamic | A customer MCP server from the catalog |

**Permissions.** A context grants access per source (`read`, `write` where the source supports it) and allowed deliveries, for example `pr:agent/*`. A run's effective policy is the intersection of the agent version's policy (ADR-20261027090016 §3), the context's grants and any tenant narrowing. A context can never widen a policy.

### 2. Versions and building

- **Resolving a version.** agentd resolves refs to revisions when a run is triggered. The version digest covers:
  - the source revisions;
  - the lockfile digests;
  - the build recipe;
  - the agent base image digest.

  A version that already exists is reused.
- **The build path:**
  1. A builder microVM (ADR-003, the ADR-791 shape) fetches the archive through githubd and `pkg/gitfetch`. It applies `pkg/sourcedelta` against the previous version when there is one, then runs the `deps` command with `registries` egress (ADR-20261027090013 §6).
  2. The VM streams two tar outputs, source and dependencies, to imaged over the existing builder output path.
  3. imaged assembles each into ext4 with `pkg/rootfs`'s pure-Go staging and unprivileged mkfs, as for app layers. It never mounts a guest-built filesystem.
  4. It runs the ADR-101 secret scan, which blocks publication on a hit.
  5. It enforces `ContextImageMaxMB` and publishes through the storage backend under content-addressed keys.
- **Reuse.** A new commit with unchanged lockfiles rebuilds only the source image, from a delta (target under 10 s for repositories under 100 MB). A lockfile change rebuilds the dependency image.
- **Prebuild.** githubd push webhooks on tracked branches start builds before any run asks for them. A refresh schedule covers non-git static sources.
- **Credentials.** No tenant secret is placed in a build. Dependencies from private registries are open question 1.

### 3. Attaching to a run or session

- **Drives.** Two read-only drive roles, `context_src` and `context_deps`, are bound into the jail through the existing read-only staging (link or bind), as the base drive is. They are never copied into tmpfs.
- **Mounting.** guest-init mounts both read-only and builds an overlay:
  - lower: source over dependencies, so `node_modules`, `.venv` and similar appear at their in-repository paths;
  - upper: the run's scratch, or the session's `/workspace` drive;
  - target: `/work` for runs, `/workspace` for sessions.

  Writes never reach the shared images.
- **Cold boot** attaches the drives at boot.
- **Warm restore** (ADR-20261027090015 §1):
  - preset snapshots are taken with two empty context slots, backed by tiny placeholder images and never mounted in the guest;
  - at restore, vmmd stages the version's images and points the slots at them, using the Firecracker drive update it already issues for rate limits (`PATCH /drives/{id}`), before resuming;
  - guest-init rescans the virtio-blk capacity and mounts on its attach command.
- **The restore path must be proven.** A metal test must show the rescan and mount after restore before the warm path is on. Until then, a run with a context restores without it and falls back to cold boot (ADR-005).

### 4. Dynamic sources and consistency

- **Tools.** Dynamic sources appear as capability-gateway tools (ADR-20261027090016), for example:
  - `context.deploys` and `context.logs(query, since)`;
  - `context.errors`;
  - `context.db.query` on the clone;
  - `context.s3.list` and `context.s3.get`;
  - connection tools.
- **Pins.** Every run records pins so its view is consistent and reproducible:
  - logs and errors up to the run's start;
  - the database clone point;
  - S3 listings as of the run's start, with object versions where the bucket has them.
- **Trust.** Content from dynamic sources, and from public repositories, is untrusted for taint (ADR-20261027090016 §4). A seller can mark a private repository trusted, and the audit records it.

### 5. Distribution, cache and scale

- **Node cache.** Agent nodes keep images on local NVMe, per account, least recently used, within `ContextCacheNodeMaxPercent` of the data disk.
- **Affinity.** agentd and schedd prefer nodes that already hold a run's version, as with snapshot affinity. On a miss, the node fetches the images from object storage before attaching.
- **Fan-out.** A hundred runs on one version fetch the images once per node and share its page cache.
- **Builds.** Context builds use builder slots on agent nodes, with ADR-207 cache affinity, and never outrank tenant wakes.
- **Retention.** A context keeps its newest `ContextVersionsRetained` versions plus any a run pinned. Older images are deleted.

### 6. Performance targets

| Step | Target |
|---|---|
| Attaching cached images (bind plus overlay) | under 300 ms |
| Trigger to first tool call, warm preset and cached images | under 4 s (today 8–60 s for a checkout and install) |
| Per-commit source image build, repository under 100 MB | under 10 s |
| Cache miss, 1 GB of images from object storage | under 5 s on the agent-node network |

These are verified with the keyless experiment rig (`scripts/experiments/agent-runs/memory`). It compares PR triage with context drives against a fresh checkout and install, on time to first tool call, CPU-seconds and memory, before contexts are turned on for anyone.

### 7. Security

- **Per account.** Images belong to one account. There is no dedup across accounts; within an account, images dedup by content.
- **Builds stay off hosts.** Untrusted install scripts run only in builder microVMs. imaged never mounts a guest-built filesystem.
- **Secrets.** Every image passes the secret scan. Build-time credentials are never baked in.
- **Read-only, block devices only.** Guests cannot change the shared images. No host directory is shared.
- **Credentials** for dynamic sources stay in outboundd (ADR-20261027090016, ADR-20261027090017).
- **Production data** is reachable only through point-in-time clones, never the live database. Masking is open question 2.
- **Policy and audit.** A context can only narrow a run's policy. Every attach and every dynamic read is audited (ADR-20261027090016 §6).

### 8. Pricing and economics

- **No fee.** Contexts are a software feature. Images count against the plan's included object storage (1, 10, 50 or 200 GiB, ADR-1350). Builds count against build limits. The node cache is platform cost.
- **Lower cost per run.** Contexts remove most per-run setup. In the economic plan, a run that reinstalls its dependencies costs about 14× a light run, and shared images cut memory per run through the shared page cache.

## Rollout

All steps stay on local branches, behind the internal `agents` capability, after ADR-20261027090016.

1. This ADR.
2. Tables, apid intents, and version resolution in agentd.
3. The context build job: a builder microVM, two tar outputs, imaged assembly, the secret scan and publishing.
4. Drive roles, cold-boot attach and the guest-init overlay. Metal tests:
   - writes never reach the images;
   - two runs on one version do not see each other's writes;
   - leakcheck is clean.
5. The node cache and placement affinity.
6. Warm restore with context slots, behind its own switch until the metal test passes.
7. Dynamic sources through ADR-20261027090016: `gregale_app`, `database` (point-in-time clones), `s3`, then connections and MCP.
8. Prebuild on push, and retention.
9. The keyless measurement against checkout and install. Contexts are turned on only after the §6 targets are met.

## Open questions

1. Dependencies from private registries: credentials through the capability gateway during the build, or the existing app-build path.
2. Masked read replicas as an alternative to point-in-time clones for large databases.
3. Lazy materialization for monorepos too large to prebuild.
4. Sharing images of public repositories across accounts (proposed: never).
5. Whether `s3` sources may also be baked into images when small.
