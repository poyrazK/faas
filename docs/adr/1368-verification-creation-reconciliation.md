# ADR-1368: Verification creation reconciliation

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Admission and completion can recover from lost responses, but an uncertain receipt creation still required a manual inspection/resume even when the original UUID could prove success. Explicit reviewed-creation and read-only inspection helpers already provide the selection contract.
- **Decision:** Reviewed app/graph creation in Go, Node and synchronous/asynchronous Python performs read-only reconciliation after eligible connection/stream failures, transport timeouts or HTTP 502/503/504. Send exactly one creation POST with the caller-selected UUID. Never generate a replacement UUID, repeat the POST or obtain another review automatically. Permanent failures and successful-but-invalid receipt responses retain existing explicit failure behavior.
- **Bounds:** Recovery gets at most five seconds, additionally bounded by the original caller context/signal and the earliest requested TTL measured from the creation attempt. Additional transient GET attempts use the existing status-read retry budget (default three, range zero through eight); zero still permits the initial reconciliation GET. Once observed, the receipt's own original expiry must remain valid. Synchronous Python clamps configured transport timeouts to the remaining budget, checks stop events between requests and interrupts backoff; asynchronous Python and Node also interrupt in-flight recovery/callback waits. No receipt deadline is renewed.
- **Proof:** Validate the original UUID, app/project/environment, deployment and service targets, review digests, manifest and graph members, consent, concurrency, policy revision, exact plans and original lifetime. Freeze the mutable fields used for proof before invoking creation or recovery callbacks. Reject expired, blocked or cancelled receipts, failed/malformed resources, duplicate graph identities and incomplete passed results. A matching pending/passed receipt may return to the caller; normal resume/admission and fresh qualification remain server-authoritative. Reconciliation itself admits no resources.
- **Failure:** Preserve the typed creation error, original UUID, attempted flag and original write cause when proof is missing, malformed, unreadable or interrupted. Preserve native Python task cancellation with its original ID, attempted flag and uncertain write cause. Callback failures stop recovery. Explicit reconciliation methods retain exactly one GET and can inspect matching expired or terminal receipts; they do not implicitly execute anything.
- **Progress and options:** Creation options add `StatusReadRetries`/`statusReadRetries`/`status_read_retries` and `OnProgress`/`onProgress`/`on_progress`. Python also accepts the existing runner-style `stop_event` control. Emit sanitized `reconciling` events with `operation: creation` and existing `retrying` read events. The CLI forwards its existing retry/progress settings, continues the same receipt after proof, and keeps JSON stdout as one final result. Existing recovery-ID announcements remain intact.
- **Validation:** App/graph committed creation, 503 responses, missing commit and permanent read failures; bounded retries, disable and invalid budgets; review, lifetime, consent, concurrency, ownership and membership drift; expired/cancelled receipts, failed resources and incomplete passed results; callbacks, deadlines and native cancellation; frozen input and custom Go plan representation; SDK suites, CLI continuation without replacement work, race checks, synchronization and lint. The central five-second limit is checked against every SDK by the synchronization gate. No endpoint or database changes.
