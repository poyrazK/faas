# ADR-1643: Managed worker service probes

- **Status:** accepted
- **Date:** 2026-10-17
- **Decision:** Extend ADR-1642's managed HTTPS verification to active worker callers. Require the frozen workload class and effective execution mode to agree: HTTP with request/service mode, or worker with worker mode. Targets remain HTTP request/service workloads. Jobs, held candidates, HTTP edges and unknown or inconsistent contracts remain unsupported.
- **Isolation:** Use the existing fresh, command-free app-task boot path. Stage the task marker before guest boot; it takes precedence over worker mode and all image entrypoints. Probe tasks never restore worker snapshots, launch the worker listener or enter serving-instance inventory. A service probe does not publish or consume queue work. Strict all-binding verification still requires separate `--queue-publish` consent for eligible queues.
- **Authority:** Keep the existing `managed-https-v1` guest/API contract and all frozen caller, target, deployment, scope, release and policy fences. Revalidate before admission and dispatch and before reusing evidence. The caller's live app defaults cannot replace its frozen execution mode or binding map. No schema or migration changes are needed.
- **Reviewed graph prerequisite:** Service-bound workers use a distinct `worker-queue-v3` qualification policy that hashes their reviewed service identities and effective transport alongside the queue smoke. Queue-only workers keep `worker-queue-v2`. Individual claims still reject service dependencies; atomic graph execution validates each live dependency route before capture and restored smoke. Qualification URL staging and route policy use the effective frozen runtime, including reviewed overrides of baseline settings.
- **Acceptance:** Cover worker admission and stale receipts in state, PostgreSQL, API and scheduler regressions, plus task boot and entrypoint isolation. Version 2 of the managed-service native suite requires a reviewed worker with a custom HTTPS dependency and a push queue, single and strict batch CLI verification (including an explicit blocker for an unsupported queue), separate release/policy invalidation and unchanged pending queue work. Independently retire all owned workloads and check host leaks. Version 1 HTTP-only evidence cannot qualify worker support.
- **Limits:** Route verification does not establish worker process behavior, consumer health or resident configuration adoption. Managed zero-traffic worker queue-canary admission was a separate gap, addressed by [ADR-1644](1644-managed-worker-queue-canaries.md); strict batch coverage cannot waive it. Native test-metal and leakcheck evidence remains required; portable tests and tagged compilation do not supply it.
