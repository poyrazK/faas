# ADR-20261026090000: Durable request rollback acceptance recovery

## Status
Accepted.

## Context

A checked rollback already commits a durable operation and readiness outbox in
one transaction. Its UUID was generated by the server, so a lost HTTP reply left
an expired MCP plan without an exact identity to read. Current traffic cannot
prove whether that original request was accepted or completed.

## Decision

Accept an optional `Rollback-Attempt-ID`, exactly 32 lowercase hexadecimal
characters, for an exact manual default-scope request-deployment rollback. Its
UUID representation is the original operation ID. Alert attribution, release
acknowledgement, services, workers and implicit deployment selection are excluded.
APID validates the header and exact UUID pair. Both stores check attempt reuse
under the app lock before changing target readiness or inserting the operation.
Transactional app reads use that same connection, so competing attempts cannot
exhaust the pool while the lock holder waits for another connection.
A matching accepted attempt returns `rollback_attempt_accepted`; a different
original pair or reason returns `rollback_attempt_conflict`. Terminal operations
cannot be restarted by reusing the ID. Existing ownership, serving CAS, artifact,
release, contract and binding gates remain authoritative.

No database migration or new receipt endpoint is needed. The existing operation
ledger and read endpoint retain the immutable app, scope, pair, reason and creation
time. Existing workers preserve these identities while updating progress; N-1
workers need no new receipt fields. The random operation ID plus a canonical
request fingerprint bind the original attempt without relying on the HTTP cache.

Before its first POST the bridge atomically persists the attempt marker and an
encrypted, minimal reference: attempt ID, exact target/current IDs, request hash
and original action binding. It never gives legacy attempted plans replacement
identities. An independent namespace survives older bridge rewrites, shares action
history retention/capacity and is purged with the connection grant.

`gregale_get_action_outcome` with its default apply phase verifies the exact
operation and original request hash, returning only redacted acceptance and an
exact `gregale_get_rollback` call. Recovery works after expiry and with writes
disabled. History/resources/prompts discover the same lookup without fetching
native evidence. Storage, consent, immutable app identity and retained references
are checked again before releasing the result. Recovery does not alter recorded
history or restore authority to apply the expired plan.

## Consequences

Acceptance is historical, even when the operation later fails. Read operation
progress and current deployment traffic/health separately. Missing or mismatched
evidence remains unresolved and never proves non-commit. Service rollback,
service-abort and environment-promotion rollback recovery remain separate work.
Older APIs may ignore the additive header and create another operation UUID;
its outcome remains unresolved rather than being inferred from current traffic.
Native/provider execution qualification remains separate from portable fixtures.

## Validation

Race tests cover lost replies, restart/expiry, read-only discovery, independent
completion observations, malformed evidence, final guards, legacy non-backfill
and pruning. Mem/Pg tests cover atomic receipt creation, concurrency, stale CAS,
terminal retries, conflicting requests and ownership. HTTP tests drop a native
accepted response and read the existing ledger without write access. Typed SDK,
OpenAPI, documentation and pinned real-client acceptance cover the same contract.
