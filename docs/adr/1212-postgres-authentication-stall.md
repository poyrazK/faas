# ADR-1212 · Authentication challenge stalls after verified PostgreSQL TLS

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Extend ADR-1211's bounded persistent connection control with the authentication phase. After both TLS legs are verified, validate and hold the first cleartext-password, MD5-password or SASL challenge before it reaches the client. Preserve the challenge bytes and normal authentication on release. Apply the existing 1–5000 ms per-attempt bound, 100 control/hold-record caps, disconnect cancellation and joined shutdown. Do not stall AuthenticationOK, rejection or SASL continuation/final messages.
- **Why:** TCP and SSLRequest readiness can succeed while login never completes. TLS verification must not be confused with a usable pooled database client, and failed login attempts must not leave waiters or backend processes behind.
- **Consequences:** Evidence records the authentication phase and timing, validated challenge count and pending logins separately from TLS negotiations; it retains no credentials, mechanism payloads or endpoint identities. Pending login ends at initial ReadyForQuery or connection closure. Real verified-TLS PostgreSQL tests require bounded caller-selected retries, queued acquisition failures, release/recovery, expiry and shutdown using the normal SCRAM exchange. Independent SQL checks every client-backend PID introduced by each test retires, including incomplete logins. Wrong-password rejection remains intact after release. Portable tests cover held challenge bytes, cancellation, AuthenticationOK/rejection pass-through and malformed challenge negative controls. Recovery requires one encrypted idle client and no waiters; final cleanup leaves no logins, clients, backend sessions, timers or sockets. Further authentication-message faults and native/deployed qualification remain separate work.
- **Rejected alternatives:** Stalling SSLRequest again does not exercise authenticated connection readiness. Logging or replaying client authentication payloads is unnecessary for phase evidence. Manufacturing AuthenticationOK or selecting a weaker authentication mechanism would hide login failures. Considering TLS completion as pool readiness would mask stuck authentication. Retiring only authenticated application-name sessions can miss backend processes that never completed login, so the disposable fixture also compares backend PIDs.
