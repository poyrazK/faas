# ADR-20261115194000: Platform alerts for outages and failing crons

Status: Accepted
Date: 2026-11-15
Related: ADR-045 (alert rules), ADR-749 (alert channels), ADR-20261109153000
(ratio alerts need a minimum request count), ADR-20261026201726 (cron
schedules), ADR-20261107140000 (agent approval emails, the delivery pattern
reused here)

## Context

The 2026-11-15 production rounds found two failures nobody was told about:

- A microservices-demo frontend answered 100% 5xx for more than five hours.
  Alerting is opt-in: an account gets nothing until it writes an alert rule,
  and an alert rule needs a webhook or channel the customer sets up.
- A cron calling a removed route got HTTP 404 every 15 minutes for weeks. Each
  run woke and billed the app (about 250–500 GB-h a month), and nothing ever
  stopped it or said so.

## Decision

The platform detects both conditions itself and emails the account. The
customer configures nothing.

1. **Failing crons pause.** Before schedd dispatches a due HTTP cron, it
   checks the cron's newest `CronFailurePauseRuns` (10) finished runs. When all
   of them failed, and the oldest was scheduled at least `CronFailurePauseSpan`
   (24 h) ago, schedd sets `crons.suspended_reason = 'failing'`. In the same
   transaction it queues a `cron_failing_paused` notice. A run counts once it
   has started, so an occurrence that missed its start deadline is not the app
   failing. A paused cron does not fire or bill. Editing the cron (schedule,
   path or `--enable`) or promoting a deployment resumes it. Only runs after
   the last pause count toward the next pause, so a resumed cron gets its full
   allowance again. Command crons are not covered yet: their runs are app
   tasks, not invocations. (Amended 2026-11-28: the whole failure streak
   counts, see below.)
2. **Outages are detected fleet-wide.** Every 5 minutes, meterd reads every
   app's error rate in one Prometheus query: 5xx over 2xx and 5xx, the same
   population as `error_rate_pct` alert rules. An app is in outage when its
   rate is at least `AppOutageErrorRatePct` (90%) over `AppOutageWindow`
   (15 m) on at least `AppOutageMinRequests` (20) requests. meterd then queues
   an `app_outage` notice, unless the app has an enabled `error_rate_pct` rule
   of its own, because its owner already chose how to be told.
3. **One sender, deduplicated.** Notices live in `platform_alert_notices`,
   with one pending row per (kind, subject) and none within
   `PlatformAlertCooldown` (24 h) of the last. meterd claims them. It emails
   the app's owner, or the owners and admins of the app's organization, on
   their verified addresses. It retries a mail failure 5 times and trims
   finished rows after 30 days. Delivery is counted in
   `meterd_platform_alert_notices_total{kind,outcome}`.

All thresholds live in `pkg/api/limits.go`.

## Consequences

- An outage or a dead cron reaches a person within minutes or a day, without
  a webhook to set up. Accounts that write their own error-rate alert are
  not emailed twice.
- A cron that fails on purpose for a day stops running. The email says why
  and how to resume it, and `gregale cron get` shows the reason.
- The outage check depends on Prometheus. Without it, only cron notices are
  sent.
- Not covered here, fixed separately on 2026-11-16: delivered cron, queue,
  async and delayed-task invocations now record request metrics and HTTP
  log rows as internal service calls do (client family `gregale-<source>`,
  still no financial usage event); gateway error groups are titled
  `HTTP 500 Internal Server Error on /route`, not `unhandled: /`; the
  service map shows no latency, not 0.0 ms, for an edge with no successful
  call.

## Amendment 2026-11-16: default alerts for checks and SLOs

A second microservices-demo run had a synthetic check on `GET /cart` failing
for hours and its SLO burning at 126x, and nobody was told: checks and SLOs,
like error rates, only alert through a rule with a channel. Owner decision:
alert the account by default.

- meterd's platform alert pass (every 5 minutes) also queues
  `check_failing` when an enabled check failed its last
  `SyntheticCheckFailingRuns` (3) runs, and `slo_burn` when an SLO's
  multi-window burn rate (`slo.MultiWindowBurn`, the value
  `slo_budget_burn` rules read) is at least `PlatformAlertSLOBurnRate`
  (14.4, the fast-burn page threshold).
- Either is skipped when an enabled alert rule names the check
  (`synthetic_check_id`) or the SLO (`slo_id`).
- Same recipients, cooldown and sender as the outage notice.
  `gregale alert check create` and `gregale alert slo create` say so.
- SLO notices need Prometheus; check notices read only the run history.

## Amendment 2026-11-28: the whole failure streak counts

Decision 1 looked only at the newest 10 finished runs. For a cron that runs
more often than every 2.4 hours those 10 runs span less than 24 h, so a
15-minute cron that failed for weeks never paused (async assessment
2026-11-28). schedd now counts the cron's unbroken failure streak: every
finished run since its last successful one (and since its last pause). The
cron pauses when that streak has at least `CronFailurePauseRuns` (10) runs
and its oldest run was scheduled at least `CronFailurePauseSpan` (24 h) ago.
A successful run still resets the streak; a daily cron still needs 10 failed
days.
