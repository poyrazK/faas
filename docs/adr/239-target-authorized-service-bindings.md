# ADR-239: Target-authorized internal service bindings

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** New project workloads default to caller-side `declared` service bindings. A target may independently allow only named same-account callers through `x-gregale-allow-callers`; an explicitly empty list denies all callers. Existing manifests without a target allowlist retain same-account reachability, and existing callers without an explicit policy retain their persisted policy on project reapply. Private app ingress is available on every plan.
- **Why:** An injected discovery URL is not an authorization grant, and caller-only declarations cannot let `billing` decide whether `frontend` may call it. Private service deployment must not require an unrelated plan upgrade.
- **Consequences:** The service proxy checks both the caller's binding and the target's allowlist before endpoint lookup or wake. Allowlist names are stable logical app slugs; the list is capped at 100 names to match the Scale deployed-app ceiling. Same-project PR previews are still constrained by the existing preview policy. The project scanner validates and persists the target list, and diffs report policy changes. No public hostname is required for internal routing. Direct API app creation retains the legacy account policy until a separate API contract and migration are designed. This does not add RPC code generation, environment-specific bindings, or a service mesh.
- **Rejected alternatives:** Derive target consent from `depends_on` (the target never declared it); silently change existing account-policy apps (breaking change); enforce by DNS or guest firewall only (bypassable and too late to prevent wake); remove plan validation entirely (unknown plans must fail closed).
