# ADR: The event GA gate: targets, durability and the evidence that proves them

Date: 2026-10-29
Status: Accepted
Amends: spec Appendix D V12 (adds the GA target rate and the failover drill)
Related: [ADR 20261023215834](20261023215834-event-plan-caps.md) (per-plan caps), [ADR-1236](1236-paging-set.md) (event paging), [ADR 20261028095548](20261028095548-event-job-lifecycle.md), [ADR 20261028131500](20261028131500-event-claim-lease-renewal.md), ADR 20261029012000 (backlog throughput), `docs/runbooks/ControlPlaneFailover.md`

## Context

The 2026-10-25 event audit found no GA gate with numeric targets. V12 had
only run on the 2 vCPU test node, where it sustained about 20 events/s end
to end (about 50/s on a quiet host). There had been no failover drill. The
asynchronous Postgres standby also means that an unplanned failover can lose
events already acknowledged with 202, and nothing told customers so.

The owner settled four questions on 2026-10-29:

1. the GA throughput target is 50 events/s;
2. the standby stays asynchronous, and the loss window is documented;
3. the warm standby is enough: GA does not wait for a multi-host control
   plane;
4. the evidence runs on the GCP test node now, as provisional evidence, and
   is repeated on the OVH reference host before promotion.

## Decision

### Targets

On one control plane, with every number taken from a V12 run
(`make bench-event-substrate`):

| Target | Value |
|---|---|
| Sustained end-to-end rate | **50 events/s**, with ≥ 95 % of the offered rate achieved and nothing pending after the settle window |
| Publish to handler | p95 ≤ 5 s at the target rate |
| Ordered lanes (20 keys) | the same criteria at 20 events/s |
| Per-account caps | stay at ≤ 50 % of the sustained rate (V12); Scale's 6.9 events/s is 14 % of the target |
| Routing after a schedd crash | resumes within 1 minute (claim lease, ADR 20261028131500) |
| Recovery after an unplanned control-plane failover | RTO 15–30 minutes (`ControlPlaneFailover.md`); warm app traffic keeps flowing meanwhile |
| Events lost on an unplanned failover | only those accepted within the standby's replication lag, which `FaasPostgresStandbyLagHigh` bounds; normally seconds |

### Durability

Acceptance means the event is committed on the primary database. The
standby stays asynchronous. A synchronous standby would add a round-trip to
every publish, and would make the standby's health gate publishing. On an
unplanned failover, events accepted within the replication lag can be lost.

The event docs and the failover runbook state this. Producers that must not
lose an event republish it after a failover with the same identity: one that
survived answers `duplicate`, and one that was lost is accepted again. A
planned switchover loses nothing.

### Evidence

Promotion of the `events` capabilities to GA needs all of:

1. **V12 at the target:** a run that meets every target above, kept in
   `docs/ops/evidence/` with the commit it measured. Runs on the test node
   are provisional, and promotion needs one on the OVH reference host.
2. **Failover drill:** `make drill-event-failover` against a primary and
   streaming standby. It publishes at the target rate, crashes the primary
   mid-load (an immediate stop, no checkpoint), promotes the standby, and
   records:
   - acknowledged and surviving events, and the loss window;
   - the time from the crash to the first accepted publish on the new
     primary;
   - that routing resumes on the new primary and every surviving receipt
     settles.

   The test-node drill is provisional. Promotion needs the
   `ControlPlaneFailover.md` drill between the OVH hosts.
3. **Operations:** the alerts, runbook and owner from ADR-1236's amendment,
   already merged.
4. **Launch items:**
   - an events journey in `tests/journeys`;
   - published docs;
   - scorecard evidence in the capability catalog.

## Consequences

- The numbers are fixed before the evidence runs. A run that misses one is a
  finding to fix, not a target to lower.
- Customers see the failover loss window before GA, along with the way to
  recover from it.
- A synchronous standby can come later through another ADR if a customer
  needs zero loss.
