# ADR-496 · Object-storage binding verification

- **Status:** accepted
- **Date:** 2026-10-02
- **Decision:** Extend the existing deployment-attached task canary, CLI selection and durable revision-aware inventory evidence to managed object-storage compute bindings. The guest uses the six injected environment variables and makes one signed, path-style `ListObjectsV2` request with `MaxKeys=1`.
- **Why:** Metadata, runtime freshness and rotation progress cannot establish that app credentials can reach the gateway and read the storage provider. Gregale's `HeadBucket` checks gateway authorization without contacting the provider, so it is insufficient for this canary.
- **Boundaries:** Five-second request deadline, one attempt, no redirects, no pagination, response XML capped at 64 KiB, and no object writes. Require a successful list response identifying the selected bucket. Reports expose only stable environment, configuration, connection, authorization and bucket-access diagnostics. No endpoints, access keys, secret keys, object names or raw SDK/provider errors appear in reports. A connection passes when an HTTP response is received; authorization and bucket access pass only on a validated successful list response. Non-authorization HTTP failures do not imply accepted credentials.
- **Evidence:** Reuse the app task verification pin and latest-admission projection from ADR-494. Include the internal binding ID and latest retained rotation stage ID in configuration identity, alongside public metadata and the existing app runtime configuration stamp. This detects credential cutover before a separately retriable rotation stamp. Select the latest stage by creation time and ID, including finalized stages, so cleanup does not change current credential identity. An additive index supports this metadata-only query without reading credential material or app-secret rows. The public inventory omits internal IDs and raw report details. Storage metadata and evidence retain the `storage:manage` or admin boundary.
- **CLI:** `--object-storage <PREFIX>` checks a managed binding in the scope selected for manual tasks. It is mutually exclusive with `--postgres`, `--all` and positional service selection. `--all` includes object storage in that scope and fails on unreadable supported-family metadata. Both forms reject a pass if task admission selected another deployment or scope.
- **Limits:** Evidence establishes point-in-time bucket-list read access from a fresh task guest. It does not establish write access, object-download capability, continuous provider availability or adoption by resident app instances. Runtime freshness remains independent. This adds no executor, scheduler lifecycle or external connectivity service.
- **Migration rollback:** Remove object-storage pins from retained task rows before restoring the older two-family constraint. Task execution history remains retained; service and PostgreSQL evidence is preserved.
