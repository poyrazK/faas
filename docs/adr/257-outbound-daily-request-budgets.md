# ADR-257: Durable outbound usage and daily request budgets

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Persist an admitted-request counter and optional daily request limit per outbound integration. Account owners set limits on customer-owned integrations through the API; operators may configure them for operator-owned integrations in `outboundd.toml`. The counter is updated in the same Postgres transaction and row lock that grants the integration's rate/concurrency admission and lease. Limits reset at 00:00 UTC. A request consumes one unit when admitted, including when the provider later fails; requests rejected before admission consume none.
- **Plan ceiling:** The maximum configurable per-integration limit is plan-specific (Free 100,000; Hobby 1,000,000; Pro 10,000,000; Scale 100,000,000 requests/day). `outboundd` clamps a stored limit to the account's current ceiling on every integration resolution, so a plan downgrade takes effect without a reconciliation job. An absent customer-selected limit remains uncapped.
- **API:** Account owners can read the current UTC-day count and reset timestamp, and can set or clear a limit on a customer-owned integration. API reads expose counts and effective policy only; no credential material is added to the usage surface.
- **Consequences:** The single current-day counter stays bounded to one row per integration and is shared across gateway replicas. Request counts are durable but are not a historical billing ledger. Dollar spend, token counts, and provider-specific units require provider adapters and are not inferred from generic HTTP traffic. Daily-limit rejection returns 429 with `Retry-After` to the next UTC midnight.
- **Rejected alternatives:** In-memory counters lose usage across restart and disagree across replicas. Incrementing in a separate post-request write can over-admit concurrent calls at the limit. Estimating dollar spend from generic status/body data is not reliable across providers.
