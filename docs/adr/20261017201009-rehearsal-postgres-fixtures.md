# ADR-20261017201009 · Isolated PostgreSQL rehearsal fixtures

- **Status:** accepted; disabled pending isolated PostgreSQL and native qualification
- **Date:** 2026-10-17
- **Decision:** Add a versioned SQL-fixture adapter to warm, contained command rehearsals. apid creates a fresh database and an unprivileged login on a dedicated disposable PostgreSQL cluster for each run. A private gateway listener authorizes the live rehearsal caller and the exact database/login before forwarding PostgreSQL traffic. The runtime never falls back to a managed binding, customer URL, or the control-plane database.
- **Why:** Application-produced behavior JSON cannot independently establish database effects or starting-data parity.
- **Consequences:** Pin fixture bytes and selected table/column contracts. Independently read bounded, canonical row multisets before and after execution; record lock-wait observations. Fence new connections, disable database connections, reject unfinished SQL, terminate retained pools, collect final committed state, and confirm database/login deletion before evidence becomes complete. Different initial data, collector loss, unsupported catalog objects, incomplete actions, bounds violations, or failed cleanup cannot pass comparison.
- **Rejected alternatives:** Running fixture SQL as an administrator, reading production, sharing databases between revisions, trusting command output as a database receipt, and treating SQL transaction rollback as whole-application undo.

The first adapter supports PostgreSQL 16+, a single private gateway/fixture-cluster placement, sanitized SQL files and ordinary persistent tables with built-in scalar columns. It uses no provider API and imports no production snapshots. Each run owns one database and login with a fixed expiry and an apid process owner. A restarted collector cannot adopt evidence; expired journals are cleaned independently of enrollment gates. Customer SQL and table reads execute only under the generated login. Final collection rotates its password, connects the restricted reader, and then disables login/database connections. Administrative connections never evaluate customer table projections; `row_security=off` rejects forced policy filtering. The cluster must be separate from platform/customer databases and contain no network-capable extensions. The adapter stays off by default.

SQL queries and server-side identifier/literal quoting live in sqlc sources. Nontransactional CREATE/DROP DATABASE commands and bounded table SELECT statements are executed only from these server-produced command strings. Declared fixture SQL is an explicit customer-code execution input, executed with the restricted fixture role; it is never interpolated into a platform query. Identifiers, passwords, connection URLs, query text and raw SQL errors are excluded from diagnostics.

The private PostgreSQL proxy has no public listener or arbitrary target selection. Its single operator-selected loopback target must match the qualified cluster. It accepts only the exact database/login from a live journal, rejects extra startup options and cross-run identities, and rechecks admission before forwarding. Database freezing remains authoritative for existing connections. Ordinary managed database bindings, services with their own databases, lifecycle fault matrices and recipe cleanup commands remain unsupported in this initial scope; the platform owns fixture cleanup.

Database evidence is separate from application-reported behavior. It records the run, app, deployment, dataset and collector contract, initial and final selected rows, row changes and sampled maximum lock wait. Lock budgets are assertions rather than exact timing comparisons. Sampling does not promise detection of every short wait. Missing samples, owner loss, active SQL at sealing, or an unsealed action window are inconclusive. Only code/configuration/migration plans are release candidates; fixture databases are destroyed.

The durable journal pins a hash of the PostgreSQL system identifier, administrative database OID and fixed local endpoint. Every administrative connection rechecks this identity; a changed cluster or endpoint cannot acknowledge deletion of an older fixture. Active journals block owner purging; confirmed complete/deleted journals follow app/account cascading retention.
