# ADR-20261021223225: Path routes in gregale.yaml

Date: 2026-10-22
Status: Accepted
Related: [ADR-091](091-edge-rules.md) (edge rules: `kind=route`, `kind=rewrite`)

## Context

One domain often fronts several apps: `/api/**` on a backend, `/**` on a web
app, `/hooks/**` on a worker-facing service. Gregale already routes this at
the edge: a `kind=route` edge rule sends a host and path to another app of the
same account, checked at request time (ADR-091), and a `kind=rewrite` rule
changes the path the target sees. Both are created imperatively, rule by rule,
with `gregale edge-rules create`.

Platforms that deploy a frontend and its backends as one project declare that
layout next to the code, so it is reviewed, versioned and deployed with the
services. `async_routes` already does this for async edge rules: rules owned by
a manifest key, reconciled per app on source-ref and project deploys, never
adopting or deleting unmanaged rules.

## Decision

- `gregale.yaml` accepts `routes`:

  ```yaml
  routes:
    - name: api
      match_host: shop.example.com
      match_path: /api/**
      to: api              # app slug, or the workload name in a project deploy
      strip_prefix: /api   # optional: /api/items reaches the app as /items
      match_methods: [GET, POST]   # optional; every method by default
      priority: 50                 # optional, 0-10000, default 100
  ```

- **Rules belong to the target.** Each route becomes a manifest-owned
  `kind=route` edge rule on the `to` app (key `path-route:<name>`), targeting
  that app. `strip_prefix` adds a `kind=rewrite` rule (key
  `path-route:<name>:strip`, From = the prefix, To = `/`) on the same app. The
  gateway's existing same-account check at match time therefore always holds.
- **Reconciliation is the async_routes contract**, through one shared
  reconciler (`reconcileManifestEdgeRules`) that async routes now use too:
  names are stable per target app; later deploys update a matching rule in
  place, remove stale manifest-owned rules and create new ones; unmanaged
  rules are never adopted or deleted, and an unmanaged rule of the same kind
  on the same host, path and methods fails the deploy with guidance. Omitting
  `routes` leaves managed routes unchanged; `routes: []` clears them. Project
  deploys reconcile selected workloads only, and `--no-triggers` leaves routes
  unchanged, exactly like async routes. Both rules go through the edge-rules
  API's body validation and the plan's edge-rule quota.
- **Validation at load time:** names and targets are `[a-z0-9-]+`; hosts are
  names, not URLs; paths are globs, and an OpenAPI-style `{param}` path is
  refused with the equivalent glob; `strip_prefix` is a literal prefix of
  `match_path` without a trailing slash; two routes with the same host, path
  and methods are refused. A single-app deploy may only declare routes to
  itself; a project deploy may name any of its workloads.
- **Rewrite to the root strips cleanly.** `ApplyEdgeRuleRewritePath` (shared by
  the gateway and the trace preview) returned `//items` for `/api/items` with
  From `/api` and To `/`. It now returns `/items`, and `/api` itself becomes
  `/`. Every other rewrite keeps its result. An existing rule with To `/` and a
  non-empty From could only have produced the double slash, so this changes
  nothing a customer could have relied on.
- Organization-owned projects refuse `routes` for now, like async routes,
  pending the organization ownership review of manifest-owned edge rules.

## Consequences

- One manifest can describe a domain's whole URL layout, deployed with the
  workloads it names. A single-app deploy rolls its route changes back with a
  failed deployment; a project deploy rolls back the routes step if any of its
  route writes fails.
- Imperative `kind=route` rules keep working beside manifest routes; a
  conflicting pair is reported instead of silently shadowed.
- Plan output reports routes as a warning line; per-rule plan rows can follow
  if customers need them.
