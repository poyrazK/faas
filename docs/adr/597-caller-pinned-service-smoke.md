# ADR-597: Exact caller deployment for service smoke tests

- **Status:** accepted
- **Date:** 2026-10-04
- **Context:** ADR-277 pins the target of a service handler GET, but its caller uses automatic manual-task deployment selection. Operators cannot explicitly test a zero-traffic caller candidate, and the CLI previously accepted a passing guest report without checking all request identities or HTTP status independently.
- **Decision:** Add `bindings smoke --caller-deployment ID|vN` and `--target-deployment UUID`. Keep `--deployment` as the target alias; reject conflicting aliases. The caller selector is optional, preserving automatic caller selection when omitted. Revision handles resolve within the caller app.
- **Admission:** Add `smoke_deployment_id` to direct app-task requests, reserved for the platform's five-argument service smoke command. It is mutually exclusive with `verification_deployment_id`. Require a canonical service, exact nonzero target UUID, bounded origin-form path and valid status policy. Require the service to be declared on the caller. Select only an app-owned, materialized live caller deployment, including candidates with zero traffic. PostgreSQL locks the app and deployment rows and checks liveness in the same statement as task creation; MemStore checks under its mutex. Exclusive-operation task admission rejects either selector. Generic commands retain automatic selection. No database migration or VM lifecycle change is required.
- **Target authorization:** Retain the gateway's existing target ownership, service policy, preview resolution, wake and header-stripping checks. Admission does not duplicate that resolver. A target that becomes unauthorized or unavailable fails the smoke request.
- **Receipts:** Before waiting, the CLI confirms task app, caller deployment, scope, manual kind and exact argv. Every poll must retain the admitted task ID and selection. Mismatched active tasks receive a bounded cancellation request. Success requires a complete JSON guest report matching service, target, URL, query-free path and expected status policy, plus any supplied app, caller or task identity. Independently require the expected HTTP status, succeeded task, zero exit code, no task failure, no guest error and untruncated output. JSON and human reports use CLI-owned identities and never echo the request query or response body.
- **Limits:** This invokes the target handler using the caller deployment's task runtime and current scoped configuration. It does not exercise the caller's own application handler, create binding-verification evidence, change traffic or automatically invoke handlers during `verify`, `check` or promotion. User interruption requests cancellation; CLI wait expiry leaves the bounded task running and reports failure. Older servers reject the unknown selector before task admission, and the CLI still validates returned selection.
- **Validation:** API selector and command validation; exact caller, scope and artifact selection; zero-traffic and foreign/unmaterialized/retired caller cases; retirement during admission; PostgreSQL locking and memory parity; CLI revision resolution, legacy alias, changed receipts, malformed/truncated reports, status/exit validation, wait expiry and bounded cancellation; OpenAPI and SDK regeneration.
