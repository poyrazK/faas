# ADR-1503: Month-end billing runs

- **Status:** accepted
- **Date:** 2026-10-13
- **Decision:** An account can bill one ended UTC calendar month for every customer in one request (`POST /v1/account/billing-runs`), or let a schedule (`PUT /v1/account/billing-run-schedule`) start that run for each month. A run drafts each customer's statement, optionally holds it on a completeness gap, finalizes it, and optionally exports it to the account's Stripe (ADR-1502). apid processes runs in a background worker; the run and its items record what happened to each customer.
  - **Customers.** At start, the run lists every app consumer and platform tenant with billable usage in the month. Plans have no fixed fees, so a customer without billable usage has nothing to bill.
  - **Tenant or app statement.** Usage attributed to a platform tenant is billed on the tenant's cross-app statement. When a run includes platform tenants, an app consumer with any tenant-attributed usage in the month is skipped and the item says why. A run limited to `app_consumers` bills every consumer by app statement instead.
  - **Steps per customer.** Draft the month's statement (unchanged usage replays the latest revision). Skip it if ADR-238's handoff overlap rules would reject it. Check completeness for app consumers and, with `hold_on_gaps`, hold a consumer whose ledger misses requests telemetry saw. Finalize, unless the run only drafts. With `export: stripe`, export every finalized revision of the month that has no handoff, oldest first; a revision with a zero total is never exported, so free-tier customers get no empty invoices.
  - **Outcomes.** Each item ends `drafted`, `finalized`, `exported`, `up_to_date` (nothing new to bill and nothing left to export), `held` (needs attention, such as unpriced usage or a completeness gap), `skipped` (billed through a platform tenant, or already invoiced through the other path) or `failed`. The run completes when every item is terminal; held and failed items do not fail the run.
  - **Month.** A run may start once the month ended at least one hour ago (`BillingRunSettleDelay`), so gateway usage outboxes have delivered. A schedule waits `delay_hours` (1–240) after month end. It starts with the month in which it was created and catches up missed months in order.
- **Why:** Billing a month took four commands per customer: draft, completeness, finalize, export. An account with hundreds of consumers had to script that loop, and a laptop dropping mid-loop left the month half billed. A server-side run is resumable, visible, and can run unattended.
- **Consequences:**
  - **One active run per account.** A partial unique index allows one `queued` or `running` run per account; creating another returns 409 with the active run's ID. A completed month can be run again: late usage then becomes adjustment revisions, and finalized revisions already handed off stay `up_to_date`.
  - **Resumable.** Workers claim a run with a lease (`BillingRunLeaseTTL`) and process a bounded batch of items per tick. Every step is idempotent: drafting replays, finalizing a finalized statement is a no-op, and a Stripe export resumes its draft invoice. A crash re-processes the item after the lease expires. Item updates require the current lease.
  - **Retries.** Database errors and Stripe 5xx or network failures retry the item with backoff, up to `BillingRunItemMaxAttempts`, then mark it `failed`. Deterministic failures, such as a missing Stripe customer or a Stripe 4xx, fail the item at once with the reason.
  - **No duplicate drafts across paths.** Before creating a Stripe invoice, an export now checks the handoff overlap rules of ADR-238. It refuses a statement whose consumer windows another path already handed off, rather than leaving a stray draft when the handoff is rejected after the invoice exists. The run reports such items as `skipped`.
  - **Owners.** apid remains the only writer of statements, handoffs and exports. Runs, items and schedules are new apid-owned tables. Statement logic moved from HTTP handlers into context-based functions that the handlers and the worker share, so both apply identical rules and audit events, and finalized webhooks are relayed the same way.
  - **Limits.** Settle delay, schedule delay bounds, lease TTL, batch size, tick interval and retry attempts live in `pkg/api/limits.go`. Items are listed with a cursor; a run's size is bounded by the account's consumers and tenants.
- **Rejected alternatives:**
  - A CLI loop over the existing endpoints needs no new state, but cannot run on a schedule, stops when the client disconnects, and makes the operator reconcile partial progress by hand.
  - Holding every item when telemetry cannot verify it would block every month older than telemetry's 14-day retention. Only detected gaps hold; `unverifiable` and `partial` proceed and are recorded.
  - Choosing tenant or app billing per consumer from its current tenant link would infer historical ownership (rejected in ADR-238). The run decides from request-time attribution in the usage ledger.
  - Finalizing and sending Stripe invoices remains out of scope (ADR-1502): exports stay drafts.
