# ADR-1213 · Native qualification of PostgreSQL TLS authentication stalls

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Add a fourteenth real-VM, warm-profile case to the native resilience gate, raising its verdict version to 6. Deploy a read-only readiness caller and explicitly selected payment fixture. Package the existing protocol helpers with the provider, keep its proxy listener on guest loopback, and opt into a verified-TLS external DNS upstream. Generate per-case ephemeral loopback identity/control secrets on the runner and deliver them via existing sealed workload bindings. Use the existing application assertion command to exercise fixture phases without weakening staged-scenario validation or inventing platform fault matches.
- **Why:** Portable connection tests cannot qualify guest routing, secret delivery, deployment packaging, service lifecycle or backend retirement under Gregale. A read-only connection probe isolates this initial deployment case from write/COMMIT semantics.
- **Consequences:** Baseline SELECT 42 precedes three caller-selected authentication timeouts and two successful reads after clear. Each acquisition retires its connection, guaranteeing fresh login. Token/namespace-protected control fixes the fault to five seconds; normal provider connection and caller deadlines remain two/four seconds. A run-bound proof file must show stable proxy identity, exact attempts, positive authentication phase/timing and verified TLS, empty pools/connections and independent backend retirement. Cleanup stops the fixture and requires normal developer session/fault namespace/VM inventory retirement plus independent SQL, even after receipt rejection. A pre-fault PID inventory detects new client backends, including logins that never published their application name; the disposable fixture must not accept unrelated new clients during this case, and the check never terminates any process. Shared portable imports re-export the deployed helpers; real PostgreSQL tests exercise the same provider/caller/driver lifecycle and redaction. Old thirteen-case/version-5 verdicts do not qualify the expanded gate. No database port is publicly exposed, no egress policy is changed, and ordinary write serving remains the default. The external runtime database must have a publicly trusted TLS DNS endpoint reachable under guest egress policy; this gate does not provision it.
- **Rejected alternatives:** Running a proxy on host loopback cannot route a guest connection without extra forwarding/policy changes. Adding arbitrary exposed guest TCP listeners would exceed existing HTTP routing. Claiming native success from local tests or a blocked admission report would hide deployment gaps. Adding dummy platform faults solely to permit staged commands would manufacture evidence. Reusing checked-in private keys or recording sealed values in artifacts would make test trust persistent. Testing a synthetic successful write without a ledger would obscure the read-only nature of this connection case.
