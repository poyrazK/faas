# ADR-1360: Shared verification admission budgets

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Runner concurrency is local to an invocation. Concurrent CI workers can admit distinct steps of the same receipt beyond either worker's budget, despite step idempotency.
- **Decision:** Freeze optional `max_concurrency` at receipt creation, defaulting to two and accepting one through eight from the existing API limits table. App receipts have one budget; all graph members share their root's budget. Creation replays with another budget conflict. Resume never changes the budget, review, consent or expiry. Legacy snapshots with omitted budgets resolve to two.
- **Atomicity:** Admission counts distinct underlying task and queue invocation identities, including borrowed resources, before creating another resource in the same transaction. Single-app receipt locks serialize app admissions; exclusive graph root locks precede catalog/member locks and serialize graph admission with cancellation/completion. Existing step replays return the committed identity even at capacity. Unknown live states count conservatively; missing or terminal resources no longer occupy slots. Expired diagnostic evidence and cancellation requests do not prove that underlying work stopped.
- **Backpressure:** A full budget returns HTTP 429 with `binding_verification_budget_full`, `limit` and `observed`. Go, Node and synchronous/asynchronous Python runners wait and reread the original receipt before retrying. Other errors retain existing recovery behavior. Waiting remains bounded by the original receipt deadline and local stop controls; no cancellation, new receipt or deadline renewal occurs implicitly.
- **Public diagnostics:** App and graph diagnostics expose the shared root ID, frozen limit, unfinished resource count, unadmitted step count and fullness. Observations grant no admission authority, include no commands, pins, credentials or resource output, and remain behind existing read gates.
- **Compatibility:** Optional create/receipt fields preserve old client and snapshot decoding. The CLI sends its creation-time concurrency selection; a lower local resume budget can further restrict observation/admission attempts. New server enforcement remains authoritative even when an older runner stops on backpressure. The receipt budget does not reserve scheduler, queue or account capacity and does not cap work across independent receipts.
- **Validation:** Memory and real PostgreSQL races across distinct steps/members; replay at capacity; borrowed identity deduplication; terminal slot release; cancellation and deadline invariance; immutable creation budgets; HTTP problem/diagnostic contracts; shared Go/Node/Python backpressure and unrelated-capacity recovery vectors; OpenAPI/SDK generation and lint.
