# ADR-169 · Container guest service proxy identity

- **Status:** accepted
- **Date:** 2026-09-09
- **Decision:** Expose the ADR-168 service proxy on each compute node's tenant-bridge address at reserved TCP port 10080. Guests call `/v1/internal/services/<slug>[/<path>]`; gatewayd resolves the caller from the source `HostIP` mapped to a live instance on the local compute node, and an optional caller header is accepted only as a matching assertion. The per-netns nftables forward chain admits only `HostBridgeIP:10080` before the lateral-movement deny.
- **Why:** The loopback-only proxy was usable by in-box components but not by workloads. The existing per-instance MASQUERADE gives the host a stable source identity, so the service path can be enabled without trusting a guest-supplied app ID or adding a second transport.
- **Security boundary:** The listener must bind a private host-bridge address and the reserved port; wildcard, loopback, and other ports are rejected at boot. Unknown, stale, foreign-node, or ambiguous source IPs fail closed. The authorizer still enforces same-account access, and the caller header is stripped before the vmmd guest hop.
- **Consequences:** Cross-VM stateless HTTP calls are available from guests on the same account through a stable node-local address. The endpoint registry, identity map, and service proxy remain local to the compute node and refresh within bounded five-second leases. A DNS name resolver and public multi-port ingress remain follow-up work.
- **Rejected alternatives:** Binding the listener to `0.0.0.0` would widen the unauthenticated surface beyond the tenant bridge. Trusting a guest-provided caller header would allow cross-tenant spoofing. A DNS-only feature would still need a transport listener and would not solve caller identity.
