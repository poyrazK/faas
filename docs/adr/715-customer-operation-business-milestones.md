# ADR-715: Transaction-backed Customer Operation milestones

- **Status:** accepted for internal implementation; production admission stays disabled
- **Date:** 2026-10-07
- **Decision:** HTTP transaction definitions may declare named public milestone payload schemas. The Node SDK validates a batch against the pinned definition before committing business writes, result receipt, and milestone outbox together in the application's PostgreSQL database. After commit it publishes pending facts under the current workload identity and execution proof, acknowledging each outbox row only after the platform responds.
- **Why:** A progress stage records execution activity. Customers also need durable business facts, such as an order being fulfilled, which remain discoverable across lost responses and authorized execution recovery.
- **Consequences:** A publication failure leaves business writes committed and the outbox pending. The SDK throws `OperationMilestonePublicationError` with `committed = true`; replay of the same Operation returns its receipt and publishes pending facts without rerunning the callback. Stable IDs and occurrence timestamps are saved before commit. Platform publication deduplicates `(operation_id, milestone_id)` across generations and rejects reuse with different contents. A lost publication acknowledgement is safe to retry. Reporting always checks current claim authority before deduplication.

Declarations require `http_transaction_version: 1`. Their bounded schemas are source-local files in YAML/TOML manifests and resolved immutable JSON Schemas in API definitions. They participate in the definition revision. Omitting milestones preserves existing revisions and receipt behavior. Only definitions with declarations negotiate `X-Gregale-Customer-Operation-Milestone-Version: 1`. The additive outbox table requires explicit application schema installation; declarations cannot silently bypass the outbox on an older installation.

Limits are centralized in `pkg/api/limits.go`: 16 declarations, 16 KiB aggregate canonical schemas, 8 KiB per payload, 64 milestones per Operation, and a 64 KiB validation batch. Validation is read-only and does not reserve quota or renew claim authority. Milestones do not change business outcome, recovery rules, idempotency keys, execution leases, or managed Operation receipts. Publication is an assertion by the authorized application, whose transaction boundary provides the business commit evidence; the platform cannot inspect arbitrary business tables. Other SDKs expose validation and publication for application-owned transaction/outbox integrations.

A dedicated platform ledger retains facts for the Operation result lifetime, independent of the shorter generic event history. Deletion of the parent Operation cascades to facts. A small `milestone` event contains the name, ID, occurrence time, and sequence, while the ledger owns the public payload. PostgreSQL uses `json` for bounded payloads and feed projection so valid escaped NUL strings and exponent-form numbers do not suffer JSONB conversion failures or size expansion. The Operation's persisted milestone count prevents recovery from resetting its quota. The ledger is operational state and is excluded from environment cloning.

Read APIs provide a single Operation feed or an exact business-reference feed within an explicit app and environment. Tenant routes derive ownership from credentials and omit account-operator tenant metadata. Account routes use existing account/app/MFA boundaries with an optional customer filter. Descending keyset cursors use first publication time, Operation ID, and milestone ID; fingerprints bind purpose, owner, app, environment, and selectors. Occurrence time describes application timing, not cross-Operation causality. Immutable business references come from the admitted Operation rather than report bodies.

The Go/Node/Python SDKs, CLI, and dashboard expose these feeds. Dashboard payloads use normal HTML escaping and only come from declared, validated public facts. Applications must choose customer-visible fields and authorize the underlying entity before receipt replay, as required by ADR-713 and ADR-714.

Portable acceptance kills the actual order example after business commit and before first publication. Authorized recovery publishes the saved fact once, returns the original result, and leaves one business write. Additional memory/PostgreSQL and Node tests cover changed-ID replay conflicts, schema rollback, lost publication acknowledgements, stale claims, bounded JSON encoding, immutable snapshots, quota enforcement, and customer/filter isolation. Native preview qualification remains a separate rollout gate.
