# ADR-1367: Binding CLI progress and recovery summaries

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Durable SDK runners expose resource progress, qualification waits, read retries and write reconciliation. The CLI did not connect those callbacks and discarded ephemeral qualification conditions from stop reports, leaving users with silent waits and incomplete recovery context.
- **Decision:** Add `--progress auto|plain|ndjson|off` to durable app/graph verify and receipt resume. Explicit progress flags require execution, excluding dry-run and nonexecution actions. Auto emits compact plain updates on stderr for human output and disables live updates under `--json`. Plain suppresses unadmitted planned-step noise. NDJSON emits typed `binding_verification_progress` records on stderr, carrying existing sanitized runner metadata and graph selectors. JSON stdout remains exactly one final report.
- **Deduplication:** Track the last emitted event per member/step. Qualification observation timestamps alone do not cause another update; changed conditions, resource state, retry attempts or reconciliation phases do. Human waits show at most three conditions. NDJSON and final JSON retain all bounded typed conditions.
- **Recovery:** Stopped app reports and graph result envelopes add optional `recovery` with the original root UUID, last observed phase/operation, detached `last_qualification` and exact status/diagnostics commands. The qualification timestamp explicitly identifies a historical observation, not current authorization. Plain final summaries show that context; NDJSON human-output runs use `binding_verification_notice` records for stops. Progress off still records recovery context. Creation continues announcing its recovery identity before the write even when live progress is off; NDJSON uses a `creating` record.
- **Streams and failures:** During execution, NDJSON cleanup failures use a sanitized `cleanup_failed` notice rather than raw transport payloads. Argument, authentication and other failures before execution retain existing CLI error handling. For CI use `--json --progress ndjson`, separating events from the final report. Progress writes are best effort: sink failures never cancel work or change admission, qualification, deadlines, exit codes or existing cleanup behavior. Recovery commands recommend inspection rather than assuming cancellation or immediate resumption is appropriate.
- **Validation:** App/graph progress through waiting, retry and reconciliation; stopped runs whose subsequent status omits qualification; strict single-result JSON stdout and parseable NDJSON stderr; condition deduplication and terminal escaping; disabled output and human defaults; timeout cleanup, secret omission and failing output writers; execution-only flag validation, CLI compatibility and generated help/reference parity.
