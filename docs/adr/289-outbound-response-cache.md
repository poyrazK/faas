# ADR-289: Opt-in outbound HTTP response cache

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** Allow an integration owner to opt into a short response freshness window (0–300 seconds, default disabled). Cache only bodyless `GET` responses with status 200. A configured TTL is an upper bound; provider `Cache-Control`, `Expires`, and `Age` metadata can shorten it. Never store responses marked `private`, `no-store`, or `no-cache`, responses with `Set-Cookie`, or `Vary: *`. Range and conditional requests, and requests asking for no-cache/no-store behavior, bypass the cache.
- **Isolation and storage:** Keep entries in a process-local LRU bounded to 1,024 entries, 32 MiB total, and 1 MiB per response. Limit concurrent fill buffers to eight so a burst of oversized responses cannot multiply transient memory without bound. Keys are HMACs of integration ID, verified app ID, policy revision, URL, and all forwarded request headers. This partitions by app and provider credential without retaining credentials in cache keys. Customer-sealed credentials are still resolved after admission and before lookup, so revocation and rotation continue to fail closed. Restarts and other outboundd replicas begin with an empty cache; no response data is persisted.
- **Admission and telemetry:** Every caller request still passes identity, route, rate, concurrency, and daily-budget admission. A hit avoids the provider call and upstream-attempt metrics, but remains one admitted logical request. Cache hit/miss telemetry uses the existing bounded integration label.
- **Why:** Repeat reads can reduce provider latency and provider-side cost without introducing app wrappers, while explicit opt-in, very short freshness, conservative response rules, and strict memory bounds limit stale-data and data-isolation risks.
- **Consequences:** Caching is local and best-effort; it does not promise fleet-wide hit rates. Integrations whose providers return private/no-store/no-cache responses remain uncached. A distributed cache and broader HTTP cache semantics are intentionally out of scope.
- **Rejected alternatives:** Caching all methods or bodies could replay side effects. Sharing entries across apps or credentials could leak tenant data. Persisting provider response bodies would expand the credential/data-at-rest surface. Treating configured TTL as permission to override provider prohibitions would serve explicitly uncacheable data.
