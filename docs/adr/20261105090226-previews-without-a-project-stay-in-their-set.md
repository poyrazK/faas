# ADR-20261105090226: Previews of apps without a project stay inside their pull request

- **Status:** accepted
- **Date:** 2026-11-03
- **Amends:** ADR-219 (preview-scoped internal service resolution), ADR-20261101160300 (apps bound without a project are previewed as one set), ADR-20261028090000 (the `pr-preview` scope)
- **Context:** A review of PR previews on 2026-11-03 found four gaps:
  1. When several apps are bound to a repository without a project, a pull request previews all of them as one set. But a preview resolved service names globally. Calling `api` reached production `api`, not the PR's `pr-<N>-api`. The project `preview_service_policy`, which defaults to deny, did not apply because these previews have no project. The target's `x-gregale-preview-calls` defaults to allow, and apps outside a project default to reaching every app in the account. So a branch's unreviewed code could call any app of the account as the production app, with real side effects.
  2. Buckets and managed PostgreSQL bindings could be created on a PR preview. Teardown cleaned them only for `gregale dev` sessions, so they outlived the preview and stayed billed. A database binding also handed the database's credentials to unreviewed code. When a pull request dropped such a service, the set swap refused with "a preview app name is already used", which was wrong.
  3. Removing a value or secret from the production app's `pr-preview` scope never reached open previews. A leaked test credential stayed in every open preview until each one was destroyed.
  4. Agent marker comments were adopted from any bot. A pull request's workflow comments as `github-actions[bot]` and could post the marker first.
- **Decision:**
  1. A PR preview of an app bound without a project calls only the previews of its own PR preview set (`pr_preview_sets`). It names them by their production slugs, as production does, and the resolver routes the name to that set member. A name the set does not preview resolves to the production app, and the authorizer refuses the call with `preview_production_dependency_denied`, the project default. A preview of another pull request, or a stale or torn-down member, is refused. The gateway's pinned policy view reads the set (`PRPreviewSetPeerIDs`) in the same snapshot. Production callers, project previews and `gregale dev` sessions are unchanged.
  2. `POST /v1/apps/{preview}/buckets` and a managed PostgreSQL binding for a PR preview answer `409 pr_preview_resource_unsupported`. Previews get test credentials through the production app's `pr-preview` scope. The janitor and `gregale preview destroy` delete a PR preview's buckets, as they do a dev session's, and remove its PostgreSQL bindings, never the database. A set swap that would retire a preview still owning a bucket reports that, not a name conflict.
  3. Deleting a key from the production app's `pr-preview` scope deletes it from each open PR preview that still holds the copy a sync gave it, compared by value or sealed bytes, and invalidates that preview's snapshots. A value changed on the preview itself is kept. A secret is removed with the same revocation as a direct delete. The production delete has already committed, so a failure on one preview is logged and audited (`preview_config.remove_failed`) rather than undoing it.
  4. Agent marker comments are adopted only when GitHub attributes them to this App, as preview status comments already are.
- **Consequences:** A frontend preview of an app without a project that called production services now gets 403 for those calls. Its set's other apps are reached instead, and a service the PR does not preview needs a test endpoint in the `pr-preview` scope. A database or bucket can no longer be attached to a PR preview. Existing ones are cleaned up when the preview is torn down: buckets are deleted, and databases keep their data and lose the preview's binding.
- **Rejected alternatives:**
  - *An account-level switch to let these previews reach production.* Projects already offer `allow_marked`. Apps without a project had no review gate for it, and the safe default comes first. A project is the way to opt in.
  - *Resolving the sibling by its generated slug `pr-<N>-<name>`.* PR numbers repeat across repositories in one account, so the slug alone could pick another repository's preview. The set is the authority.
  - *Keeping buckets on teardown.* The app they belong to is deleted, so nothing could reach or delete them afterwards.
