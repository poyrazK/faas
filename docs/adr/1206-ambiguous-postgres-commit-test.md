# ADR-1206 · Acknowledgement loss after a successful Postgres COMMIT

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Extend the Postgres write example's portable acceptance gate with a bounded plaintext-loopback wire proxy. Forward one original COMMIT, observe its successful CommandComplete and idle ReadyForQuery, suppress both acknowledgements and close the connection. Require an independent SQL witness of the confirmed row before explicit same-key reconciliation. Treat transport/timeout errors after COMMIT submission, connection-class SQLSTATEs and statement-completion-unknown as unknown outcomes; discard the connection and do not retry or infer rollback.
- **Why:** A rejected COMMIT tests rollback; it does not test a successfully committed operation whose client cannot determine its result.
- **Consequences:** Payment exposes a redacted 503 unknown-outcome receipt. Caller and provider do not automatically repeat this write after the failure. Reconciliation and conflicts must preserve one confirmed operation. Recovery reports check pending/active/queued work, pool waiters, idle transactions and joined socket cleanup. SQLSTATE-reported transaction rejection passes through the armed proxy without counting acknowledgement loss. Frame parsing handles fragmentation with a 1 MiB frame bound, socket deadlines and backpressure; it logs no SQL/auth bytes. This is portable real-Postgres evidence against an owned disposable container; the native thirteen-case restart verdict and verified TLS behavior remain separate.
- **Rejected alternatives:** Dropping the connection immediately after sending COMMIT cannot prove the transaction committed. Throwing after a successful client-side COMMIT still lets the client observe its acknowledgement and does not test wire ambiguity. Treating a failed rollback attempt as proof that a COMMIT did not happen loses correctness. Decrypting deployed database traffic or weakening TLS would add an unrelated transport/security contract.
