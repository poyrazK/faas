# ADR-316 · GitHub branch freshness before promotion

- **Status:** accepted
- **Date:** 2026-09-27
- **Related:** ADR-092 (headless source-ref deploy), ADR-311 (GitHub push freshness and promotion fence), ADR-313 (GitHub push head recheck), ADR-315 (Actions-owned mapped environment deployments)
- **Decision:** When a source-ref request or GitHub App push names a branch, apid records the branch and installation identity alongside the resolved commit SHA. Imaged asks githubd for that branch's current head immediately before promoting the deployment. A deleted or advanced branch fails with `source_ref_stale`; a lookup failure or missing verifier fails closed with `source_ref_unavailable`. Tags and commit SHAs remain pinned to their resolved commit and do not receive mutable-branch metadata.
- **Why:** Source-ref imports and webhook pushes previously retained only the resolved commit, losing the branch intent after fetching. A slow build could become live after its branch moved, even if the newer push delivery had not yet been accepted. The ingress-time webhook head checks and accepted-revision fence do not cover that build window.
- **Consequences:** Deployment rows preserve branch and installation identity, and retries carry those immutable inputs forward. githubd validates the account/install pairing before resolving the branch. Webhook source URLs retain the codeload repository and commit provenance so imaged can verify they match the stored commit before resolving the branch. Split-box imaged reaches githubd through the private `githubd.faas:50053` mTLS listener; the manifest, firewall, and per-box PKI setup provision that route. The recheck runs after build/readiness validation and immediately before the live-pointer transaction, so stale code is not intentionally promoted and the previous live revision remains available. The remote branch read and database promotion cannot be atomic; an upstream push in the small interval between them may still race the cutover.
- **Rejected alternatives:** Checking only when apid accepts the request leaves the full build window unprotected. Treating every non-SHA ref as a branch incorrectly changes tag behavior. Using only the latest deployment revision misses upstream branch movement when no second deployment has been queued.
