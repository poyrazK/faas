# ADR-316 · GitHub branch freshness before promotion

- **Status:** accepted
- **Date:** 2026-09-27
- **Related:** ADR-092 (headless source-ref deploy), ADR-311 (GitHub push freshness and promotion fence), ADR-313 (GitHub push head recheck), ADR-315 (Actions-owned mapped environment deployments)
- **Decision:** When a source-ref request, GitHub App push, or GitHub Actions branch-push workflow identifies a branch, apid records the branch and installation identity alongside the resolved commit SHA. A custom CI workflow may send an immutable SHA with `source_branch`; apid confirms that the branch still names that SHA before accepting the deployment, then records the same provenance. Imaged asks githubd for the branch's current head immediately before promotion. A deleted or advanced branch fails with `source_ref_stale`; a lookup failure or missing verifier fails closed with `source_ref_unavailable`. Tags and explicitly pinned commits without branch metadata stay pinned to their resolved commit.
- **Why:** Source-ref imports, webhook pushes, and Actions branch builds previously lost branch intent after resolving the commit. A slow build could become live after its branch moved, even if the newer push delivery had not yet been accepted. The ingress-time webhook head checks and accepted-revision fence do not cover that build window, and an immutable Actions event SHA alone does not establish that it is still the current branch head.
- **Consequences:** Deployment rows preserve branch and installation identity, and retries carry those immutable inputs forward. githubd validates the account/install pairing before resolving the branch. Webhook and Actions source URLs retain codeload repository and commit provenance so imaged can verify they match the stored commit before resolving the branch. The first-party Action attaches the branch for push events; custom CI can use `--source-branch` with a full 40-character commit SHA and omit it for intentional pinned rollbacks or tag deployments. Split-box imaged reaches githubd through the private `githubd.faas:50053` mTLS listener; the manifest, firewall, and per-box PKI setup provision that route. The recheck runs after build/readiness validation and immediately before the live-pointer transaction, so stale code is not intentionally promoted and the previous live revision remains available. The remote branch read and database promotion cannot be atomic; an upstream push in the small interval between them may still race the cutover.
- **Rejected alternatives:** Checking only when apid accepts the request leaves the full build window unprotected. Treating every non-SHA ref as a branch incorrectly changes tag behavior. Using only the latest deployment revision misses upstream branch movement when no second deployment has been queued.
