# ADR-258: Customer-configurable outbound request policy

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Let account owners choose a complete rate, burst, maximum in-flight, and upstream request-timeout policy when creating a customer-owned outbound integration and replace it later through an MFA-gated deploy-write API. Omitted create-time policy retains the existing 10 RPS, burst 20, 10 in-flight, and 30-second defaults. Store settings in the existing integration columns; no migration is needed.
- **Plan ceilings:** Free: 10 RPS / burst 20 / 10 in-flight / 30 s; Hobby: 20 / 100 / 50 / 60 s; Pro: 100 / 500 / 250 / 120 s; Scale: 500 / 2,000 / 1,000 / 300 s. These are configurable per-integration ceilings, not included usage allowances. Daily request budgets remain a separate control.
- **Enforcement:** `outboundd` resolves customer policies from Postgres and the admission transaction re-reads the current policy while locking the account and integration rows. A completed update therefore applies to subsequent admissions across all replicas without restart, including requests whose earlier resolver snapshot was stale. Rate tokens are clamped to a newly reduced burst. Lowering concurrency does not terminate existing requests; new admissions wait until active leases fall below the new maximum. Already-admitted requests keep the deadline chosen at admission.
- **Plan changes:** Runtime admission and API read projections clamp a saved customer policy to the account's current plan. A downgrade therefore takes effect on the next admission and read; an upgrade does not automatically raise values the customer previously selected. Operator-provisioned integrations remain operator-managed and are not customer-updatable through this route.
- **Consequences:** Each integration can express provider-specific protection (for example, a short Stripe timeout and a lower GitHub request rate) without application wrappers. The policy is shared by all apps bound to the integration and across outboundd replicas. The request count remains generic HTTP admission telemetry; this decision does not estimate provider spend, retry calls, or cache responses.
- **Rejected alternatives:** Requiring delete-and-recreate for every policy adjustment makes credentials and app bindings unnecessarily fragile. Applying edits only at daemon startup would make account policy stale and replica-dependent. Automatically terminating active requests when a limit falls would make a configuration edit an unsafe cancellation operation.
