# ADR-1363: Bounded verification status read retries

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** A temporary polling GET failure stops a runner even when receipt work is still progressing. Repeated manual resumes make CI needlessly fragile.
- **Decision:** Go, Node and synchronous/asynchronous Python runners retry transient receipt status GET failures. Default three additional attempts per read, configurable from zero through eight. Use exponential equal-jitter delay from 250 milliseconds, capped at two seconds, always bounded by the original confirmed expiry and caller stop controls. Successful reads reset the per-read retry budget.
- **Classification:** Retry connection/stream failures and transport timeouts where identifiable, plus HTTP 502, 503 and 504. Do not retry authorization, not-found, conflict, quota, other HTTP errors, malformed successful responses or selection/authority validation failures. Resume, create, admission, completion, cancellation and diagnostic reads keep their existing recovery behavior. Existing explicit admission-budget backpressure remains separate.
- **Progress:** Existing progress callbacks receive root `retrying` events with `retry_attempt` and `retry_delay_ms`, followed by current receipt progress when observation recovers. Events expose no raw transport error text. Callback failures stop observation and skip automatic diagnostics. Cancellation interrupts backoff immediately; neither retry nor observation creates another receipt, renews its expiry, replaces work or activates routes.
- **Recovery:** Exhaustion returns the existing typed recovery error with the original receipt ID, latest failed read cause and best-effort diagnostics under their existing bounds. A successful retry is still validated against the original frozen review, membership, deadline and resource identities before any subsequent admission or qualification.
- **CLI:** Durable verify and resume accept `--status-read-retries` (default three, zero disables). Other actions reject this execution option. No server endpoint or database changes; limits live in the API limits table, and the Go SDK source synchronization gate includes retry helpers and tests.
- **Validation:** App/graph recovery without duplicate admission, exhaustion/disable, permanent failures, changed selection after reconnect, callback failure, caller cancellation and deadlines; backoff bounds; SDK suites, CLI regression, race checks, source synchronization and lint.
