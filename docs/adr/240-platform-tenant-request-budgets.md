# ADR-240: Cross-app platform tenant request budgets

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Let an account owner set optional per-minute and per-UTC-day admitted-request ceilings for one platform tenant. A single atomic counter row coordinates every linked consumer-key and verified tenant-surface request across apps and gateway replicas. Zero disables a dimension; the default is unlimited.
- **Why:** ADR-226/239 supply an authoritative request-time customer ID and ADR-238 supplies a later billing snapshot, but a platform cannot prevent one customer from consuming its shared capacity across apps. App/account rate limits cannot express a customer-wide ceiling.
- **Consequences:** Admission runs after the existing account/app gates and before body buffering or wake. One allowed request consumes one unit, regardless of its eventual guest outcome. A denied request consumes none, returns `429` with `Retry-After`, and cannot enter the financial usage ledger through either the outbox or debugger fallback. A database error returns `503` and also cannot become billable. Because an unavailable store cannot prove that a customer has no configured policy, tenant-attributed traffic fails closed even when its last known policy was unlimited. Other traffic is unchanged. The control-plane GET/PUT API exposes ceilings, current counters, and UTC reset times under the existing MFA-gated platform-tenant scopes. It never guesses tenant identity from request headers.
- **Rejected alternatives:** Derive a hard budget from asynchronous billed usage (late events permit overshoot); reuse the existing central token bucket unchanged (its process-local fallback violates a hard shared ceiling); keep one row per minute (unbounded retention); apply the budget per app (a customer can rotate apps); use a monetary ceiling without synchronous price reservation (misrepresents what is guaranteed).

The policy and minute/day counters share one bounded Postgres row per tenant. Admission locks that row, reads database time after the lock, checks both ceilings, and increments both counters in one transaction. Policy updates serialize on the same row and preserve counters; setting both ceilings to zero stops counting without erasing earlier usage. With no policy row the request is admitted. The configured numeric safety maxima live in `pkg/api/limits.go` and are not subscription-plan allowances. The admission counters and durable financial ledger intentionally differ: the former counts admitted attempts, the latter records completed billable traffic.

Deploy the new gateway fleet before allowing operators to configure budgets; an older gateway cannot enforce this new policy during a rolling upgrade. The feature does not add money caps, JWT-claim attribution on unrelated domains, or a payment system. A follow-up may add a bounded policy cache only if it retains fail-closed update semantics.
