# ADR-278: Method and path scopes for service callers

- **Status:** accepted
- **Date:** 2026-09-26
- **Decision:** Add an optional target-owned `allowed_service_call_scopes` map keyed by logical caller app. Each grant names HTTP methods and decoded URL path prefixes. Prefixes match only the exact path or slash-delimited descendants. If the map is present, callers absent from it are denied. The existing `allowed_service_callers` list remains supported and intersects with this map when both are configured. The gateway enforces a caller's method/path grant after app identity and target authorization but before endpoint lookup, wake, or forwarding. Ambiguous paths fail closed. The reserved platform binding-verification HEAD probe remains a control-plane probe and does not need a customer route grant.
- **Why:** App-level binding authorization currently grants an allowed app access to every HTTP route and method on the target. Service owners need a least-privilege boundary for callers without exposing a public endpoint or requiring every handler to reimplement caller identity checks.
- **Consequences:** Standalone app APIs support create, read, replace, and clear semantics; Compose can declare the same policy with `x-gregale-allow-call-scopes`. Project-managed policies remain source-owned. Scope denials return 403, increment a bounded `scope_denied` service-call metric, and cannot wake a target. Existing apps without this field retain their current behavior.
- **Rejected alternatives:** Replacing `allowed_service_callers` with a structured object would break the existing list contract. Caller-owned outbound rules alone are insufficient because the target must own the resource boundary. Arbitrary regular expressions and route-template syntax are deferred; literal prefixes keep matching deterministic and auditable.
