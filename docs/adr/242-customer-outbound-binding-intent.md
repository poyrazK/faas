# ADR-242: Customer binding intent for managed outbound integrations

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Accounts may list their operator-provisioned managed outbound integrations and attach or detach one to an app through authenticated `apid` routes. `apid` alone writes `outbound_app_bindings`, a customer-intent table. `outboundd` remains the sole writer of integration policy and operator attachments; its resolver reads the union of operator attachments and customer bindings on each request.
- **Why:** The first managed-credential slices required an operator to edit `app_ids` for every app. A separate intent row makes `bind` self-service without giving the customer or app the provider key, and without letting `apid` mutate the runtime integration policy owned by `outboundd`.
- **Security:** The database trigger requires the account, app, and managed integration to share ownership. The API repeats this check, only offers enabled managed integrations, scopes every query to the authenticated account, and returns metadata without gateway tokens or provider credentials. The outbound resolver checks current account ownership for every attachment and excludes soft-deleted apps. Operator reconciliation rejects an account change for an existing integration ID. Customer binding rows never grant access to legacy application-auth integrations, even if an operator later changes an integration's auth mode.
- **Operational behavior:** A managed integration may start with zero operator-attached apps. A successful bind becomes effective on the next gateway resolution without an `outboundd` restart; deleting it revokes this customer attachment immediately. Operator-owned `app_ids` remain separate and are not removed by a customer unbind. Existing managed integrations still require a configured provider authorization value, JWKS, and explicit method/path policy.
- **Limits:** This slice attaches to existing account-owned integrations only. Customers cannot create an integration, upload or rotate a provider key, change origin/policy, or derive an arbitrary outbound gateway endpoint through this API. Sealed customer-provided credentials and full integration lifecycle need a subsequent owner/reconciliation design. It does not make direct egress transparent or enforce cost budgets.

The app invokes the explicit `/i/{integration_id}/...` gateway path with a vmmd-signed workload identity token. The app receives the integration ID and route policy, but never receives the provider key.
