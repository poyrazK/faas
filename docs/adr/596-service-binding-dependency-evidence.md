# ADR-596 · Service binding dependency evidence

- **Status:** accepted
- **Date:** 2026-10-04
- **Context:** Service probe pins previously covered only caller configuration. A target authorization change could leave passed evidence usable, including at binding-gated promotion. Gateway resolution also depends on project PR siblings, production fallback and registered test-run membership.
- **Decision:** Include a private service dependency revision in service probe pins and inventory comparisons. Conservatively invalidate all service bindings in an account when an app's service resolution/authorization configuration, project preview service policy or scenario test membership changes. Include both old and new accounts on reassignment. Do not duplicate gateway resolution or expose target metadata. A dependency read failure makes inventory incomplete and prevents recording trusted probe evidence.
- **Promotion:** PostgreSQL increments the service revision and existing promotion revision together in the configuration transaction, using the same revision row held through traffic commit. MemStore hashes equivalent account app, project policy and test membership facts under its existing mutex and includes that digest in the promotion fence. Task completion, deployment traffic and runtime heartbeats do not invalidate the service dependency token.
- **Tradeoff:** Changes to unrelated apps in the same account can require service probes to be rerun. This is deliberate conservative invalidation; an exact dependency graph can replace it when the gateway and API share a resolver contract. Evidence remains a point-in-time infrastructure observation subject to its configured maximum age.
- **CLI:** `bindings verify --all` reports every inventory binding, including explicit unsupported and skipped reasons, coverage and incomplete reads. Supported probe success preserves existing exit behavior when known unsupported bindings are present; use `bindings check` to enforce coverage. Unknown binding types fail closed. `bindings check --wait --timeout` observes pending work with bounded read-only polling, pins the first selected deployment/scope and emits one final report. Terminal failures, missing evidence and unsupported requirements stop immediately. Waiting creates no probes, restarts or acknowledgements.
- **Validation:** Target policy changes invalidate evidence and leave traffic unchanged; PostgreSQL dependency mutation, rollback and lock-wait tests; account isolation and policy/membership changes; CLI partial coverage, deterministic omissions, read-only waiting, deployment drift, timeouts and cancellation.
