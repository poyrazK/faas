# ADR-240: Workload identity for managed outbound credentials

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Managed-credential outbound integrations accept only a short-lived vmmd-signed workload identity assertion with audience `gregale:outbound:<integration-id>`. `outboundd` derives the app ID from verified claims and checks its attachment; it ignores a caller-provided app ID and does not accept the legacy shared gateway token for these integrations. Application-owned integrations retain the ADR-156 token protocol.
- **Why:** ADR-239 put a provider key behind the gateway, but a shared gateway token plus caller-provided app ID cannot prove which attached app is invoking it. The existing guest metadata endpoint already mints an instance-bound assertion without distributing long-lived admission secrets.
- **Trust:** The daemon reads a locally provisioned public JWKS at startup. It accepts only RS256 signing keys with unique key IDs, signing use, and valid RSA-2048+ public material. It verifies signature, configured issuer, exact single audience, subject/app-ID agreement, required account/app/instance claims, issued/not-before/expiry times, and a maximum five-minute assertion lifetime. It never fetches a JWKS URL supplied by a caller or forwards the assertion to a provider. A missing or invalid JWKS prevents startup when a managed integration is configured; a replica without a verifier fails closed.
- **Deployment:** The operator must publish vmmd's signing public keys in `workload_identity_jwks_path` and configure the same issuer on both daemons. During rotation, overlap old and new keys until old assertions expire and restart `outboundd` replicas to load the new file. Drain old gateway binaries before enabling managed integrations because their earlier token-authenticated behavior is not compatible with this security boundary.
- **Limits:** The assertion is a bearer token and remains replayable until expiry; this does not check live instance status. The configured gateway token remains in the database schema for now, but is not given to managed-integration apps or accepted on their request path. This is still operator provisioning, not a customer binding API, external-API cost budget, cache, or safe retry policy. ADR-241 subsequently adds HTTP method/path guards; provider-side key scopes and response behavior still matter.

This supersedes ADR-239's application-held admission-token rule for managed integrations only. The fixed HTTPS origin, no-redirect/no-automatic-retry behavior, and all shared rate/concurrency admission rules remain unchanged.
