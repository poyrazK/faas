# ADR-1209 · Bandwidth limits for the PostgreSQL TLS test fixture

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Extend the opt-in loopback COMMIT/TLS fixture with explicit per-direction application-frame bandwidth controls. Accept integer 1024–16777216 bytes/second rates, shared across connections in that direction. Serialize and pace small chunks without an initial burst, retaining ordered frame bytes and receiver backpressure. Clearing a limit wakes queued writes at normal speed; connection closure and proxy shutdown cancel waiting transfers. Bound limits to 100 records, accepted connections to 16, individual frames to 1 MiB and pending limiter bytes to 8 MiB.
- **Why:** COMMIT delays model waiting for an acknowledgement; they do not exercise sustained transfer or deadline expiry while a large database response is only partly received.
- **Consequences:** Monotonic evidence records configured rate, application bytes accepted by destination writes, duration and cancellation; it includes live queues, buffered bytes and timers without SQL/authentication/row data. TLS negotiation is excluded, while startup/authentication traffic is shaped if controls are enabled before client connection. Real verified-TLS PostgreSQL reads test completion, removal during a partial transfer, database-client deadlines and proxy shutdown. Successful reads require complete payload equality; timed-out partial reads retire their connection, then use a fresh unlimited connection. Independent SQL verifies encrypted idle recovery sessions and removal of retired backend sessions. Portable tests prove request/response shaping, aggregate concurrency, byte order and cleanup. Existing native restart qualification remains unchanged; deployed routing, encrypted-wire rate measurements and COPY/replication need separate evidence.
- **Rejected alternatives:** Delaying one complete response does not model sustained bandwidth restrictions. Applying one independent budget per connection would exceed the configured proxy-wide limit under concurrency. Dropping residual bytes when removing a limit would corrupt protocol framing. Reusing a timed-out partial-response connection would misattribute later bytes to another query.
