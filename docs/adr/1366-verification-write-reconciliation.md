# ADR-1366: Verification write reconciliation

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** An admission or completion response can be lost after the server commits the operation. Previously, runners required a manual resume even when the original receipt could prove success.
- **Decision:** Go, Node and synchronous/asynchronous Python runners perform read-only reconciliation after eligible connection/stream failures, transport timeouts or HTTP 502/503/504 from admission or completion. They never automatically replay the uncertain write. The CLI inherits the shared runner behavior. Creation, initial resume and cancellation retain their explicit recovery contracts.
- **Proof:** Read the original app receipt or graph root, using the existing bounded status GET retry policy. Revalidate identity, frozen review, membership, selectors, original expiry, resource kinds, ownership and all previously observed resource IDs. Admission requires a valid owned resource for the exact reviewed member and step. Completion requires fresh passed root/member status, finished resources and no pending qualification observation. A missing commit, pending completion, failed resource, malformed response or drift stops recovery with the original receipt ID and write cause retained. Generic errors and permanent HTTP failures do not trigger reconciliation. Existing explicit admission-budget backpressure is unchanged.
- **Bounds:** Recovery shares the original receipt expiry and caller stop controls. Status retry settings bound additional reads, including zero retries. Callback failure and cancellation stop immediately. Progress exposes sanitized `reconciling` events with `operation` (`admission` or `completion`) and, for admissions, the selected app, member receipt and step. Read retries use the existing `retrying` events. No raw error payloads enter progress.
- **Compatibility:** No endpoint, server persistence, deadline renewal, replacement receipt, replacement admission or traffic mutation is introduced. A proven completion returns without repeating completion. An uncertain result that cannot be proved remains an explicit recovery error. Python retains local deadline/stop exceptions while keeping the original uncertain write reachable through the exception cause chain.
- **Validation:** App/graph admission and completion for committed and absent writes; 503 responses; changed review/deadline, malformed or unowned resources, incomplete graph members; bounded GET retries and exhaustion; callback failures, cancellation and expiry during recovery. All SDK suites, shared runner race tests, CLI compatibility, source synchronization and targeted lint.
