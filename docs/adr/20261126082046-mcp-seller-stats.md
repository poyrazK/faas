# ADR-20261126082046: Seller stats for sold MCP servers

- Status: Proposed (dark: API monetization routes)
- Date: 2026-11-26
- Related: ADR-20261124094745 (self-serve consumers), ADR-20261125194510
  (account tools), ADR-20261125230541 (upgrade prompt), ADR-20261123192254
  (MCP per-tool billing), ADR-950–953 (consumer pricing and statements),
  ADR-20261123110137 (MCP tool insights)

## Context

A seller can sell an MCP server end to end: strangers sign in, use a free
plan, get an upgrade prompt and pay. The seller cannot see whether it
works. The data exists (consumers, OAuth identities, sign-ups, plan
assignments, usage and route usage minutes, statements, rate cards) but
only per consumer; `mcp server insights` shows the last hour of tool
calls, not customers or money.

## Decision

Owner decisions (2026-11-26): funnel, revenue and units per tool, and
customers near their limits; revenue = billed plus a month-to-date
estimate; surfaces = API, CLI and a hosted MCP management tool; windows
are calendar months, up to 12.

1. **Endpoint.** `GET /v1/apps/{slug}/mcp-stats?months=N` (1–12, default 1:
   this month to date), read scope and MFA like the other consumer reads.
   Organization members need the app-security permission, like
   `monetization-funnel`: it names customers and revenue. It is part of the API
   monetization surface: hidden while `api_monetization_enabled` is off.
   Works for any app with consumers; MCP tools come from the
   `MCP /tools/<name>` billing labels.
2. **Per month (UTC calendar months):**
   - `signed_up`: consumers created, split by how they were created:
     `oauth` (an MCP sign-in created it: external ref `oauth:`), `signup`
     (the hosted sign-up page: a sign-up row or external ref `signup:`) or
     `owner` (created by the seller). An identity linked later does not
     change it;
   - `active`: consumers with billable units that month (anonymous traffic
     counts toward units, not customers);
   - `paying`: consumers whose month amounts to more than zero (statements;
     this month, the estimate);
   - `closed`: consumers revoked that month;
   - `requests`, `units`;
   - revenue per currency: `billed_millicents` (finalized statements whose
     period starts in the month, before credits) and
     `estimated_millicents`: for this month, priced exactly as statements
     are (the consumer usage quote, ADR-950–953); for a closed month, the
     latest draft of each period the month-end run has not finalized yet.
3. **Per tool, over the window:** units and distinct customers from route
   usage; this month's estimated revenue per tool from the quote's route
   breakdown. Closed months have no per-tool revenue: statements do not
   split by route.
4. **Near limit:** open consumers at 80% or more of their current plan's
   monthly units this month, most used first, at most
   `api.MCPSellerStatsNearLimitMax`.
5. **Cost bounds.** Four app-level aggregate queries (usage by consumer and
   month, route usage by route, finalized statements, plan assignments)
   plus one quote per open consumer, at most `api.MCPSellerStatsMaxQuotes`
   (those with the most units this month first),
   `api.MCPSellerStatsQuoteParallelism` at a time within
   `api.MCPSellerStatsQuoteBudget` (20 s, inside the CLI's 30 s request
   timeout). Customers left unpriced set `estimate_complete` to false.
6. **Surfaces.** `gregale mcp server stats --app <app> [--months N]` and the
   read-only `gregale_get_mcp_seller_stats` tool in the hosted management MCP
   server.
7. **Ownership.** apid only; new logic in `pkg/apid/mcpstats` (ADR-982).

## Compatibility

No schema or proto changes; new read-only queries over existing tables.
New API route and CLI command; older CLIs ignore it.

## Consequences

- Sellers and their agents can answer "how is my MCP server doing?".
- The estimate costs one quote per open consumer; large apps get a partial
  estimate, flagged.
- Per-tool revenue is month-to-date only until statements record a route
  split.
