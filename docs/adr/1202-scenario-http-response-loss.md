# ADR-1202 · Scenario HTTP response loss after dependency execution

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Add `http_response_lost` to the existing isolated HTTP service proxy. Forward the authorized request through the existing route, wake, and retry path. Drain and discard a successful response body, then return its 2xx status with a deliberately short entity (`Content-Length: 1`, zero bytes).
- **Why:** Pre-forward synthetic faults cannot test an operation that committed before its acknowledgement became unusable.
- **Consequences:** A response-writer adapter discards successful bodies without buffering them. Non-2xx, 204, 205, and empty responses pass through with headers, bodies and trailers intact and do not count as injections. HEAD and upgrades bypass this fault. Request cancellation remains with the existing transport; canceled requests do not count as successful fault injections. Fault selection is latched for the authorized request, so already-selected requests can complete after fault clear; clear and lease expiry stop new selections. Metrics and generation-scoped match evidence are recorded only when a nonempty successful response has actually been drained and the loss is emitted. The fault creates no new forwarding attempt and does not certify a database commit by itself. The example independently checks a durable, payload-bound provider ledger to prove one committed operation across retries and conflicting payloads. Updated API/gateway deployments are required; existing plan storage is JSON and needs no migration.
- **Rejected alternatives:** Replaying a write at the proxy to force a retry would change application semantics. Buffering entire dependency bodies would add unbounded memory demand. Hijacking connections would bypass HTTP/2 and existing response wrappers. Dropping before forwarding would not exercise an ambiguous committed outcome.
