# ADR-20261107220000: Kernel lockdown on every host; module lock opt-in

- **Status:** accepted
- **Date:** 2026-11-07
- **Amends:** ADR-143 (host hardening): host_hardening raises kernel
  lockdown and sets three more sysctls.
- **Related:** ADR-20261103163954 (app hosts point straight at the nodes),
  ADR-20261107203000 (host security evidence off the host), spec §11

## Context

Compute nodes now take app traffic from the internet with nothing in front.
Once an attacker has root on a host, the cheapest way to keep it, and to hide,
is the kernel: load a module (a rootkit), write kernel memory through
`/dev/mem`, or `kexec` into a kernel of their own. Nothing on our hosts stops
that today: on gregale-internal-test-1 (Ubuntu 24.04, 7.0.0-1011-gcp) on
2026-11-07 lockdown was `[none]`, Secure Boot off, `kexec_load_disabled` 0 and
`io_uring_disabled` 0.

No platform code needs any of those: nothing reads or writes `/dev/mem`,
MSRs, I/O ports or kernel debugfs; nothing kexecs; nothing uses io_uring
(Firecracker's block engine is Sync, and Go and PostgreSQL 16 do not use it).

## Decision

### 1. Lockdown `integrity`, raised by a unit early in boot

`faas-kernel-lockdown.service` (host_hardening) runs after
`systemd-modules-load` and before `sysinit.target` and writes
`faas_hardening_kernel_lockdown` (default `integrity`) to
`/sys/kernel/security/lockdown`. Under `integrity` the kernel refuses
unsigned modules, `/dev/mem` and `/dev/kmem`, kexec of an unsigned kernel,
MSR and I/O port writes, ACPI table overrides, module parameters that set
hardware addresses, and hibernation.

- **A unit, not a kernel argument.** The kernel lets root raise lockdown at
  run time but never lower it until reboot. A unit works the same on every
  image and bootloader; the grub role's arguments do not reach GCP's cloud
  images, whose `/etc/default/grub.d` overrides them (internal-test-1 boots
  without the grub role's `cgroup_no_v1=0`). Ansible starts the unit, so a
  converge protects the running host without a reboot.
- **What remains.** Someone with root can disable the unit and reboot. A
  reboot of a node is visible, and the unit file write raises
  `host_config_write_unattended` (ADR-20261107203000) when it is not done
  by systemd or a package tool. Secure Boot, which would make lockdown
  automatic, is not available on every provider we use.
- **Not `confidentiality`.** It also blocks reading kernel memory: kprobes,
  perf kernel sampling and BPF reads, which tracing and the runtime detection
  we plan next need.
- Ubuntu's modules are signed, so signed modules keep loading on demand.

### 2. Three more sysctls

- `kernel.kexec_load_disabled = 1` (one-way until reboot);
- `kernel.io_uring_disabled = 2`;
- `dev.tty.ldisc_autoload = 0` (already Ubuntu's value; now pinned).

### 3. Module lock, off by default

With `faas_hardening_modules_lock: true` the same unit loads
`faas_hardening_modules_preload` and then sets `kernel.modules_disabled=1`, so
no module loads until reboot, signed or not. A feature whose module is not in
the list fails with `EPERM`, often far from its cause (an nftables rule type
used for the first time, a new qdisc). The list is the set of modules the
`pkg/fcvm` metal suite loaded on internal-test-1, plus the overlay network's
tunnels and the reject/fib expressions; it has not seen every feature on
every provider. So it is opt-in, per host group, after `lsmod` from hosts that
ran every feature (runbook `kernel-lockdown.md`).

## Verification

2026-11-07 on gregale-internal-test-1 (Ubuntu 24.04, 7.0.0-1011-gcp,
main 09cdeee4da): the rendered unit raised lockdown from `none` to
`integrity` and was a no-op when run again. With lockdown and the three
sysctls in force, `scripts/ci/run-native-metal-smoke.sh` (Firecracker 1.7.0,
guest kernel 6.1.134) ran the `pkg/fcvm` metal suite and the namespace batch:
1827 passed, 101 skipped, 0 failed; leakcheck clean; no `Lockdown:` or taint
line in the kernel log; no module loaded that was not loaded before the run.
The runner's verdict was FAIL only because the native-owner-recovery phase
requires three tests that skip on that node for fixture reasons
(`pkg/fcvm/testdata/native-capture-peer` absent, `FAAS_NATIVE_CAPTURE_VM`
unset), not because of lockdown. The node was rebooted afterwards to return
it to `none`.

## Consequences

- A rootkit module, `/dev/mem` writes and a kexec into an attacker's kernel
  are refused on every host after its next converge.
- Debugging that needs those (a crash kernel via kexec, `/dev/mem` tools) is
  off; set `faas_hardening_kernel_lockdown: ""` on one host and reboot it.
- The module lock stays off until someone collects real module sets.
