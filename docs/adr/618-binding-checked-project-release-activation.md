# ADR-618: Binding-checked project release activation

- **Status:** accepted
- **Date:** 2026-10-06
- **Context:** ADR-598 intentionally blocks project graph changes under binding enforcement. Graph routing can select dark deployments independently of traffic weights. Single-app checks do not qualify a graph's service target revisions.
- **Decision:** Add read-only `POST /v1/projects/{slug}/environments/{environment}/release-sets/check`. Presence of `expected_active_release_id` on the existing publication request selects checked activation; empty means no active graph. Pin a complete immutable workload/deployment map, environment, TTL and expected active graph, and return its deterministic digest and per-deployment binding reports. The check is an observation, never an activation grant. Publication requalifies every member, including scopes whose stored policy is off, without starting verification tasks or user handlers. Existing unchecked publication remains available only when policy permits it.
- **Service edges:** A reserved service verification command may include a third argument naming an exact target deployment UUID. APID records this target in the private verification pin and its revision digest. Guest-init sends a marked HTTPS HEAD with the exact target selector. The gateway performs its usual caller, declaration and target authorization checks, validates the target deployment, and requires a healthy endpoint for that revision. It echoes the exact selector without waking the target or invoking an application handler. Missing exact confirmation fails verification. Ordinary and exact-target evidence cannot substitute for one another; smoke results remain diagnostics. Graph checks require every declared service target to belong to the selected graph.
- **Prepared settings:** Explicit deployment inventory and probe admission resolve immutable workload settings before reading declared service bindings. Editing the desired head cannot omit a pinned dependency or authorize a binding absent from that deployment.
- **Commit boundary:** APID holds all managed PostgreSQL memory-catalog fences together, or requires the shared PostgreSQL backend. Memory and PostgreSQL validate all member fences, policy revisions, materialized live artifacts and retention eligibility, then compare the expected active graph before any routing mutation. PostgreSQL inserts the candidate inactive, publishes its immutable members, authorizes an internal grant scoped to that candidate and predecessor, and swaps the pointer in one transaction. The graph trigger rechecks every member's evidence at each pointer write, after all lock waits. Unchecked promotion, rollback and deactivation paths retain their fail-closed guard.
- **Audit and retention:** Checked activation writes exact membership, graph digest, predecessor and private evidence fences to `project.release_set_checked` in the same transaction as publication. The regular audit stream reports the public qualification receipt. Previous release TTL and deployment retention behavior remain unchanged.
- **CLI:** `projects environments release-sets check|publish PROJECT ENVIRONMENT --file FILE --expected-active UUID|none` accepts exact deployment UUIDs. Check performs one read-only qualification request; publish performs one checked mutation and validates its receipt against the requested membership. `bindings verify APP SERVICE --deployment ID|vN --target-deployment UUID` explicitly creates exact route evidence. No graph check or publication automatically probes bindings.
- **Scope:** This slice covers manual release-set activation. Environment promotion/rollback workers need a separate integration with the same graph qualification contract. Native x86 Linux/KVM acceptance is still required to qualify the guest/gateway route on a deployed platform; portable tests do not establish that operator evidence.
- **Validation:** Memory/PostgreSQL all-or-nothing rejection, missing/wrong member fences, stale configuration/policy, expired evidence after another member's lock wait, exact graph CAS, retained predecessor compatibility, exact service route and no-wake/no-handler checks, API qualification and blocked publication, CLI receipt mismatch/old-server rejection, SDK contracts and generated-file drift.
