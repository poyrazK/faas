# ADR-1646: Binding qualification before managed graph activation

- **Status:** accepted
- **Date:** 2026-10-17
- **Problem:** Enforced binding release policies require checked evidence, but active-release probes cannot execute against held GitOps candidates. Ordinary project verification deliberately rejects managed deployments. A successful source build and isolated runtime smoke therefore cannot authorize an enforced graph replacement.
- **Decision:** Extend the existing graph qualification path with private, candidate-bound binding evidence. Apid snapshots the exact enforced policy revision, immutable reviewed source/image artifact and service-policy revision when it publishes qualification work. No public request can supply a receipt or nominate its own target. Existing applied migrations remain unchanged.
- **HTTPS evidence:** The private gateway observes a complete successful HTTPS exchange from a restored qualification caller to its exact restored dependency. It rechecks the observed node/IP identity, original execution frames, graph, binding, target policy, port and original deadline at completion. Capture-only calls, redirects, errors, failed writes, cancelled streams and ordinary serving routes produce no receipt. One immutable receipt per binding/attempt retains only identities and time bounds, never response bodies, credentials or cleanup capabilities. This attests an actual authorized TLS exchange; it does not assert that arbitrary application TLS clients verified their peer certificate.
- **Executable contract:** The reviewed HTTP health endpoint or worker smoke handler must exercise every declared HTTPS dependency before returning success. A declaration or a successful route lookup alone cannot qualify an edge. Services need no platform task or shell support for this path. A health endpoint that never calls a declared dependency leaves activation blocked.
- **Queues and consent:** Only reviewed push-worker queue smoke is supported. Every queue must have an explicit reviewed smoke payload and a `handler_completion` release requirement. The existing qualification owner sends that payload directly to the isolated candidate and checks the exact acknowledgement. This never publishes or claims a customer queue message. Approval of the reviewed smoke contract is the consent for this isolated execution; it does not authorize ordinary queue canary publication or prove production consumer readiness.
- **Activation:** Every project release member must be a candidate in the same complete prepared graph, with an enforced policy. Qualification, graph activation and serving convergence remain separate facts. The publisher rechecks artifact/context and all successful retired restore/smoke evidence under its existing source, project, app and deployment locks. PostgreSQL records an immutable release-to-qualification audit and validates exact release membership, current policy/source/artifact context and expiry again at commit. The serving owner must consume the same evidence before increasing candidate traffic. Once weights match, gateway/consumer acknowledgement can finish without granting a new traffic increase.
- **Freshness:** The earliest policy maximum age, qualification attempt lease and original HTTPS exchange deadline bounds authority. A changed policy, source generation, reviewed contract, build/archive/rootfs or dependency cohort invalidates it. Old active-release receipts and partial cohorts cannot substitute. Existing completed qualification work is immutable: after expiry or policy change, approve a fresh reviewed generation to collect new evidence rather than upgrading an old receipt.
- **Bounds:** Initial support covers complete HTTP/request/service and push-worker candidate cohorts. Retained/manual release members, jobs, pull queues, HTTP service edges, application-ack requirements, managed Postgres, object storage and outbound integrations stay blocked under enforcement. Ordinary active-release CLI verification and checked rollback/deactivation retain their existing contracts. Complete managed graph removal uses [checked retirement authority](1647-checked-binding-retirement.md); retirement completion still follows ADR-1331. No policy is disabled automatically.
- **Acceptance:** Portable memory/PostgreSQL lifecycle tests cover image/source candidates, missing HTTPS evidence, policy drift, expiry and held-state preservation; gateway tests cover successful versus failed/incomplete exchanges. These are control-plane fixtures, not native qualification. Real dedicated x86_64 Linux KVM execution and leak qualification remain required before release qualification.
