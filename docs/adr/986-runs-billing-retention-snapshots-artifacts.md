# ADR-986: Runs billing, receipt retention, runtime snapshot capture and derived artifacts

- **Status:** accepted
- **Date:** 2026-10-11
- **Relates to:** ADR-171 (disposable one-shot executions), ADR-382 (output artifacts), ADR-383 (dependency profiles)
- **Decision:** Settle the four items ADR-171 left open so Runs can be enabled with one switch:
  1. **Billing.** A Run is billed like every other compute workload (§4.7): admitted memory plus `api.PerVMOverheadMB`, for every started second between `running` and its terminal state, using host timestamps. The scheduler writes one `usage_minutes` row with `meter_kind = 'run'` and `execution_id` in the same transaction that records the terminal state. Caps, credits, provider delivery and invoices already sum `usage_minutes`, so Runs enter the same GB-hour allowance and overage with no second meter. A Run that never reached `running` (restore failure, queued cancel, expiry) is not charged.
  2. **Receipt retention.** A terminal Run keeps its receipt (result, stdout/stderr, inline artifacts, replay events) for `api.ExecutionReceiptRetention` (7 days). schedd then deletes the row in bounded batches, including on nodes where dispatch is off. The usage ledger no longer cascades from `executions`, so usage and billing survive. Receipts without a recorded usage row, and receipts of a still-active managed workflow, are kept.
  3. **Runtime snapshots.** A runtime snapshot catalog miss cold-boots the Run, as before, and queues a background capture of the same machine. The capture boots a dedicated payload-free execution VM (no tenant source, input, broker grant or Run ID), waits until the guest acknowledges the resume hook, parks it into fresh storage keys, and registers the pair in the catalog. Later Runs with that identity restore. Execution guests now bind the resume hook after their execution listener, so restores re-seed entropy and step the clock (§11 V6), and the acknowledgement doubles as the capture readiness barrier. A successful snapshot verification is cached per node, because catalog entries and their objects are immutable. Every Run VM uses a fixed `api.ExecutionVCPUCount` (2), so a snapshot does not carry one plan's vCPU count to another plan. The CPU limit stays a cgroup quota.
  4. **Derived artifacts.** schedd derives each Run's machine from what the release and imaged already publish: `kernel/<fc version>`, the runtime or profile base and its digest sidecar (image config digest, plus the guest-init digest, which is the executor identity), and a payload-free execution layer per profile (`execution/layer-v1-<profile>-<arch>.ext4`) that imaged now stages at startup. The eight `FAAS_EXECUTION_<RUNTIME>_*` variables remain as an explicit per-runtime override. One inventory switch, `faas_runs_enabled`, sets both the apid admission gate and every schedd dispatch gate.
- **Why:** Runs had their code built but could not be operated. Every Run would have cold-booted (nothing published runtime snapshots, and execution guests could not complete a restore). Usage was recorded but never billed. Receipts of up to 16 MiB stayed in Postgres forever. Enabling dispatch needed about forty hand-copied digest and key values, and no producer existed for the execution layer.
- **Consequences:**
  - A Run is now a billable workload. Its compute shows up in `GET /v1/usage` and `/v1/usage/daily` as one row per account with `kind: "run"`, keyed by the account ID. In financial evidence it is grouped under the workload name `runs`.
  - The first Run of a new identity (runtime, profile, memory, scratch shape, kernel, base, guest-init) cold-boots; later Runs on the node restore once the capture lands. A changed base generation or guest-init is a new identity and gets a new capture. The capture VM briefly uses one extra VM slot on the node.
  - Receipts older than seven days return 404. Re-running a local workflow manifest after its receipts expire starts those steps again.
  - Changing guest-init changes every base's guest-init digest, so existing runtime snapshots go stale as intended (ADR-005: snapshots are cache).
  - `ephemeral_disk_mb` still only selects the snapshot shape; Run scratch is the guest `/tmp` tmpfs, bounded by memory.
- **Rejected alternatives:**
  - A separate Runs meter or invoice line was rejected because it would need provider changes and a second allowance, contradicting the single GB-hour plan model.
  - Capturing the snapshot from the observing Run's own VM was rejected because it ties capture timing to tenant work and risks capturing after payload delivery.
  - A release-time capture job was rejected because it needs KVM on the release runner and per-node storage publication. Lazy capture on a miss works on every node.
  - Keeping the forty environment variables was rejected because they duplicate facts imaged already records and drift on every base re-stage.
