# ADR-598: Stored binding release policy per deployment scope

- **Status:** accepted
- **Date:** 2026-10-05
- **Context:** ADR-529 provides an opt-in bindings promotion route. Omitting the CLI flag, using ordinary traffic PATCH, or advancing a canary bypasses that route. Caller-pinned smoke tests from ADR-597 improve diagnostics but do not create verification evidence.
- **Decision:** Add an app/scope policy with `off` and `enforce` modes, a whole-second maximum verification age between 1 second and 24 hours (default 10 minutes), and an optional application-ACK requirement. Unconfigured scopes default to off, revision 0. GET/PUT require existing read/deploy-write permissions and completed MFA. PUT requires the current revision; every accepted update increments it. Promotion requests can strengthen, but cannot weaken, an enforced policy. Unsupported connectivity coverage cannot be waived under enforcement.
- **Traffic boundary:** Ordinary PATCH and manual/worker canary advance evaluate every deployment whose weight increases, including recipients of redistribution after a reduction. They pass internal observation fences to the state transaction. Dedicated promotion applies the stored policy too. The transaction compares ownership, scope, materialized live artifacts, binding/configuration revision, policy revision and evidence deadline after locking. Memory catalogs keep their own revision lock through the traffic write. The token-authenticated loopback worker stamps a private inventory-read context for its owner account; public requests retain normal per-catalog permissions. Neither checks nor promotion start probes or invoke user handlers.
- **Backstop:** An append-only migration installs a deployment trigger that serializes positive traffic admission and increases with policy changes. APID's transaction-local grants are set only after internally evaluated fences have been checked under the binding revision lock, and expire at the write boundary. Public bodies cannot supply grants; the setting is local to the transaction and resets on commit/rollback. PostgreSQL is a trusted control-plane boundary, not an authorization interface for customers. MemStore mirrors admission and traffic checks before mutation.
- **Other release paths:** Enforced scopes require explicitly zero-traffic candidate admission, including custom canaries whose first stage is 0%. Built-in canary presets start with positive traffic and are blocked at admission. Automatic cutovers, initial positive canary admission, legacy rollout recovery and automatic rollback do not yet carry binding fences and fail closed when they would increase protected traffic. Project release graph activation/deactivation can change routing without modifying weights, so a separate trigger rejects graph switches involving enforced scopes. Graph-wide qualification and activation need a subsequent integration. Already-serving traffic is not reevaluated or removed when policy is enabled; this is a release gate, not an outage detector.
- **Recovery and audit:** There is no implicit rollback waiver or request-level override. An operator with deploy-write permission can explicitly set the policy to off with its current revision and a single-line reason, perform recovery, then re-enable it. Policy changes and their reasons commit to durable history in the same transaction as the revision fence; the normal audit stream also records the change. Disable remains available without querying binding catalogs. A failed zero-traffic candidate may be marked failed if fallback routing would not increase protected traffic.
- **CLI and compatibility:** `bindings release-policy get|set APP --scope SCOPE` exposes the settings, revision and reason in human/JSON output. `--require-verification` aliases `--mode enforce`; `--expected-revision` is mandatory for set. Receipt validation accepts stricter effective promotion policies, while still rejecting weaker policies. Binding blockers render on all API error paths. OpenAPI and Go, Node and Python SDKs include policy management.
- **Validation:** Memory/PostgreSQL policy defaults, scope/account isolation, revision CAS, durable history, direct SQL backstop, partial traffic and redistribution recipients, request waiver rejection, concurrent enabling/policy changes, deadline expiry while waiting for locks, manual/worker canary advancement, reasoned disable/recovery, CLI receipt validation, migration up/down/up and existing promotion/traffic/canary regression suites. No VM resource lifecycle implementation is changed.
