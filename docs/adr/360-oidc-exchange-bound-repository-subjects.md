# ADR-360 · OIDC exchange admits every subject of an OAuth-bound repository

- **Status:** accepted
- **Date:** 2026-09-29
- **Context:** Secretless deploys (ADR-101) exchange a CI OIDC token for a short-lived deploy bearer. The account's trust policy is one row per (account, issuer). Since 2026-09-05 the first exchange from a GitHub repository bound to the account creates that row pinned to the exact subject that exchanged, e.g. `repo:acme/app:ref:refs/heads/main`. Every later exchange was verified against that one subject, so another branch, a `pull_request` run, or a second repository of the same account resolved to the account through its GitHub binding and then failed verification. Secretless deploys worked for exactly one repository + ref per account. Separately, policies auto-created before 2026-09-05 had an empty subject pattern and audience and admitted any token from the issuer; those are removed by migration `20260929081244731` and an empty pattern no longer binds a subject.
- **Decision:** When the stored policy's subject pattern does not match the token's subject, the exchange asks whether the subject's repository resolves, through the account's OAuth-proven GitHub binding (`apps.github_repo_full_name` joined to the account's `github_installations`, exactly one account, app not deleted), to the same account. If it does, the token is verified against a policy pinned to that exact subject, using the stored policy's audiences, JWKS URL, algorithms and required claims. The stored row is not rewritten. If the repository is not bound to the account, verification uses the stored policy and fails as before.
- **Security:** The repository binding is the same proof that authorizes the first-use policy: an installation the account's user connected via GitHub OAuth. The change widens trust from one ref of a bound repository to every workflow of it, which matches push-to-deploy through the GitHub App. GitHub does not issue OIDC tokens to fork `pull_request` workflows; `pull_request_target` runs the base repository's workflow code. Audiences stay pinned to the stored policy, and the exchanged bearer remains deploy-scoped and capped by the token's expiry.
- **Consequences:** Multiple repositories and branches of an account deploy without secrets. A policy explicitly narrowed by an operator still governs subjects its pattern matches; subjects of bound repositories outside it are admitted by the binding. Unbinding a repository (or deleting its app) stops the fallback immediately.
- **Rejected alternatives:** One policy row per subject — every branch would persist a row, and the (account, issuer) key would need a schema change. Rewriting the stored pattern on each exchange — the policy would flap between subjects and lose its audit meaning.
