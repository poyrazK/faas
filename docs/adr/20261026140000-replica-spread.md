# ADR 20261026140000 · Spread service replicas and minimum-instance floors across zones and nodes

- **Status:** proposed
- **Date:** 2026-10-26
- **Amends:** spec §6.3 (wake placement)
- **Related:** ADR-025 (multi-node placement), ADR-062 (per-node schedd),
  ADR-071 (minimum-instance floors)

This record has a date-and-time identifier because numbered ADRs collide
when parallel changes pick the next number.

## Context

A service's desired replica count is a failure-isolation contract: the
service reconciler's own comment says so, and it marks replica admissions
with `withServiceReplicaPlacementSpread`. That flag only dropped the
sticky-warm hint. The rest of placement still pulled replicas together:

- The owner node is the preferred node of every ordinary admission, and it
  wins whenever its CPU headroom ties the best.
- Physical CPU headroom ranks first, so on unequal nodes the larger node
  takes every replica until its headroom falls below the smaller node's.
- A node holding the snapshot keeps restores unless a peer has twice its
  CPU headroom.
- Zones never entered the decision.

One node failure could therefore take every replica of a service, and a
minimum-instance floor kept warm capacity on one node.

## Decision

1. `Request.SpreadReplicas` marks admissions that keep away from the app's
   other live instances: service replicas (`TriggerServiceReplica`, or the
   replica spread context) and minimum-instance floors (`TriggerFloor`,
   `TriggerFloorDep`). Cold-burst siblings keep their snapshot locality: a
   local restore takes well under a second, a remote one many seconds.
2. The owner scheduler counts the app's serving reservations per node from
   its ledger (`NodeLedger.AppInstancesByNode`). The owner admits every
   instance of its apps, so no database read is added to placement.
3. Among the nodes that fit every resource guard, the chooser keeps those
   whose failure zone (region and zone) holds the fewest of the app's
   instances, then those whose own node holds the fewest. The existing
   ranking (owner and warm hints, snapshot locality, physical CPU, RAM,
   guest vCPU, upstream region, names) chooses among the kept nodes. A hint
   outside the kept set is dropped. Zone counts include instances on nodes
   that no longer fit, since those still share the zone's failure domain.
4. Spreading is a preference, never a gate. A fleet with one fitting node
   admits there. Nodes without region or zone form one domain, so a fleet
   without zones spreads by node alone.

## Consequences

- A service with N replicas on N fitting nodes runs one per node, and across
  zones first when zones are configured.
- A spread replica may restore its snapshot on a node that must fetch it
  first. Service replicas and floors are long-lived, so that one-time cost
  buys failure isolation.
- No new configuration, schema or wire field.

## Validation

`TestChoosePlacementSpreadsReplicas` (owner and snapshot hints yield, zone
before node, an unequal fleet, a full node, a single node),
`TestChoosePlacementWithoutSpreadKeepsTheRanking` and
`TestServiceReplicasSpreadAcrossUnequalNodes` (engine, two unequal nodes).
