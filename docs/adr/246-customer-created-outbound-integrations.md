# ADR-246: Customer-created outbound integrations

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Allow an account to create and delete its own managed outbound integration through MFA-gated deploy-write API routes. Creation fixes a public HTTPS origin, explicit maximum HTTP methods and path prefixes, a customer-sealed credential source, and bounded server-selected admission defaults. The provider Authorization value is uploaded separately, sealed to the fleet recipient, and opened by `outboundd` only after workload-identity and route checks.
- **Ownership:** `apid` may create or delete only rows marked `owner_kind = customer`; the owner kind is immutable. `outboundd` remains the writer for operator rows and cannot reconcile over customer-owned IDs. Both integration policy and customer app bindings are resolved from Postgres on each request, so creation, binding, credential rotation, and deletion need no gateway restart.
- **Protection:** Customer origins pass `ValidatePublicOrigin` before persistence and the outbound dialer repeats public-address validation at connection time. App bindings can narrow the integration's method/path ceiling. Customer integrations share one bounded Prometheus metric label. Per-account creation is serialized and capped at 25 enabled integrations; each has a fixed 10 RPS, burst 20, 10 in-flight, and 30-second request timeout.
- **Consequences:** Fleet workload-identity JWKS and the fleet age private credential must be configured on `outboundd`; `apid` must have the matching public recipient. Deletion cascades to sealed credentials, app bindings, and admission state. Provider keys can still be echoed by a provider response, and this API does not add spend budgets, transparent interception, caching, or retries.
- **Rejected alternatives:** Requiring operator provisioning for every origin defeats self-service. Allowing arbitrary private origins would create an SSRF path; these are rejected rather than supported through the default transport.
