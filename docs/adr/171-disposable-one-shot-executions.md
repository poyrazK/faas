# ADR-171 · Disposable one-shot executions from sanitized runtime snapshots

- **Status:** proposed
- **Date:** 2026-09-09
- **Decision:** Add a first-class `execution` resource for authenticated, caller-supplied Node.js or Python source. `POST /v1/executions` admits a closed request envelope (`runtime`, single-file `source`, JSON `input`, resource `limits`, and `network.mode=none`), persists encrypted execution intent, and returns a durable execution id. The caller may wait for a terminal response or poll `GET /v1/executions/{id}`; disconnecting does not extend or cancel the admitted deadline. `DELETE /v1/executions/{id}` requests cancellation. The public routes remain disabled until the restore-execute-destroy path and metal isolation suite land.
- **Language contract:** `node22` and `node24` source is an ES module whose default export is `async function main(input, context)`. `python312` and `python313` source defines `def main(input, context)` (an `async def` is also accepted). `input` may be any JSON value and the return value must be JSON-serializable. The initial contract has no dependency install, tenant secrets, environment injection, or multi-file bundle. Go and other compiled languages require the existing builder isolation boundary and are deferred.
- **Snapshot contract:** A runtime snapshot contains only the kernel, guest init, one-shot executor, interpreter, and read-only standard-library image. It is captured before any tenant source, input, identity, environment, or secret enters the VM. Its immutable catalog key includes architecture, kernel digest, guest-executor digest, runtime/base-image digest, memory shape, scratch-disk shape, and snapshot-format version. A missing or corrupt snapshot falls back to a cold boot of the same sanitized image; snapshots remain a cache, never truth.
- **Execution lifecycle:** `schedd` claims durable `queued` intents and is the only component that creates the associated instance row. It asks `vmmd` to restore or cold boot into a fresh jail, network namespace, cgroup, tap, and scratch drive. Source and input cross the authenticated host/guest boundary in a length-prefixed vsock request only after the restore resume hook has refreshed entropy and time. The guest invokes the entrypoint exactly once, streams bounded result/stdout/stderr frames, and exits. The VM is destroyed on success, language error, timeout, OOM, cancellation, protocol failure, or host restart; it is never parked, pooled, or snapshotted after tenant code runs.
- **Resource boundary:** The deadline begins when apid admits the execution and includes queue and restore time; the guest receives only the remaining duration. A host timer is authoritative and kills the VMM at expiry. Memory and CPU are independently enforced with cgroup v2 (`memory.max`, `memory.events`, `cpu.max`); PID count is capped in host and guest; scratch capacity is a shaped disposable ext4 drive; result, stdout, and stderr share one byte cap enforced on both sides of vsock. Memory and disk use closed shapes because Firecracker restore requires a compatible machine/device configuration. All plan gates, defaults, and maxima live in `pkg/api/limits.go`.
- **Network boundary:** v1 is loopback-only. The disposable VM receives no tenant bridge route, platform DNS, service-discovery endpoint, metadata route, or public egress rules. Enabling any outbound connectivity requires a follow-up ADR and an explicit allowlist contract; it cannot be introduced by changing the meaning of `network.mode=none`.
- **Persistence and retention:** The durable state machine is `queued → restoring → running → {succeeded, failed, timed_out, out_of_memory, cancelled}` with terminal states immutable. Metadata, resolved limits, host-observed usage, and bounded output live in `executions`; source and input live as ciphertext in a separate payload row, are delivered only to the claimed execution, and are erased when the execution becomes terminal. A sweeper removes orphaned payloads and stale terminal output after the documented retention window. API responses never echo source or input, and platform logs record ids, shapes, and byte counts rather than payload content.
- **Why:** Gregale already has strong Firecracker isolation, snapshot restore, cgroups, jailer, and run-to-completion scheduling, but its snapshots currently include deployed application state and its invoke surface accepts data rather than source. Reusing a warm app VM would permit cross-execution state and would turn tenant code into a snapshot input. A sanitized runtime snapshot plus mandatory teardown closes those gaps while preserving the existing cold-boot correctness invariant.
- **Consequences:** This is a new workload class rather than an alias for `/invoke` or Jobs. Jobs continue to run stored images and functions continue to serve repeat requests from deployment snapshots. The implementation must add the durable store and sqlc queries, schedd claim/recovery loop, runtime-snapshot catalog, guest executor protocol, vmmd restore/cold-boot adapter, public handlers/client/OpenAPI surface, metrics, leakcheck, and metal tests before the capability can be advertised. Billing and retention values need product-model approval before the ADR can move to accepted.
- **Rejected alternatives:** Evaluating source inside `apid` or a long-lived worker has no microVM boundary. Reusing a deployed function snapshot captures tenant code and state. Restoring one VM for multiple callers violates disposal and cross-tenant isolation. Encoding source into an existing invocation payload hides a different lifecycle behind `/invoke`. Treating source as a Job image forces callers through a build/publish workflow and cold boot, so it does not satisfy snapshot-restored one-shot execution.
