# ADR-20261021215353: Early freeze — stop billing shortly after the last request

Date: 2026-10-22
Status: Accepted, behind schedd `frozen_tier_early_freeze_after_s` (off by default). Amended 2026-10-27: settable in the deployment manifest (see "Amendment 2026-10-27").
Amended by: [ADR-20261023171905](20261023171905-unbilled-quiet-pause.md) — unbilled quiet pause takes over billing; early freeze stays off unless an operator wants earlier memory reclaim, with that reason recorded.
Amends: [ADR-1151](1151-pause-tiers.md) (pause tiers) decision 2
Related: [ADR-906](906-frozen-instances.md) (frozen instances), [ADR-1740](1740-frozen-fast-path.md) (frozen fast path)

## Context

ADR-1151 freezes an idle instance at its idle timeout. A frozen instance holds
its measured memory and no vCPU or concurrency, is not billed, and resumes on
the next request in a few milliseconds. Between the last request and the idle
timeout, though, the instance stays RUNNING and billed: 30 s for a function,
60 s to 10 minutes for an app. A quiet-paused instance (ADR-1151 decision 1)
uses no CPU in that window but is still a running, billed instance.

ADR-1151's simulation over the Azure Functions trace priced that window.
Policy E (quiet pause, freeze at the idle timeout, the shipped design) bills
29.4 GB-h per app-month; policy F (freeze 2 s after the last request, frozen
time unbilled) bills 9.3 GB-h at the same density, 716 apps per EX44, with
99.8% of wakes thawing in 8.5 ms. Revenue per app-month moves from €3.94 to
€3.83, because most of the reclaimed hours fall inside included allowances.

Competing serverless platforms now bill memory only while a request is in
flight. Policy F is how Gregale matches that without changing what a billed
second means (§4.7: plan RAM + 8 MB per running second): the instance simply
stops being a running instance sooner.

## Decision

- schedd `frozen_tier_early_freeze_after_s` (0 = off, otherwise 2-300,
  `FAAS_FROZEN_TIER_EARLY_FREEZE_AFTER_S` overrides it) freezes an eligible
  instance once it has been quiet for that long, instead of at its idle
  timeout. It needs `frozen_tier`; it is ignored otherwise.
- **Who freezes early.** Exactly the instances the frozen tier would freeze
  at the idle timeout (ADR-1151 eligibility, including `frozen_tier_apps` for
  apps) **and** whose effective pause is `between_requests`: functions by
  default, and apps that opted in. Those workloads already accept that timers
  stop between requests, so freezing them earlier changes nothing they can
  observe except that the next request thaws (5-15 ms) instead of resuming
  from a quiet pause (1-3 ms). `when_idle` apps keep running through their
  idle timeout as they declared, then freeze as before; `never` apps never
  freeze.
- **Quiet means** no request in flight, no open connection, no `waitUntil`
  tail, and a last request (or start) at least `after` ago but less than the
  idle timeout ago; at the idle timeout the ordinary reaper path takes over.
  Apps with a `--min` floor and apps inside their scale-in cooldown are not
  frozen early: a floor is resident by design, and the cooldown protects a
  fresh scale-out.
- **Nothing else moves.** The freeze is the ADR-1151 freeze (same state
  machine, ledger charge, fences, `FrozenMaxPerNode`, fast-path tickets). The
  frozen TTL still ends at last activity + idle timeout + `FrozenTTLSeconds`,
  so an early-frozen instance parks when it would have parked anyway. Billing
  needs no change: frozen is outside the billable set.
- `schedd_frozen_total{outcome="frozen_early"}` counts early freezes; other
  outcomes keep their labels.

## Consequences

- With the switch on, a `between_requests` workload accrues usage only for
  the seconds it serves plus the early-freeze delay. On the reference
  simulation that cuts billed GB-h per function app-month by about two
  thirds.
- Each request after a quiet period takes a thaw through schedd (one state
  compare-and-set each way; with ADR-1740's fast path, no wake-path reads).
  A chatty app with requests closer than `after` never freezes, so the delay
  bounds that churn; 10 s is the recommended production value.
- The platform holds the frozen VM's measured memory unbilled for longer.
  ADR-1151's memory-pressure order already parks frozen instances first.
- Rollout follows ADR-1151: canary with functions, then apps. The economics
  should be re-checked against the financial model before the switch is on
  fleet-wide.

## Alternatives considered

- **Do not bill quiet-paused time.** Keeps resume at 1-3 ms, but makes a
  running instance partly billable, needs per-interval pause accounting in
  metering and holds vCPU bookings for unbilled VMs. Freezing reuses a state
  that is already unbilled and already holds no vCPU.
- **Change the default pause of apps to `between_requests`.** Would stop
  timers in apps that rely on them; the pause is the app's declaration.

## Amendment 2026-10-27: a manifest key, default unchanged

On rc.297 on 2026-10-27, `frozen_tier_early_freeze_after_s = 10` in
compute-1's (fsn-2) `schedd.toml` froze a quiet instance and thawed it in
12 ms after a 20 s gap; with the freeze cadence, not every gap froze.

Release rollouts re-render `/etc/faas/schedd.toml` from the deployment
manifest, so a value set by hand on a node is lost at the next rollout. The
manifest now carries it: `daemons.schedd.frozen_tier_early_freeze_after_s`
(0, or `api.FrozenEarlyFreezeMinSeconds`-`api.FrozenEarlyFreezeMaxSeconds`,
checked by `gregale manifest validate`). Omitted, nothing is rendered and
schedd keeps its default.

The default stays 0 (off): after ADR-20261023171905, early freeze is for
earlier memory reclaim, not billing, and an operator sets it with that
reason. 10 s remains the recommended value. A manifest that sets the key is
rejected by a `gregalectl` or `imaged` built before it, so the production
manifest sets it only after a release that parses it is live on every node.
