# ADR-20261115110124: gRPC steps in `gregale test` scenarios

Status: Accepted
Date: 2026-11-15
Related: ADR-126 (bridge H2C terminator), ADR-20261105095300 (Compose
`x-gregale-app-protocol`), ADR-20261026181020 (service addresses)

## Context

Apps can serve gRPC (`--app-protocol grpc`, `x-gregale-app-protocol: grpc`),
but `gregale test` scenarios only send HTTP requests from OpenAPI or Postman
input. Smoke-testing a gRPC service meant a hand-written grpcurl script beside
the manifest (2026-11-15 microservices-demo feedback). The owner chose the
scope: definitions from `.proto` files and server reflection, all four call
shapes, assertions on status, response JSON and metadata, and both execution
engines that send traffic (`local`, `real-vm`).

## Decision

A request or check step may carry a `grpc:` block instead of `method`/`path`.
It is the same step: it has a `name`, optional `as` (consumer key sent as
`authorization: Bearer …` metadata), `expect` and `capture`, and runs in the
same order and lists (`requests`, `checks`, staged `steps`).

```yaml
scenarios:
  catalog-smoke:
    project: shop
    source: ./src/productcatalogservice
    grpc:
      protos: [protos/demo.proto]   # relative to the manifest; optional
      import_paths: [protos]        # optional; defaults to each proto's directory
      reflection: auto              # auto (default) | always | never
    requests:
      - name: list-products
        grpc:
          method: hipstershop.ProductCatalogService/ListProducts
          message: {}               # one request message (unary, server streaming)
          metadata: {x-tenant: "${data.tenant}"}
          timeout: 5s
        expect:
          code: OK
          json: {/products/0/id: OLJCESPC7Z}
          headers: {content-type: application/grpc}
        capture: {first_product: /products/0/id}
      - name: chat
        grpc:
          method: demo.Chat/Talk
          messages: [{text: hi}, {text: bye}]   # client or bidi streaming
        expect:
          code: OK
          message_count: 2
          json: {/1/text: bye}
          trailers: {x-session: "${steps.chat.session}"}
```

**Definitions.** Proto files compile in the CLI with
`github.com/bufbuild/protocompile` (pure Go, no `protoc`). With
`reflection: auto` the CLI uses the protos when they define the method and
asks the server's reflection service (v1, then v1alpha) otherwise; `always`
skips the protos and `never` requires them. Validation (`gregale test
--validate`) compiles the protos and resolves every method offline; methods
left to reflection are checked when the step runs.

**Call shapes.** The method descriptor decides the shape. Unary and server
streaming take `message`; client and bidirectional streaming take `messages`
(sent in order, then the send side closes). Giving the wrong field for the
shape is a validation error.

**Messages as JSON.** Request messages are YAML/JSON in protobuf JSON form,
expanded with the existing `${…}` templates, then parsed with `protojson`
into dynamic messages (`dynamicpb`). Responses render back with `protojson`
(proto field names, defaults omitted as protojson does). The document the
`json` pointers and `capture` read is the response object for unary and client
streaming, and a JSON array of messages for server and bidirectional
streaming. `message_count` checks how many messages arrived.

**Status and metadata.** `code` is a gRPC status name (`OK`, `NOT_FOUND`, …)
or number; it defaults to `OK`. `message` (optional) matches the status
message exactly. `headers` and `trailers` match response metadata keys
(lower-case) to expected values after template expansion; a key must be
present with that value, others are ignored.

**Transport.** Each engine dials the target directly, not through the
HTTP/1 evidence proxy: `local` uses the loopback base URL with cleartext
HTTP/2, and `real-vm` uses the deployed app's HTTPS URL with TLS. gRPC steps
therefore contribute no wake evidence to the profile; a scenario that needs
wake evidence keeps one HTTP step. The `simulated` engine validates gRPC steps
but does not run them.

**Limits.** A request message encodes to at most 1 MiB (the HTTP step's JSON
limit); a step reads at most 1,000 response messages and 1 MiB of rendered
JSON; the default step timeout is 30 s, the HTTP client's, and `timeout`
may lower or raise it up to 5 minutes.

**Evidence.** A gRPC step records the same evidence entry as an HTTP step:
`method: GRPC`, `path` set to the full method name, `status` to the numeric
gRPC code, duration and pass/fail. Reports, JUnit and comparisons need no new
fields.

## Consequences

- One new dependency, `github.com/bufbuild/protocompile`, used by the CLI only.
- gRPC steps run in `requests`, `checks` and staged `steps`; load mode
  (`--load`) keeps HTTP steps only and refuses a scenario whose steps are gRPC.
- `gregale test init` and `import` stay OpenAPI/Postman; gRPC steps are
  written by hand.
