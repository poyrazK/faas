# ADR-1574: Saved production cutover and DNS recovery

- **Status:** Accepted
- **Date:** 2026-10-17
- **Context:** Migration verification ends at the Gregale URL. Customers must still connect production DNS, distinguish their old provider from the intended deployment, assess traffic and preserve recovery settings themselves.
- **Decision:** Save an immutable app-owned cutover plan with a caller UUID, a currently passed default-scope verification, one concrete production hostname, all previous A/AAAA or CNAME routing records and TTLs, the previous proxy setting, and explicit error/latency budgets. Preparation performs storage reads and writes only. Add domains through the existing ownership/quota/audit API. Provider DNS, default hostname, deployment traffic percentages and saved monitor policy are never edited by cutover orchestration.
- **Checks:** `start_checks` explicitly arms a thirty-minute checking window. An indexed due queue, versioned forty-second leases, two workers and bounded public probes survive browser closure and apid restart. Check domain ownership, current Gregale DNS routing, system-trusted hostname TLS and the existing gateway-authored exact-deployment response proof on the original read-only verification path. A successful old-provider response or certificate is insufficient. Only the operator's published public edge addresses are eligible: use the configured edge addresses or resolve the operator-controlled edge target. Every customer DNS answer must belong to that set, then numeric dialing preserves hostname/SNI validation without a second lookup. This keeps smoke challenges away from arbitrary public origins. Redirects and environment proxies are disabled. No response bodies or gateway challenge tokens enter cutover receipts; public TXT ownership instructions remain available.
- **Fences:** Revalidate source verification, deployment/configuration and domain binding after network checks. The private binding revision includes the challenge token, fencing domain deletion/recreation, reassignment and environment binding changes. Versioned cancellation or manual recovery acknowledgement defeats an in-flight worker save. Evidence cannot qualify a changed deployment. Reads revalidate saved evidence without network probing; previous DNS recovery remains available when the plan becomes blocked.
- **Traffic:** Reuse the existing read-only route-monitor preview for GET on the selected exact route with the plan's budgets. Re-evaluate only completed windows beginning after continuous hostname proof. Exclude pooled pre-cutover history and customer cohorts. Report observed deployment/route coverage explicitly; the telemetry is not hostname-specific and does not prove every customer moved. Sparse, missing, unavailable or plan-gated telemetry is unknown. A sustained budget violation blocks completion. Unknown evidence requires explicit acknowledgement. Completion always performs fresh hostname checks before saving its result; it never automatically changes routing.
- **Recovery:** Save typed routing values only, excluding URLs, credentials and arbitrary notes. Show original routing, TTLs and proxy setting for manual restoration at the provider. `confirm_restored` records a customer's explicit attestation; it is not a DNS transaction or platform-verified restoration. `cancel` stops checks without changing DNS or service lifecycle. Keep the previous service available through propagation and verify it before recording recovery.
- **Bounds:** Up to sixteen prior routing records and twenty saved plans per app; terminal plans may be pruned after ninety days on subsequent creation. Prepared, checking, ready and attention plans retain recovery records. Thirty-second check cadence, five-second queue polling, batches of sixteen and two workers. All bounds are centralized in `pkg/api/limits.go`. Creation and actions require deployment write scope, verified email and MFA; reads require app read scope and MFA.
- **Validation:** Tests cover no-work preparation, lost-response identity, restart discovery, optimistic claims, cancellation during network I/O, configuration drift, binding replacement, trusted old-provider responses, redirects, mixed private/public DNS, post-switch observation windows, zero-traffic limits and explicit recovery acknowledgement. The console exercises saved-plan recovery and browser closure. The full migration bundle still requires native Firecracker lifecycle/leak acceptance on a dedicated x86_64 KVM host before shipping.
