# ADR-20261022120744 · Release page

- **Status:** proposed
- **Date:** 2026-10-22
- **Uses:** explained rollout decisions ([ADR-1447](1447-explained-rollout-decisions.md)), post-release watch ([ADR-1445](1445-post-release-watch.md)), release gates ([ADR-20261019071734](20261019071734-release-gates-on-customer-signals.md)), release approvals ([ADR-20261020085706](20261020085706-release-approvals.md)), release diff ([ADR-20261021101117](20261021101117-release-diff.md)), scheduled releases ([ADR-20261021152201](20261021152201-scheduled-releases.md))
- **Decision:** One read model and one page for a single release.
  - `GET /v1/deployments/{id}/timeline` composes what Gregale already records about a release into a phase, a one-line summary and a time-ordered list of events: created, scheduled, approvals, rollout start, each canary step with the decision behind it, holds, gate results, completion, the post-release watch, abort or rollback, and the release that replaced it.
  - `/dashboard/releases/{id}` renders it with the release diff, and offers the next step: advance or abort a canary, or open the approval page.
  - `gregale deployment timeline <id|vN>` prints the same timeline.
- **Why:** A release's story is recorded in five places: the deployment row, its `deployment_audit` rows (traffic changes and holds carry the ADR-1447 decision, with its gate results), the approval tables, the schedule and the rollout timestamps. Answering "why is my release stuck at 10%?" or "why was it rolled back?" means reading several commands' output and raw audit JSON. Approval and schedule notifications already link a release by its ID, and the approval page lives at `/dashboard/releases/{id}/approval`; `/dashboard/releases/{id}` was the natural missing page.
- **Rejected alternatives:**
  - **A new table of release events.** Every event already has a durable source. A second copy would need its own writers in apid, meterd and the store transactions, and could disagree with the sources it copies. The timeline is computed on read; it is bounded by `api.ReleaseTimelineAuditRowsMax` audit rows.
  - **Extending the deployment detail page** (`/dashboard/apps/{slug}/deployments/{id}`). That page is about the build: stages, scan, logs, preview URL. Its route needs the app slug, which notifications do not carry, and it checks only the account that owns the app, not organization access. The two pages link to each other.
  - **Extending `deployment summary`.** The summary is the cheap cockpit for the deploy flow: the previous row and the rollback target. ADR-20261021101117 kept it cheap; the timeline reads the audit history and the approval state.
  - **Returning raw audit rows.** `GET /v1/deployments/{id}/audit` already does. Clients would each have to know which audit kinds matter, decode the decision payloads, collapse repeated holds and derive the watch window.

## Decision

### Phase

The phase is the first match in this order:

| Phase | When | Summary, for example |
|---|---|---|
| `building` | the deployment is pending, building, imaging or snapshotting | Building |
| `failed`, `cancelled` | the build failed or was cancelled | Build failed: … |
| `rolled_back` | the rollout was aborted, or an automatic rollback replaced the release | Rolled back at 10% of traffic: … (the decision's summary) |
| `scheduled` | a pending schedule waits for its time | Scheduled for 2026-10-23 09:00 UTC |
| `awaiting_approval` | the approval state is `waiting` | Waiting for 1 more approval |
| `superseded` | a newer release replaced it | Replaced by v43 |
| `held` | a canary in flight with a hold recorded for its current step | Held at step 2 of 4 (10% of traffic): … (the hold's summary) |
| `rolling_out` | a canary in flight | Rolling out: step 2 of 4, 10% of traffic |
| `watching` | the rollout completed and the post-release watch still judges it | Released; watched until 14:32 UTC |
| `released` | live | Released to 100% of traffic |

### Events

| Event kind | Source |
|---|---|
| `created` | the deployment row (deployer, commit, PR, tag, reason) |
| `scheduled`, `schedule_started`, `schedule_blocked`, `schedule_cancelled` | the release's schedule |
| `approval_requested`, `approved`, `rejected`, `approval_expired` | the approval state and its decisions |
| `rollout_started`, `completed`, `aborted` | `deploy.rollout_*` audit rows |
| `advanced`, `traffic_changed` | `deploy.traffic_changed` rows: `advanced` when the row carries an advance decision, `traffic_changed` for a hand-set split |
| `held` | `deploy.rollout_held` rows. Consecutive holds with the same rule collapse into one event with a `repeats` count. |
| `rolled_back`, `rollback_requested` | `deploy.rolled_back` and `deploy.rollback_requested` rows, with their decision and reason |
| `watch_passed` | derived: the watch window ended without a post-release rollback |
| `superseded` | derived: the next release of the same scope that took traffic |
| `note` | any other audit kind (health probes, alert rules, scan regressions, worker drains), with a fixed sentence and no payload |

Events carry the ADR-1447 decision when their source has one, so gate results show at the step that judged them. The response's `gates` are the results of the newest decision that judged gates. Actors are shown as the deployer's or approver's email for people, and as "Gregale" for apid and meterd.

The newest `api.ReleaseTimelineAuditRowsMax` (500) audit rows are read; when there are more, `truncated` is set and the oldest are left out. Approval comments and abort reasons are already bounded where they are written.

### Access and actions

The endpoint uses the deployment read routes' access checks (`loadCanaryDeployment`: organization access, app access, read scope). The page renders no release data on the server: like the approval page, its script reads `/v1/deployments/{id}/timeline` and `/v1/deployments/{id}/diff` with the signed-in session, so the same checks apply. Its buttons call the existing write routes, which keep their MFA, role, approval, freeze and gate checks:
- **Advance** sends `POST /v1/deployments/{id}/canary/advance` with the step the page showed, so a stale page cannot skip a step;
- **Abort** sends `POST /v1/apps/{slug}/rollouts/recover` with `action: abort`, the release and the stable release it replaces;
- **Review approval** opens `/dashboard/releases/{id}/approval`.

## Consequences

- No migration and no new writer. An audit kind added later shows as a `note` until the timeline learns it.
- The approval page, the deployment detail page and the CLI link to the release page.
- A release created before ADR-1447 has no decisions in its audit rows; its timeline shows the transitions without explanations.
