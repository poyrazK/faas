# ADR-523 · Queue consumer readiness at bindings promotion

- **Status:** accepted
- **Date:** 2026-10-02
- **Decision:** Evaluate scheduler consumer readiness for enabled push queue bindings in the shared bindings check and server promotion gate. Connectivity coverage remains unsupported. A connectivity waiver never waives a missing, paused, degraded, stale, unobserved or unknown push consumer.
- **Freshness:** Reuse the queue status threshold of thirty seconds through `api.QueueConsumerMaxPollAge`. Require an active consumer, healthy liveness and a nonzero poll timestamp no later than the evaluation clock. The exact age boundary passes; older polls fail even if an earlier inventory labelled them healthy. Probe `max_verification_age` does not change this threshold. Queue status treats future polls as unknown and zero polls as unobserved.
- **Atomic promotion:** After a passed assessment, derive the earliest deadline among required connectivity proofs and enabled push consumer polls. Check that deadline through the existing ADR-529 traffic guard after acquiring locks. Existing revision fences already cover queue bindings, consumer triggers and health timestamps in MemStore and PostgreSQL. A later poll/configuration mutation invalidates the assessment; elapsed time alone can also invalidate it. Expired polls return a binding-specific `queue_consumer_stale` blocker with scheduler recovery instructions, rather than asking for an unsupported queue connectivity probe.
- **Coverage:** A healthy idle consumer needs no delivered message or last-success timestamp. Scheduler polling is app-wide control-plane telemetry, not deployment-specific guest connectivity, application readiness or end-to-end delivery proof. External pull consumers retain unsupported/partial coverage with the explicit waiver. Disabled bindings are skipped. Known queue readiness failures appear as `blocked` per-binding results while connectivity coverage remains partial. This extends ADR-527/529 without changing wire shapes.
- **Operations and rollback:** Inspect `gregale queue status APP` and binding status to restore missing projections, resume consumers, resolve errors or repair scheduler clocks/polling; retry after a fresh healthy poll. The checks send no messages, consume no queue work, create no tasks and change no VM lifecycle behavior. No migration or new state field is needed. Rolling back the code restores the earlier preflight policy and preserves queue configuration and health history.
- **Validation:** Shared-policy cases cover missing/paused/degraded/stale/unknown consumers, absent/zero/future timestamps, the exact age boundary, healthy idle polling, external pull and disabled bindings. Passing service, PostgreSQL, object-storage and outbound probes cannot hide queue failures under a waiver. API and CLI tests cover structured blockers, recovery and partial coverage. API tests expire an unchanged healthy poll before the traffic write and reject a health mutation after assessment. MemStore/PostgreSQL tests cover health, trigger and binding mutations, plus the existing expiry-after-lock-wait regression.
