# ADR-20261102192943: Common Compose files deploy as written

- **Status:** accepted
- **Date:** 2026-11-02
- **Owner:** reposcan and reconcile maintainers
- **Amends:** ADR-685 (Compose dependency release gates), ADR-20261022131852 (unpublished Compose services are internal)
- **Decision:** Three shapes found in most real Compose files now deploy, and none of them gets a meaning Compose did not give it:
  - **Loopback ports stay private.** A service whose `ports:` all bind a loopback address (`127.0.0.1:8081:8080`, `[::1]:…`, `localhost:…`, or `host_ip: 127.0.0.1`) is internal, like a service without `ports:`. Docker publishes such a port only to the machine running Compose; the scan used to drop the address and give the service a public URL. These are usually admin tools (Adminer, MailHog, debug dashboards). The service still serves (`class=http`), the plan warns, and an existing app keeps the visibility it was created with. A bracketed IPv6 host (`[::1]:8081:8080`) is now parsed at all; it used to leave a built service without ports.
  - **A health gate on a datastore relaxes.** `depends_on: {db: {condition: service_healthy}}`, where `db` is a Compose datastore (`postgres`, `redis`, …) that Gregale does not run as a service, becomes `service_started` with a plan warning. ADR-685 refused it, because no deployment of `db` exists whose health a release could wait for. The dependency stays, so the service still gets the datastore's variable. A managed database provided by the deploy is created before the services that use it; the service should still retry its connection, as it does when Compose restarts a database.
  - **A completion dependency is a release command.** A service that others wait for with `condition: service_completed_successfully` (a migration or seed step) runs as the release command of the waiting service that serves requests and shares its build (the same `build:` context, Dockerfile, build options and Go command, or the same `image:`). It runs once before each release of that service goes live, in that service's image with its environment and secrets, which is what Compose ran. It is not deployed as an app. The step's environment keys and dependencies join the owner's; other services that listed it stop waiting for it, and the plan says so. ADR-685 refused completion gates for want of a durable job-run contract; the release task is that contract (`releaseAllowsPrime` holds the release until the task succeeds).
- **Keeping the release command.** Reconcile stores the command on the owner app (`AppManifest.ProjectReleaseCommand`), and `resolveSourceReleaseCommand` uses it when the deployed source declares no release command of its own (gregale.yaml `release.command` or Procfile `release:` still win). So GitHub pushes, single-app deploys and a project with one remaining service run it too, not only a reviewed multi-service deploy. A changed command is a reconcile change (`release_command`). A Procfile `release:` is not stored on the app, exactly as before.
- **Refused, with the reason in the plan:** a completion dependency that builds from other source than every service waiting for it, publishes ports, has no `command:`, is a datastore, or waits for another completion dependency (chains); a waiting set with no serving service (the release fence holds a serving release, so a worker alone cannot own it); two completion dependencies for one service; and a repository that also declares a Procfile `release:`, which would run the migration twice.
- **Why:** An investigation of the multi-service path (2026-11-02) ran real-world Compose files through the scan. The two most common database shapes (`service_healthy` on `postgres`, a `migrate` service with `service_completed_successfully`) failed the plan. Without the condition, the migration service became an always-on worker that worker recovery restarted every 5–300 s, re-running the migration. And `127.0.0.1`-bound admin tools got public URLs without a warning.
- **Consequences:**
  - Projects that failed the plan now deploy. Nothing that deploys today changes, except that a service whose ports are all loopback-bound is created internal instead of public.
  - A migration runs on every release of its owner, including PR previews (with the preview's own variables), as Compose runs it on every `docker compose up`.
  - The migration runs only in its owner's release. Other services that waited for it in Compose may start before it ends; the plan names them.
- **Rejected alternatives:**
  - **Deploy the completion dependency as a job app and gate on its run.** Needs a per-release job-run record and a new gate in schedd, for the case a release command already covers.
  - **Hold the dependent until a managed database is ready.** The database is created before its consumers deploy, and a database a customer runs elsewhere has no health Gregale can read.
  - **Publish loopback-bound ports and only warn.** A warning does not take an unauthenticated admin tool off the internet.
