# ADR-292 · Shared outbound provider cooldown

- **Status:** proposed
- **Date:** 2026-09-27
- **Decision:** When an outbound provider returns HTTP 429 with a valid `Retry-After`, record a per-integration cooldown in Postgres, bounded to one hour. Check the shared deadline on cache misses before contacting the provider; reject a fresh provider call with 429 and a positive `Retry-After` while the deadline is active. Concurrent updates extend the deadline but never shorten it. Reset the deadline when the integration policy revision changes. A valid `Retry-After` longer than the one-second in-request retry window is not shortened into an early retry; return the provider response and let a later request honor the shared cooldown.
- **Why:** `max_retries` and the shared retry token bucket govern additional attempts within a logical call, but neither prevents independent requests on other replicas from immediately repeating calls after a provider has explicitly rate-limited the integration.
- **Consequences:** Cooldown state shares the existing per-integration Postgres admission row. A provider's first 429 response and headers pass through unchanged. New cache misses receive a gateway-generated 429 with `X-Gregale-Outbound-Rejection: provider_cooldown`; cache hits remain available because they do not contact the provider. The cooldown gate follows ordinary admission, so rejected attempts still count against configured admission budgets. Missing or invalid `Retry-After` values do not create shared cooldown state. Metrics report bounded record, block, and state-availability outcomes without exposing customer integration IDs.
- **Rejected alternatives:** Process-local timers, which would let each replica keep sending; opening the optional circuit breaker on every rate-limit response, which conflates provider quota guidance with the transient-failure threshold; retrying after a locally shortened delay, which can violate the provider's explicit wait request.
