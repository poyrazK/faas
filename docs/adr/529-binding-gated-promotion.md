# ADR-529 · Bindings gate at traffic promotion

- **Status:** accepted
- **Date:** 2026-10-02
- **Decision:** Add opt-in `traffic promote --require-bindings` using `POST /v1/deployments/{id}/promote`. The API evaluates ADR-527 policy against the exact materialized live deployment from ADR-528, then atomically compares the observed facts before promoting it to 100%. Keep the existing traffic PATCH behavior.
- **Policy:** Default verification age is ten minutes. `--max-verification-age` selects a positive duration. `--allow-unsupported` explicitly waives queue/outbound connectivity coverage and retains partial coverage. Both policy options require the gate in the CLI. Inventory permissions, completeness, supported probe stages, binding identity/generation, scope, rotation/refresh and runtime freshness retain the preflight rules. The gate schedules no probes, tasks or restarts.
- **Concurrency:** PostgreSQL maintains an internal per-app epoch and revision. Row triggers increment it in the same transaction as relevant configuration, catalogs, verification tasks, runtime observations or refresh metadata. Environment/secret writes and credential rotations invalidate the revision before the separate runtime-config timestamp is marked. Read the revision before collecting inventory; lock and compare it inside the existing traffic transaction after locking live deployments. Reuse the existing deployment reader before that transaction; every deployment field used by the guard is covered by the revision, so its locked comparison also validates that snapshot. Hold that lock through traffic commit. Avoid lease, usage and request-heartbeat fields outside the policy. Managed PostgreSQL and state stores must share the same pool; other arrangements fail closed. Serialization/deadlock conflicts return a retryable check conflict, with all tentative traffic changes rolled back. Writers retain ordinary PostgreSQL transaction semantics and can also encounter serialization/deadlock conflicts.
- **Memory stores:** Compare a private digest of relevant state facts under the state mutex through the traffic write. Managed PostgreSQL has a separate mutex; compare its private catalog digest and hold that mutex through the state callback, in catalog-to-state lock order. No digest, revision token, secret or provider detail is accepted from or exposed to API callers.
- **Expiry:** Derive the earliest expiry of required passed evidence and check it after acquiring the traffic/revision locks. A check that expires while waiting cannot authorize promotion. The receipt records the check time at the locked write boundary.
- **Failure and retries:** Return structured `bindings_check` reports on 409 `bindings_check_failed` or `bindings_check_changed`. Failures leave traffic unchanged. Preserve plan, ownership, deployment-write permissions, serving expectation and active-canary controls. A target already at 100% must still pass the gate; after that check it returns an idempotent receipt without requiring its former serving deployment to remain at 100%. Do not emit another traffic audit/notification for this retry.
- **Compatibility:** A dedicated gated route makes older servers return 404 before mutation, instead of ignoring a new field on the legacy PATCH. The CLI checks the receipt's exact deployment, scope, applied age/waiver and passed report before reporting success. Go, Node and Python SDKs expose the route and report; problem envelopes retain the structured blockers.
- **Limits:** The fence protects local committed observations at promotion. Later configuration changes, upstream outages, guest credential adoption and application readiness remain independent. Zero-resident and zero-binding cases retain the preflight warnings and coverage semantics. The migration adds revision writes to affected mutations; rollback removes only fence infrastructure and preserves app configuration and probe history. A new epoch after reinstallation invalidates prior internal tokens.
- **Validation:** MemStore/PostgreSQL promotion and retries, changed env/config before the runtime stamp, catalog rotation locking, serving conflicts, expiry after lock waits, trigger column coverage and transaction/migration rollback, exact candidate evidence, safe problem reports, older servers, SDK generation and existing traffic behavior.
