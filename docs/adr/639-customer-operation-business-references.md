# ADR-639: Customer Operation business references

- **Status:** accepted for internal implementation; production admission stays disabled
- **Date:** 2026-10-07
- **Decision:** An HTTP Operation definition may declare `subject: {type: order, id_from: /order_id}`. A new admission extracts a string from the validated, canonical input using a JSON Pointer and saves the public `{type, id}` reference in the Operation record. No declaration preserves existing behavior and definition revisions.
- **Why:** Customers and operators need to reopen the work related to an application entity without remembering Gregale Operation UUIDs. Several operation names or submissions can relate to the same entity.
- **Consequences:** The reference is immutable across progress, completion, recovery, redeployment, and idempotent replay. New submissions with a missing, non-string, empty, or oversized selected value fail before creating work. Idempotent replays use the originally admitted reference, even if the current deployment changes its declaration. The reference does not change the idempotency key, owner, or execution fences.

Types are lower-case slugs of at most 64 bytes. Selectors are non-root JSON Pointers of at most 2048 UTF-8 bytes, with RFC 6901 escapes and canonical decimal array indices. IDs are opaque nonempty strings of at most 256 UTF-8 bytes. Selectors and IDs reject ASCII control characters. Comparisons preserve case and whitespace; there is no implicit normalization. Definitions and references use the central API limits.

History accepts `subject_type` and `subject_id` together and matches both exactly. Account, app, explicit environment, authenticated customer, retention, and existing name/state filters still apply. Cursor fingerprints include the reference only when selected, preserving unfiltered cursor compatibility and preventing reuse with different filters. Separate SQLC queries and partial expression indexes support descending keyset pagination; indexes are scoped to account/app and optionally customer. References live in the existing JSONB record, protected by a CHECK constraint and an immutable update trigger. Existing records omit the field. Rollback removes guards and indexes, without deleting record metadata.

Business references are public correlation metadata chosen by the application, never proof of business entity ownership or authority. Applications must authorize the underlying order before any business transaction or receipt replay. Customer routes derive ownership from credentials; identical IDs belonging to different customers do not broaden access. Operators retain the existing account/app read boundary. Choose stable IDs suitable for customer-visible history, not secrets or personal display names. No runtime credential or new execution authority is attached to a reference.

The API, Go/Node/Python SDKs, operator CLI, and dashboard expose the reference and scoped lookup. Dashboard links retain the environment and selected customer. The order example declares the order reference. Acceptance follows a committed order through lost HTTP response and authorized recovery, finds the same Operation by order ID, and verifies foreign-customer lookup returns no work. Memory and PostgreSQL tests cover identical IDs across customers, redeploy replay, filter-bound pagination, invalid admission, legacy definitions, and database immutability.
