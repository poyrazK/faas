# ADR-20261030131528: A project workload's bindings name its own project's services

- **Status:** accepted
- **Date:** 2026-10-30
- **Amends:** ADR-20261022111119 ("Calls to services outside the project still need a declared binding"). ADR-20261022120205 decides the name lookup order this ADR narrows.
- **Decision:** A binding on a workload that belongs to a project names a service of that project. It never resolves to, or declares, an app outside the project.
  - **Resolution.** When a project caller has a binding for a name, the name resolves only inside the caller's project: to the live member with that service name, to the project's member with that slug (bindings written by earlier reconcile versions, and the authorizer's `legacyBindingTarget`, name members by slug), or to nothing. It does not fall back to an app slug elsewhere in the account. A deleted member that can still be restored keeps its name (`ErrProjectServiceDeleted`). After it is purged, the name resolves to nothing until the project is applied again. Names the caller does not bind keep ADR-20261022120205's order: the project's service, then the account-wide slug.
  - **Authorization.** For a project caller, a binding declares only a target in the caller's project, under `declared` and `project` alike. A project workload reaches a service outside its project only under the `account` policy. Scenario-test members keep their run-scoped declared check. Standalone apps and their PATCH-declared bindings are unchanged.
  - **Target side unchanged.** `x-gregale-allow-callers` and `x-gregale-allow-call-scopes` still match an app outside the project by its slug when no service of the target's project holds the name, as documented.
- **Why:** Reconcile is the only writer of a project member's bindings. It writes them from `depends_on`, limited to the project's own services (`availableServiceNames`), and apid refuses binding edits on project members. So a project binding always means a project service. The account-wide fallback only ever applied to a binding whose service had gone. A member gets a project-prefixed slug precisely when another app holds its bare name (ADR-20261022120205), so once that member was deleted and purged, the fallback routed a sibling's stale binding to that other app, usually in another project. The declared check then admitted the call, because the stale binding matched the other app's slug. The binding stays until the next apply, and the generated URL (`http://<name>.svc.gregale`) shares its namespace with every app slug, so the call reached the other project for as long as nobody pushed.
- **Consequences:**
  - A stale binding fails closed: the call gets no route, and from `declared` or `project` callers a binding-denied error, instead of reaching another project.
  - A project workload can no longer reach an outside service through a binding. Reconcile never wrote such a binding, so only rows edited outside reconcile, such as test fixtures, relied on it; `TestServiceProxyAuthorizerProjectPolicy`'s outside-declared case now expects a denial. Workloads that need outside services use `account`.
  - The binding inventory is unchanged. The service-binding explanation API runs the gateway's authorizer, so it reports an outside target as denied. The CLI's offline explanation (`explainServiceAuthorization`) applies the same rule, with a hint to use `account`.
  - Release order: the gateway's resolver and authorizer and apid's binding verification read the rule from `pkg/state` and `pkg/servicebinding`; no schema, manifest or API change. A release N-1 gateway keeps the fallback until it is replaced, never something looser than today.
- **Rejected alternatives:**
  - **Pruning siblings' bindings at purge.** The deployed environment keeps `GREGALE_SERVICE_<NAME>_URL` until the next deploy, and its `.svc.gregale` host still resolves to the other app's slug for an `account` caller. It would also edit source-managed manifests outside reconcile.
  - **Marking reconcile-written bindings as project-scoped.** It adds a field to the app API and SDKs, and it takes effect only after every project is applied again. Every project binding would carry the mark anyway.
  - **A lasting record of retired service names.** It needs a table and a cleanup rule to state a fact the caller's binding already carries.
