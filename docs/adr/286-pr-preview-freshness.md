# ADR-286 · PR preview freshness

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** Before an App-managed pull-request webhook changes preview state, githubd reads the current PR through the installation token. An open, synchronize, or reopened delivery must match the current open PR head and same-repository head; a close delivery must match the current closed state. Source-backed deliveries recheck after source fetch and scan, before reserving the preview set. A lookup failure remains retryable. At readiness, PR preview deployments use the same atomic per-app, per-scope revision fence as GitHub production deployments, so an older build cannot reclaim the preview URL after a newer deployment was accepted.
- **Why:** GitHub may deliver webhooks out of order. A delayed synchronize can replace the recorded preview head or rebuild an older commit; a delayed close can start teardown after a PR reopened. Parallel preview builds can also finish in the opposite order from acceptance.
- **Consequences:** The GitHub App reads each eligible PR with its existing Contents:read permission; source-backed open events use a second read after scanning. A GitHub API outage delays preview mutation. A newer accepted preview deployment leaves the older candidate superseded while the last serving preview remains live. Explicit operator rollback still uses the unrestricted promotion operation. A PR change after the final verification can still race acceptance and is a future hardening boundary.
- **Rejected alternatives:** Sorting webhook delivery IDs cannot recover GitHub event order. Comparing commit ancestry fails after force pushes. Relying only on the recorded preview set suppresses old check projections but does not prevent an older in-flight deployment from taking traffic.
