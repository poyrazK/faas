# ADR-499: Customer-cohort production route monitoring

- **Status:** Accepted
- **Date:** 2026-10-03
- **Decision:** Extend advisory production route monitoring with an opt-in request-time tenant or API-consumer cohort dimension. Evaluate each cohort against the configured absolute budgets over the same closed windows, retain full-population counts with bounded detail, expose identity UUIDs only on explicit read, include aggregate impact counts in transition webhooks, and require all known violating cohorts to recover before closing an incident.
- **Why:** Aggregate route health can hide a sustained failure isolated to a customer. Operators need to understand the blast radius and verify that customers affected during an incident recover without exposing identity data in routine reads or fan-out notifications.
- **Consequences:** Configuration changes increment the monitor revision and supersede an active incident. Cohorts come from tenant/consumer IDs captured at request time and are never resolved to current names. Reports compute observed, violated, unknown, missing and attribution totals over the full selected population before capping detail at five cohorts per route and one hundred violating IDs per route. Opening incidents can save request examples scoped to a displayed violating cohort, including when aggregate budgets pass; the existing three-entry evidence cap applies. The durable recovery inventory has a 256 KiB ceiling and is cleared on recovery or configuration replacement. When more than one hundred violating identities are observed for a route, the inventory is marked incomplete and the incident does not auto-recover. Routine report/history reads redact UUIDs; `customer_details=true` is an explicit read-time projection. Webhooks contain aggregate observed/violated identity counts only. Customer-level sparse evidence or incomplete attribution is unknown, never healthy.
- **Rejected alternatives:** Reusing aggregate budgets alone would leave isolated customer failures invisible. Returning every identity would make reads, saved incidents and recovery state unbounded. Embedding names would couple historical evidence to mutable identity records and disclose unnecessary data. Closing after only the opening set recovers would ignore customers first affected later in the same incident.
