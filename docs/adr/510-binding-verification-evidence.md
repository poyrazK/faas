# ADR-510 · Durable binding verification evidence

- **Status:** accepted
- **Date:** 2026-10-02
- **Decision:** Admit the existing service and PostgreSQL canaries with a server-selected binding revision in the durable app task row. Project sanitized stage outcomes into the app binding inventory.
- **Why:** Operators need to distinguish a current successful probe from one that ran before a credential rotation, configuration change, or deployment replacement. CLI PostgreSQL selection also needs the deployment scope used by manual app tasks.
- **Consequences:** Admission atomically stores the task artifact, deployment scope, and verification pin. The revision includes public binding configuration, internal binding identity, credential generation where applicable, and the app runtime configuration change stamp; it excludes credentials. The latest admitted task per binding and scope wins, so an older task finishing later cannot replace newer evidence. Inventory reports mismatched revisions or deployments as `stale`, and pending, cancelled, malformed, or truncated reports as `unknown`. A pass requires successful task status, exit code zero, all expected stages passed, and no reported error. Inventory exposes only stable stage statuses and sanitized reasons, never raw task output or diagnostic details. PostgreSQL metadata and evidence retain their existing read permission boundary. Batch verification checks services and PostgreSQL bindings in the scope selected for manual tasks.
- **Limits:** Evidence describes a point-in-time check in a deployment-attached task guest. It does not prove adoption by a resident application instance, continuous availability, or reachability after an unrelated target-side change. Other binding types remain unverified. Runtime configuration changes conservatively invalidate evidence even when the changed setting is unrelated to the binding. Inventory is a best-effort read projection, not an atomic configuration snapshot.
- **CLI selection:** The CLI rejects a pass from a task admitted to a different deployment or scope than the inventory selection, and records the actual task scope in batch results. Task admission still uses the existing server-selected live deployment contract.
- **Rejected alternatives:** A second executor and verification results table would duplicate durable app task execution and lifecycle handling. Saving a success by environment key alone would survive binding recreation or rotation incorrectly. Ordering by completion time would let delayed old probes replace newer evidence. Returning raw probe details would widen metadata permissions to task output and increase the risk of exposing private data.
