# ADR-20261019072523: Managed PostgreSQL bindings in candidate binding qualification

- **Status:** accepted
- **Date:** 2026-10-19
- **Related:** ADR-1646, ADR-1645, ADR-1370, ADR-1347
- **Problem:** ADR-1646 blocks enforced activation of a managed GitOps graph when any member has a managed PostgreSQL binding. Most GitOps applications have one, and the canonical starter has both a runtime and a migration binding, so enforcement currently excludes ordinary database-backed applications.
- **Constraint:** Qualification candidates run with the `QualificationOnly` network policy: only the node-local service proxy and pinned DNS are reachable, and the forward chain drops everything else. A candidate cannot reach its database, so the ordinary guest probe (environment, configuration, connection, query) cannot run from it. This change keeps that isolation; candidates still never touch production data before activation.
- **Decision:** Before graph activation, apid verifies the exact sealed credential each enforced candidate receives, from the control plane, and records an immutable receipt per request attempt and binding. The activation authority (SQL deadline function and the Go mirror) requires a current receipt for every non-deleted PostgreSQL binding of every candidate. `environment_binding_catalog_supported` no longer excludes PostgreSQL bindings; Data API and Auth bindings stay blocked through the new requirement.
- **Credential check:** apid decrypts the app secret holding the binding's environment key, requires its envelope fingerprint to match the stored value hash and its managed reference and generation to match the binding, then runs the existing read-only `credentialprobe` access check with the binding's access and the database's PostgreSQL major. This proves TLS authentication to the bound database and role, the expected privileges and no elevated role. It writes no customer data. Connection strings and driver errors never leave the verifier.
- **Receipt binding:** A receipt names the request, attempt, binding, environment key, access, credential generation and secret delivery version. Insertion requires an enforced binding context, a live qualification lease, a `ready` binding with no rotation or cutover in progress, and a matching managed app secret. Receipts are append-only; downgrade refuses to discard them.
- **Activation:** For each binding of a candidate's app and scope:
  - `read_write` and `read_only`: the candidate's captured and restored runtime inputs must contain the receipt's delivery version under the binding's scoped key, so the verified credential is the one the candidate was qualified with.
  - `migration`: release-only, as in the ordinary preflight. Runtime candidates never receive it; the existing pinned release task must succeed before a deployment primes, so a qualified candidate has already used it. The receipt still pins the current generation.
  - `data_api` and `auth`: unsupported; activation stays blocked.
  - A binding that is not `ready`, is rotating or is in a cutover, or whose generation, environment key, access or delivery version changed after the receipt, blocks activation. The receipt's age bounds authority by the policy's maximum verification age.
- **Limits:** This is credential and privilege evidence, not proof that candidate code reaches the database: isolation forbids that before activation. Post-activation canary, post-release watch and rollback remain the runtime safety net. Application acknowledgement, object storage, outbound integrations, jobs and pull queues remain blocked under enforcement. Qualification dispatch remains off until native acceptance passes.
- **Alternatives:** (1) Open candidate egress to the bound database endpoint and run the guest probe: rejected, because it lets unactivated candidate code reach production data. (2) Qualify against a disposable database branch: stronger, but needs per-attempt branch provisioning and frozen-input overrides; left for a later ADR.
- **Validation:** Portable memory and PostgreSQL tests cover runtime and migration bindings, missing and stale receipts, generation and secret-version drift, rotation, cutover, unsupported access, receipt immutability and the migration round trip. apid tests cover verification success, fingerprint mismatch and probe failure without leaking connection strings.
