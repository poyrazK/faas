# ADR-239: Platform-held outbound provider authorization

- **Status:** accepted; managed caller authentication superseded by [ADR-240](240-workload-identity-for-managed-outbound.md)
- **Date:** 2026-09-25
- **Decision:** An operator may configure an outbound integration with a provider `Authorization` value held only by `outboundd`. After authenticating the caller and admitting the request, `outboundd` replaces any caller-supplied `Authorization` header with that value before sending the one request to the integration's fixed HTTPS origin. Integrations without this option keep the ADR-156 application-owned header behavior.
- **Why:** A bound app should be able to use an external API without receiving the provider key as an environment variable. The existing explicit gateway already owns request boundaries, a fixed origin, attachment checks, and rate/concurrency admission; it is the appropriate place to add one credential after those checks.
- **Consequences:** `provider_authorization_env` names a variable in `outboundd`'s private environment file containing the complete header value, such as `Bearer sk_...`. The value is validated at startup, kept in process memory, and never written to the integration tables, logs, metrics, traces, or guest environment. Postgres stores only `provider_auth_mode = managed | application`. A replica lacking the credential for a managed integration returns 503 before admission and never forwards an app-supplied header. Provider key rotation currently requires updating the private environment file and restarting `outboundd`. This change provides an operator-configured primitive, not a customer-facing binding API, provider-specific permissions, or a guarantee that a provider will never echo a credential in its response. ADR-240 subsequently replaces the originally application-held gateway token with workload identity for managed integrations.
- **Rejected alternatives:** Put the provider key in `app_secrets` and inject it into the VM (the app can read it); store a plaintext provider key in Postgres (unnecessary exposure); use the app-supplied `Authorization` value when a managed value exists (lets the app bypass the configured identity); transparently intercept arbitrary HTTPS traffic (rejected by ADR-156).

The managed value is scoped by integration ID. ADR-240 replaces the original gateway-token check for managed integrations with signed workload identity and a verified app-attachment check; a rejected request never reaches the provider. The gateway continues to reject `CONNECT` and not follow redirects, so the managed header cannot be sent to a caller-selected origin through those paths. Operators must configure provider-side key scopes and the integration's fixed origin appropriately. An app with access to a binding can still invoke any provider API path under that origin unless a future path/method policy narrows it.
