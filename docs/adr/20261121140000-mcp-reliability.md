# ADR-20261121140000: Management MCP keeps plans across restarts, promotes staged deployments and fits capped clients

Date: 2026-11-21
Status: Accepted
Amends: ADR-20261121082312 (consequence: memory plans dropped on restart),
ADR-20261026152009 (toolsets), ADR-20261023115741 (capability flags)

## Context

After the production blockers (ADR-20261121082312) were fixed, five
reliability gaps remained in the management MCP server:

1. **Memory plans.** Flag, budget and reviewed (experiment, schema) plans
   lived only in memory. Every hosted bridge restart (each release) dropped
   them, and an agent that had shown a plan to a person had to plan again.
2. **Staged deployments.** A deploy staged at 0% could be promoted only with
   the deploy plan that staged it. That plan is gone after a stdio client
   restart and never existed for a deploy staged by the CLI or another
   session, so the staged revision could not be promoted through MCP.
3. **Catalog size.** `all` with writes lists about 200 tools and 370 KB of
   definitions. Some clients refuse more than 128 tools (OpenAI's function
   limit), and every listed schema costs context on every turn.
4. **Preview tools.** Log search, incidents and product analytics tools were
   listed to every account, although apid refused each call while the
   feature was off for it.
5. **Hosted details.** Windsurf's loopback callback was not admitted, and
   hosted plan output showed the bridge's loopback apid address and its
   upload directory.

## Decision

### 1. Journal memory plans

Flag, budget and reviewed plans, with their receipts and the flag attempt
marker, are journaled in the connection's encrypted state namespace
(`memory-plans/`), as release plans are. A rebuilt server restores the
unexpired plans bound to its account; OAuth cleanup keeps a headless
connection's state while one is live. None holds a secret value.

### 2. `gregale_plan_promotion`

A new read-only core tool reviews promoting an existing staged deployment:
live, at 0% traffic, in the app and scope, and the app's latest revision.
It pins the serving release and the release review (configuration hash),
like a deploy plan. `gregale_promote_deployment` applies it with the same
guards: the original serving release must still own traffic, protected
environments are refused, and production still asks a person.

### 3. Tool search above the cap

`Options.MaxListedTools` caps the listed catalog; the CLI and the hosted
bridge set it to 128. Above the cap the server lists core tools and
`gregale_find_tools`. A search ranks unlisted tools by name and description
words, adds up to 20 matches to the listing, and the SDK sends
`notifications/tools/list_changed`. When the listing would pass the cap the
oldest found tools leave it. Found tools keep every check of a listed tool.
Agent-key servers, which select toolsets per request, are not capped.

### 4. Preview tools follow the capability registry

Product analytics joins the capability catalog (`product-analytics`, child
of `feature-flags`, gated by the existing `product_analytics` flag). The
server reads `GET /v1/capabilities` once when it starts and leaves out the
tools of a capability that is hidden or disabled for the account (log
search, incidents, product analytics). A failed read hides nothing; apid
still refuses the calls.

### 5. Windsurf and hosted output

The packaged bridge admits `http://127.0.0.1/oauth/callback` on any port,
the callback Windsurf is reported to use. Hosted tool output names the
public API origin instead of the loopback address and `[hosted-upload]`
instead of the upload directory; stored plans keep the internal address
they are checked against.

## Consequences

- A release no longer discards a reviewed flag, budget or reviewed plan.
- Agents can promote any staged revision with a reviewed plan.
- Capped clients connect with every toolset; finding a tool is one extra call.
- An account sees log search, incidents and product analytics tools only
  when they work. A capability released while a connection is open appears
  on the next connection.
- The Windsurf callback comes from a third-party report, not Windsurf
  documentation; verify a real Windsurf sign-in after release.
