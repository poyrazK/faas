# ADR-170 · Container guest service discovery

- **Status:** accepted
- **Date:** 2026-09-09
- **Decision:** Each compute node runs a DNS resolver on its tenant-bridge address at UDP/TCP port 53. It answers `<slug>.svc.gregale` with that bridge address and forwards ordinary names to the host's configured resolvers. The tenant-bridge HTTP proxy accepts the same name in the Host header and keeps the existing `/v1/internal/services/<slug>[/<path>]` form for compatibility.
- **Why:** Workloads need a stable, portable service URL without learning veth addresses or carrying a platform-owned caller header. The DNS answer is node-local, while the existing proxy registry, source-IP identity map, and same-account authorization remain the access control boundary.
- **Security boundary:** DNS is reachable only through the per-netns admission for the configured bridge address and ports 53/10080. The resolver does not publish endpoint IPs or account data; unknown names resolve to the bridge and are rejected by the proxy. Host-based routing accepts one DNS label, strips no customer headers on its own, and still binds the caller to the local instance before authorization.
- **Consequences:** A guest can call `http://orders.svc.gregale:10080/health` across compute nodes using the same five-second endpoint lease and stale-target retry behavior as the explicit proxy path. The resolver file is restaged on cold boot and restore, so a VM moved to another compute node points at that node's bridge. Public DNS, public multi-port ingress, and cross-account discovery remain out of scope.
- **Rejected alternatives:** Guest-side DNS daemons would capture a stale bridge address in snapshots and add another long-lived process to every VM. Returning replica addresses from DNS would expose transport topology and bypass the node-local proxy's identity and authorization checks.
