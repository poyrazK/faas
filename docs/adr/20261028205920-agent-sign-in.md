# ADR-20261028205920: Agents sign users in strictly, with less friction

Date: 2026-10-28
Status: Accepted
Amends: ADR-20261026195952 (hosted management MCP: grant lifetime), ADR-1239 (browser authorization), ADR-032 (dashboard OAuth sign-in)
Related: ADR-035 (auth audit events), ADR-046 (OAuth boot validation)

## Context

An agent that works for someone without a Gregale account cannot deploy
until that person signs up. We considered claimable deploys: an agent deploys
with no account and the user claims the app later. We rejected them. Anonymous
deploys need a new unauthenticated write endpoint and a moderated pool of
unowned compute (mining, proxies, phishing), and the Free plan already gives
every verified account one app. Sign-in stays strict: no deploy without an
account.

What made sign-in costly was friction, not the rule. A new user reaching
Gregale through an agent's link took this path:

1. The hosted MCP consent page links to the console approval page
   (`/cli-auth?code=MCP…`) in a new tab.
2. Signed out, apid sends them to `/login?next=/cli-auth?code=…`.
3. "Continue with GitHub" (or Google) creates a verified Free account, but the
   link dropped `next`, so the callback landed on the dashboard root and the
   approval was lost.
4. After approving, they returned to the first tab and clicked "I authorized"
   by hand.
5. The connection's `mcp-login` key lived 8 hours, so a long-running agent was
   signed out overnight.

GitHub and Google sign-ups also skipped the per-address daily sign-up cap that
password sign-ups pass through.

## Decision

### 1. Social sign-in returns to where it started

`/login` passes its validated `next` to "Continue with GitHub/Google". The
redirect handlers keep it in a short-lived host-only flow cookie beside the
OAuth state, and the callback redirects there after sign-in, validated again
by the existing safe-path check (`dashboardMFANext`: the dashboard or
`/cli-auth`, same origin only). Without `next`, sign-in lands where it did
before.

### 2. One tab for hosted MCP consent

The hosted bridge opens the approval page in the same tab and adds
`return=mcp` to its link. After the user approves an MCP code that carries
it, apid redirects the browser to the platform's own continue URL,
`https://api.<platform domain>/mcp/oauth/continue`, which apid derives from
its configuration and never from the request. That page finds the flow by its
`__Host-gregale-mcp-flow` cookie, exchanges the approved code and shows the
account review. The user never returns to another tab.

The redirect target is fixed, so `return=mcp` cannot redirect anywhere else. A
code from a self-hosted bridge keeps the two-tab flow. A continue without a
matching flow cookie shows "start again from your agent".

### 3. Connections slide: 7 days idle, 30 days at most

An `mcp-login` key is created for 7 days instead of 8 hours, and it slides
while used. apid already stamps `last_used_at` on each authenticated use of
a key, debounced to once every 30 seconds and off the request path. For an
active, non-admin `mcp-login` key, that same update also sets
`expires_at = greatest(expires_at, least(now + 7 days, created_at + 30 days))`.
There is no renewal endpoint and no new public API. The bridge's key is only
ever used by the bridge, and the bridge checks it with apid on every request,
so a connection in use keeps its key alive.

A connection unused for 7 days ends, and every connection ends 30 days after
consent; the user then consents again. Revocation (account API keys page,
`gregale mcp connection revoke`, token revocation) still ends it at once. The
values live in `pkg/api/limits.go` (`MCPLoginKeyIdle`, `MCPLoginKeyMaxAge`).

The bridge's grant mirrors the same bound after each verified request. Since
apid verifies the key on every request, the mirror only limits the bridge's
tokens; it can never extend access. A bridge or apid on the previous release
keeps 8-hour connections until both are updated.

### 4. Every sign-up passes the network cap

GitHub and Google account creation goes through the same per-address and
per-network daily cap as password sign-up.

### 5. Measure agent-driven sign-ups

- `apid_signups_total{method, source}`: method is `password`, `magic_link`,
  `google` or `github`; source is `agent` when the sign-up continued to an
  MCP approval, `cli` for a CLI approval, else `direct`.
- An `auth.signup` audit event with the same method and source on the new
  account.
- `gregale_management_mcp_consent_total{step}` on the bridge: `started`,
  `sign_in_started`, `signed_in`, `approved`, `denied`. No account labels.

Together they show where agent-driven sign-ups drop off. We revisit
anything anonymous only if they show sign-up itself is what loses people.

## Consequences

- A new user goes from the agent's link to a connected agent in one tab, with
  GitHub or Google sign-up in the middle.
- An agent connection now holds a credential for up to 30 days instead of 8
  hours, renewed only while used. Revocation is unchanged.
- Email sign-up starts on the website, which does not carry `next`; that path
  still lands on the dashboard. Carrying it is a website change.
- Agent consent stays a human decision. Nothing here lets an agent create an
  account.

## Alternatives considered

- **A renewal endpoint** (`POST /v1/keys/current/renew`) the bridge calls
  hourly. Rejected: it adds a customer-visible API that only makes sense for
  one kind of key, with its spec, SDK methods and generated SDKs, for what the
  existing per-use touch already does.

## Not included

- Claimable or anonymous deploys.
- Agent-created accounts.
- Longer connections for self-hosted bridges with pasted API keys: they keep
  their key's own expiry.
