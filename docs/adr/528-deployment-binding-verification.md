# ADR-528 · Deployment selection for bindings verification

- **Status:** accepted
- **Date:** 2026-10-02
- **Decision:** Add `--deployment ID|vN` to `bindings verify` and `bindings check`. API inventory accepts `deployment_id`; reserved service, PostgreSQL and object-storage probes accept `verification_deployment_id` in task admission. Resolve revision handles within the specified app. Require an app-owned materialized live deployment, including a candidate at zero traffic.
- **Why:** Default manual tasks prefer a serving deployment. During rollout, a passing probe from the serving revision cannot establish candidate connectivity. Evidence must remain independent for each deployment, binding and scope, and the newest admission wins even if an older probe completes later.
- **Authorization and admission:** Preserve app/account ownership and existing task-write and binding-read permissions. Missing or foreign targets return 404, unavailable artifacts or non-live targets return 409, malformed selectors return 422. An explicit task target must acquire a server-generated binding pin. Only the three reserved verification commands may opt in; shell commands, generic tasks and service smoke tasks retain ADR-230 selection. Exclusive-operation admission rejects the selector explicitly because that dispatcher does not create verification pins. Validate live status and capture artifact identity atomically in the store. PostgreSQL takes a share lock on the deployment while inserting the task; MemStore holds its lock.
- **Projection:** Explicit inventory returns only evidence for the requested deployment. Default inventory prefers its selected deployment's evidence and retains prior-deployment stale evidence only if that deployment has no probe for a binding. Existing calls without a selection retain their store behavior. A partial deployment index supports exact evidence lookup; rollback drops only that index and preserves task history and all pins.
- **Compatibility:** Inventory echoes `requested_deployment_id`, separately from actual verification deployment and scope. The CLI requires both confirmations before admitting explicit probes and validates deployment/scope on admission and polling receipts. A mismatched admission triggers bounded cancellation and cannot pass. Check reports the expected deployment and blocks ignored selectors or another deployment's evidence. Both supported UUID spellings identify the same deployment. Omitting the option preserves current selection and command behavior.
- **Policy and limits:** ADR-527 age, readiness, rotation and runtime checks still apply. `--scope` asserts the selected deployment's scope. Runtime evaluation remains conservative across all residents in that scope, including superseded deployments. A zero-resident candidate can pass with the existing adoption warning. Probes observe the deployment artifact with current scoped configuration; they do not provide an immutable configuration snapshot, prove resident credential adoption or application readiness, or fence traffic promotion against later changes. Promotion integration requires a separate concurrency design.
- **Validation:** Cover all three probe families with serving-pass/candidate-fail regressions, exact/default evidence selection and late completions in MemStore and PostgreSQL, scoped targets, unavailable/foreign targets, live-status changes during admission, older servers, UUID/revision CLI resolution and migration rollback retention. Regenerate the OpenAPI-derived Node and Python clients and mirror the Go request/client contract.
