# ADR-262 · Durable duration waits in declarative workflows

- **Status:** proposed
- **Date:** 2026-09-25
- **Decision:** Add `wait_for_duration` as a fourth, mutually exclusive workflow step target. It parks the run without dispatching a VM, records the step's first activation in `workflow_steps.started_at`, and schedules the next wake at that time plus the requested duration. Both records change atomically. A later unrelated event can wake the run for evaluation but cannot reset or shorten the timer. Parallel waits schedule the earliest deadline. The existing `awaiting_event` status is reused for wire and schema compatibility in this release.
- **Why:** ADR-081's event wait and delayed tasks do not let a workflow pause between two named steps for a fixed period. Applications otherwise maintain a cron, polling row, or delayed-task callback just to continue an order flow days later.
- **Consequences:** Duration waits accept fixed intervals from 1 second to the plan's existing 7-day `WorkflowMaxWaitDays` cap; `d` means exactly 24 hours. `input`, `method`, `timeout`, `on_timeout`, and `retry` do not apply to a timer. The step's `started_at` and the run's `scheduled_for` remain visible through existing workflow APIs; first parking emits `app.workflow.awaiting_timer`. No new migration is needed because `started_at`, `scheduled_for`, and `awaiting_event` already exist. The orchestrator must commit activation and scheduling in one state-store operation, and the Postgres implementation must lock the run before its step to match cancellation.
- **Rejected alternatives:** A long sleep inside a handler would hold compute; scheduling a separate delayed task would disconnect the workflow DAG; anchoring at run creation would incorrectly include prior step execution; anchoring only in memory would reset on scheduler restart; a new `awaiting_timer` status would require a schema and SDK rollout for no immediate behavioral benefit.

This is an additive extension to ADR-081, not deterministic code replay. A workflow remains a declarative DAG of separately invoked handlers. The current `wait_for_event` plus authenticated event API can be used to resume after an application-verified webhook, but this ADR does not create public callback tokens or a `waitForWebhook()` SDK method. `waitUntil(condition)` would need an event-producing condition source rather than database polling. A code-as-workflow SDK needs a separate decision covering checkpoint records, pinned deployment artifacts, deterministic replay, side-effect idempotency, and one-year lifecycle/retention before it can claim AWS Lambda durable-function parity.
