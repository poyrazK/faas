# ADR-284 · Safe object-storage binding rotation

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** Rotate a managed S3 compute binding by atomically replacing its current credential and two sealed app secrets while staging the previous credential as a hidden active row. After that transaction commits, stamp the app's runtime-config change once using an idempotent stage marker. Invalidate snapshots at that stamp and enqueue a durable rolling refresh with a stable wake ID. Revoke the staged credential only after the scheduler has booted replacements and drained old instances. A retry of a pending rotation reuses its wake ID and new key. An undeployed app with no resident instances retires the previous key immediately.
- **Why:** Immediate key revocation breaks workloads still running with the old environment. The former sequence could also replace a key and then fail partway through writing six secrets, leaving the binding and app environment inconsistent.
- **Consequences:** The credential table gains a rotation-parent reference, wake ID, and one-time stamp marker. Staged rows resolve S3 requests and participate in key resealing, but are hidden from inventories and quota counts. Only the two changing app secrets are updated. An incomplete refresh leaves both generations valid and the durable event replayable once queued; a failed enqueue can be retried through the rotate endpoint. Explicit binding revocation disables both. Rotation responses and binding lists expose `rotation_pending` while the overlap remains. Retired rows remain as revoked credential records.
- **Rejected alternatives:** Immediate revocation can interrupt live traffic. A fixed grace timer cannot prove old instances have drained. Writing each secret in a separate transaction can expose a mixed generation. Recreating the binding changes its ID and managed secret ownership without solving delivery timing.
