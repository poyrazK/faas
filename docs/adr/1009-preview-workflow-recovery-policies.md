# 942: Preview workflow recovery policies

Saved response plans provide fenced recovery actions, but operators still have to select each target. Apps can now opt into a preview policy that prepares plans from retained native recovery evidence while preserving explicit application.

Each app has at most one policy, disabled by default. Configuration uses an expected version and records the authenticated actor. Only `preview` mode is accepted. Policies filter explicit workflow names, saved failures, stalled executions or advisory deadline overruns. Failure-status filters (`failed` and `dead`) apply to saved failures. A missing failure filter matches either. Native retry preflight and cancellation eligibility checks are reused; operation-owned, changed or unproven generations are refused. Capacity-only retry waits may be prepared for later admission.

The scheduler evaluates enabled policies in bounded batches: ten policies per recovery poll, five retained native jobs per policy, with a one-minute delay and an identifier cursor that cycles through retained jobs. These bounds mean review coverage may lag on large backlogs. Policy settings and original target generations are frozen in immutable reviews. The evaluator only writes reviews and prepared plans; it never cancels runs or creates recovery child jobs. Existing generation checks run again when an exported plan is previewed or applied.

A policy limits the absolute resume count, the number of prepared actions in a sliding hour, and the app-wide cooldown between prepared plans. Default settings are three total resumes, ten prepared actions per hour and a five-minute cooldown. These are preparation budgets, not enforcement of manually submitted work. Up to 100 prepared actions per hour and a 60-second minimum cooldown are accepted. A plan contains at most 25 unique targets. Preparation consumes budget even if the operator never applies the plan.

Preparation of an action is deduplicated by app, run, admitted generation and action kind across parent jobs and policy versions. Identical decision sets under the same policy version and parent job are recorded once using a stable fingerprint. Reviews explain prepared targets, earlier preparation, resume limits, cooldown, budget pressure and preflight refusals. Each review retains the full policy snapshot. At most 1000 reviews are retained per app; reaching the limit stops preparation and exposes `review_limit` status. Reviews and target receipts cascade with parent-job retention, freeing capacity. Deduplication evidence therefore has the same retention boundary as recovery jobs.

PostgreSQL serializes evaluation using a locked policy row and commits reviews, target receipts, budgets and cursor advancement together. Memory storage stages writes under its mutex and mirrors account scoping and immutable snapshots. Policy updates race safely with evaluation through version checks and row locking. Configuration changes reset scanning; existing reviews remain unchanged. Disabling stops future preparation and leaves reviewed plans available for explicit use.

Read-only review endpoints let Gregale list decisions and export a prepared plan. Export uses exclusive private file creation and validates app, parent and action identity through the existing response-plan format. Existing preview, apply and status commands provide reconciliation. Policy evaluation failure does not prevent execution attention or completion notification processing.

Migration rollback refuses to discard retained policies or reviews. No new scheduler execution path or automatic-remediation mode is enabled by this change.
