# ADR-20261107180000: One config file — gregale.yaml is canonical

Date: 2026-11-07
Status: Accepted (slice 1 built)
Amends: ADR-20261025093331 (project config and whole-project previews)
Related: ADR-20261104221217 (service gregale.yaml settings on project deploys),
ADR-20261106105015 (gregale.yaml creates what it binds)

## Context

A repository can describe what Gregale should run in four files:

| File | What it holds today | Committed |
|---|---|---|
| `gregale.yaml` (also `.yml`, legacy event `gregale.toml`) | an app's manifest; in a multi-service root, project-wide `databases:` and `buckets:` (ADR-20261106105015) | yes |
| `.gregale/project.yaml` | project-wide service policy, per-service visibility and `depends_on` (ADR-20261025093331) | yes |
| `compose.yaml` / `docker-compose.yml` | services, builds, ports, environment, `x-gregale-*` extensions | yes |
| `.gregale/project.json` | which remote project, app and environment this checkout targets (written by `gregale link`) | per checkout |

The ChronoLake field report hit four findings (2, 10, 25, 34) where these
sources and their precedence disagreed or surprised the user. Fixing each
finding separately keeps the cause. The owner decided (2026-11-07) that
`gregale.yaml` is the only canonical config file and the others become
import-only.

## Decision

### End state

- **`gregale.yaml` at the repository root is the one file that declares the
  project.** Project-wide settings live in its `project:` block; resources in
  `databases:` and `buckets:`; a single-service repository's app settings at
  the top level, as today. A service directory's own `gregale.yaml` keeps
  that service's app settings (ADR-20261104221217).
- **`.gregale/project.yaml` is retired** into the `project:` block (this
  slice).
- **Compose is an input, not a source of truth.** Gregale keeps reading a
  Compose file so an existing repository deploys unchanged, but everything
  Gregale-specific moves to `gregale.yaml`, and `gregale project import` will
  write a Compose project's services into it (slice 2). Until then Compose's
  `x-gregale-*` keys keep working, and they still win over the `project:`
  block where both set a value, as before.
- **`.gregale/project.json` is local link state, not configuration.** It
  names the remote target of one checkout, like a Git remote, and does not
  describe resources. It stays out of the resource model (slice 3 decides
  whether a committed default target belongs in `gregale.yaml`).
- **`gregale.toml`** stays readable for event-enabled manifests; new
  features are YAML-only.

### Slice 1 (this change)

1. **Schema.** `pkg/projectconfig` holds the project block's schema and
   validation, shared by the manifest parser and the scanner. Its fields are
   exactly those of `.gregale/project.yaml`: `service_policy` and
   `services.<name>.{service_policy, visibility, depends_on}`.
2. **Manifest.** `gregale.yaml` accepts a `project:` key, decoded strictly
   and validated with the rest of the manifest. It never reaches an app's
   deployment.
3. **Scanner.** `reposcan` reads the root `gregale.yaml` (or `.yml`)
   `project:` block. It still reads `.gregale/project.yaml`, and adds a scan
   warning that names `gregale project import`. Settings in both places fail
   the scan with an error that names both. A root `gregale.yaml` holding
   only `project:` is not a service.
4. **`gregale project import [<dir>] [--dry-run]`** (local only) appends the
   legacy file to the root `gregale.yaml` as a `project:` block, indenting
   its lines so its comments carry over, and deletes the legacy file. It
   edits text instead of re-encoding YAML, so the rest of `gregale.yaml` is
   unchanged byte for byte. It writes nothing unless the new block decodes
   to exactly the legacy settings. It refuses when `gregale.yaml` already has
   a `project:` block, and when the root manifest is `gregale.toml`.

### Later slices

- **Slice 2: Compose import.** `gregale project import` also writes a
  Compose project's services (build context, image, ports, Gregale
  extensions) into `project.services`, and the scanner prefers that
  declaration over the Compose file. Needs per-service build and port fields
  in the block; designed separately.
- **Slice 3: link state.** Whether `gregale.yaml` may name a default
  project and app, leaving `.gregale/project.json` with only per-developer
  choices such as the environment.
- **`gregale config explain <key>`.** Shows a setting's effective value and
  the file and layer it came from, once Compose import narrows the sources.

## Consequences

- Repositories with `.gregale/project.yaml` deploy as before, with a
  warning in the plan.
- A `gregale.yaml` with a `project:` key needs a CLI and apid that include
  this change. An older apid's strict parser rejects the key on a deploy
  that sends the root manifest, so release apid before documenting the block
  widely. The CLI and apid ship from the same release train.
- `project.json` is unaffected.

## Validation

- `pkg/reposcan`: the block applies like the legacy file; the legacy file
  still applies with the deprecation warning; both at once are refused;
  strict validation of keys, values and service names; a project-only root
  manifest is not a service.
- `pkg/gregalemanifest`: the strict parser accepts and validates the block.
- `cmd/gregale`: import appends without changing the existing manifest,
  carries comments, creates a missing manifest, writes nothing on
  `--dry-run`, and refuses an existing block.

## Rejected alternatives

- **Re-encode `gregale.yaml` with the merged block.** yaml.v3 reformats
  quoting, indentation and comment placement, so a migration would rewrite
  lines the user never asked to change.
- **Keep both files with a precedence rule.** Two files that can disagree,
  with a rule users must remember, is the problem this ADR removes.
- **Move the link state into `gregale.yaml` now.** It differs per checkout
  (environment, selected app) and would create commit noise and conflicts;
  slice 3 decides what, if anything, is shared.
