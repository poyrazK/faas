# ADR-1373: Async Python object-storage bindings

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Python's synchronous storage helper rejects async factories and retires on threads. The async PostgreSQL runtime/coordinator already provide loop ownership, cancellation fences and lease draining, but applications combining database and async S3 clients still need custom storage adoption and stream cleanup.
- **Decision:** Extract PostgreSQL's existing async owned-resource engine into `_async_binding_client_runtime` and add `AsyncObjectStorageBinding`/`AsyncObjectStorageLease`. Preserve PostgreSQL public APIs, error types and lifecycle behavior. Reuse synchronous storage configuration parsing and its immutable, credential-redacted config. Keep S3/database/framework dependencies out of SDK core. Preserve both new handwritten modules through regeneration and synchronize the PostgreSQL starter's complete updated import closure.
- **Adoption:** Require async fresh-client construction, application-supplied validation and retirement hooks. The validator receives the candidate, captured bucket and cancellation token, checks an appropriate operation, closes its body and returns None. All callbacks run on the same owning loop. New acquisition fails closed during adoption/failure/revocation; invalidation is synchronous and fences queued/late publication. Reject tracked aliases without closing earlier borrowers. Factories own partial allocations until return. Retirement runs once after final release, without retries; failures stay sticky and sanitized.
- **Streams/cancellation:** Leases capture client plus bucket and remain held through actual upload/download body closure, including errors and disconnects. Cancellation returns promptly while admitted callbacks/late results stay owned until cleanup. Never extend server credential validity or replay operations. Stop admission/reloads and drain each binding before loop shutdown; timeout/cancellation of a retirement wait never forcibly closes leased resources or cancels their cleanup.
- **Mixed resources:** Register storage and PostgreSQL consumers with one async coordinator and one atomic snapshot. ACK only after every consumer validates; failure invalidates them all. This is coordinated application adoption evidence, not atomic cross-resource visibility or a distributed transaction. Cancellation cannot retract an ACK already sent or undo a completed operation.
- **Example:** Provide a FastAPI/aiobotocore download service with explicit SigV4 credentials, path-style/checksum settings, finite I/O budgets and one total driver attempt. Validate an application-provisioned readiness object with HeadObject. Own HTTP response tasks before resource acquisition, handle cancellation before headers/body iteration, and close the pinned driver's streaming body before lease release. Keep admitted streams leased through graceful shutdown; drain every additionally registered binding. Provider errors and truncated-stream failures are sanitized without replay.
- **Validation:** Keep the existing PostgreSQL lifecycle suite and materialized starter checks. Cover storage configuration/metadata capture, leases/copies, revoked/failed/cancelled adoption, aliases, cleanup errors and mixed-consumer ordering. Exercise real aiobotocore SigV4 against a controlled S3 fixture with held/truncated responses, rotation, native/disconnect cancellation, late responses and graceful drain. Opt-in TLS/SCRAM PostgreSQL plus signed S3 acceptance holds one real write and download across replacement, rejects stale credentials, invalidates both resources on a storage failure, proves one committed row, cancels blocked validation, recovers and drains all resources. Wire dependencies and acceptance into existing CI gates; verify wheel packaging and generator preservation. No server API, quota, schema or VM lifecycle changes; portable fixtures do not constitute provider or native VM qualification.
