# ADR-20261111114059: Agent budgets

Date: 2026-11-11
Status: Accepted
Related: ADR-20261104140058 (agent approvals), ADR-20261107220000 (agent
activity log), ADR-1162 (the account's hard spend cap),
ADR-20261107192333 (overage rate)

## Context

An agent key can raise what its account pays every month without anyone
noticing: it sets `min_instances`, adds schedule windows to a scaling
policy, raises RAM on an always-on app, or prewarms instances. The account
spend cap (ADR-1162) bounds the whole account, not one agent, and it acts by
parking apps once the money is gone. The approval gate asks a person about
deletes, production changes, credentials and billing, but a scale-up of a
preview app passes through it, and a person approving a production change
does not see what it costs.

Usage is metered per app, not per key, so "what an agent spent" needs a
definition that can be checked before a change happens.

## Decision

1. **Measure committed cost.** A change is priced by how much it raises the
   account's *standing* monthly cost: the always-on capacity it pays for
   whether or not traffic arrives. For an app that is

   `floor × (ram_mb + 8) MB × 730 h × api.OverageMillicentsPerGBHour`

   where `floor` is the largest number of instances its settings keep warm:
   `min_instances`, the scaling policy's `min_instances`, or the highest
   schedule window (`MaxReachableMinInstances`, the same bound the plan gate
   uses). Prices use the overage rate and ignore the plan's included
   GB-hours, so the estimate never understates. A prewarm is a one-off
   charge for its instances, RAM and duration. Traffic-driven usage is not
   committed cost and is not counted; the account spend cap still bounds it.

2. **A monthly budget per agent key.** Each agent or `mcp-login` key spends
   against a budget in cents per UTC month. A change's added cost
   (`after − before`, when positive) is recorded in
   `agent_budget_spend (key_id, month)`; a change that lowers cost records
   nothing, so scaling up and down again cannot launder the budget. Spend
   resets on the first of each month.

3. **Over budget, a person decides.** When a change would take the key past
   its budget, apid answers `428 approval_required` with a review link, as
   for other approvals, in the new category `budget`. The review page shows
   the change's added monthly cost and the key's budget and spend. An
   approval allows that exact request once, and its cost is still recorded.
   Budget approval is not a category a key can opt out of: it is how the
   budget is enforced. Any approval of the exact request (a production
   approval, say) also counts as consent to its cost, because the person saw
   the same request.

4. **Who sets it.**
   - The person connecting the agent sets the key's budget:
     `gregale key create --budget USD`, `gregale mcp connection budget <id>
     --set USD | --unlimited | --default`.
   - An organization may set `max_agent_budget_cents` in its agent policy
     (`gregale org agent policy set --max-budget USD`). The lower of the key's
     budget and the organization's ceiling applies; `--unlimited` on a key
     cannot exceed the organization's ceiling.
   - A key with no budget of its own uses its plan's default
     (`Plan.AgentBudgetDefaultCents`): half the plan's default spend cap, so
     Free $0, Hobby $5, Pro $25, Scale $75 a month.
   An agent key cannot change budgets: the routes need an admin credential.

5. **Where it is checked.** The handlers that change standing capacity call
   one middleware helper with the change's added cost after validation and
   before they write. Slice 1 covers `PATCH /v1/apps/{slug}`,
   `POST /v1/apps/{slug}/scaling` and `POST /v1/apps/{slug}/prewarm`. Creating
   an app commits nothing: a new app has no floor until one of these sets it.
   Requests from other credentials are not affected.

6. **Shown** in `GET /v1/agent-connections/{id}/budget` and
   `gregale mcp connection budget <id>` (budget, where it comes from, spent
   this month), and on the review page and in approval notifications of a
   `budget` request (the change's added monthly cost).

## Slices

1. Cost model, storage, the three app routes above, key and org settings,
   CLI, review page. (This ADR.)
2. Deployment manifests: service and worker replica minimums and
   deployment `min_instances`.
3. Project environment config and workload policies; managed Postgres and
   other resources with a standing price.

## Consequences

- An agent cannot quietly add always-on spend beyond its budget; a person
  sees the cost when it would.
- Two concurrent requests of one key can each pass a check that only one of
  them would have passed; the overshoot is bounded by one request's cost.
  Spend is recorded after the write succeeds.
- Changes outside slice 1 routes are not priced until their slice lands; the
  account spend cap still bounds them.
- New tables and columns are additive; the previous release ignores them and
  treats `budget` approvals as an unknown category it never creates.
