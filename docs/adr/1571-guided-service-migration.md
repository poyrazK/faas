# ADR-1571: Guided migration of an existing service

- **Status:** Accepted
- **Date:** 2026-10-17
- **Context:** Repository scanning and project apply already support service selection, but the browser discards connected source when handing off to archive import. Project CLI deploys configure their secret bundle after apply has already enqueued builds, and even after an optional readiness wait.
- **Decision:** Add request-only per-workload initial secrets to project apply. Validate exact selected names, secret write authority, per-value limits and aggregate cross-scope quotas. Use the existing sealing, value fingerprint, snapshot invalidation and configuration notification paths. Configure every selected target before enqueuing any deployment. A configuration failure starts no builds; apps and any completed configuration remain available for correction. This is not a new transaction guarantee across independent secret writes.
- **Reviewed source:** Add `POST /v1/projects/apply-plan` over the existing account-owned, bounded, one-hour source cache. Rebuild the normal multipart request using an in-memory pipe; initial plaintext values never enter temporary files, source caches, responses or audit data. Apply repeats normal source identity, project ownership, environment approval, selection and admission checks. Expired sources require another scan rather than silently resolving a mutable ref again.
- **Manual migration:** The connected scan's opt-in `migration` flag clears unattended GitHub project binding and suppresses schedules and async routes. The browser selects one HTTP service while the existing database, storage, siblings and production domain remain under the customer's control. Existing project and ordinary scan semantics are preserved.
- **Requirements:** Expose names from the CLI's `.gregale/required-secrets.json` array, with a workload-local declaration overriding the root declaration. Detected environment names remain advisory. Neither source analysis nor plan admission claims to prove successful runtime dependency access.
- **Browser recovery:** Configuration values remain in component memory and are submitted outside query/mutation caches. Only bounded app/repository/ref/deployment pointers enter the existing recovery URL. Persist a submitting pointer before mutation; reconcile transport failures through the saved app rather than automatically creating or applying again. Known configuration failures allow explicit correction. Accepted deployments use existing lifecycle, logs and immutable retry surfaces.
- **Validation:** Sealing precedes deployment creation; unselected and unauthorized configuration cannot mutate apps; metadata quota failures precede all writes; errors never echo values; manual scans cannot enable GitHub push deploys or triggers; the browser handles selected-service quota rescue, declared requirements, expired scans, configuration correction and uncertain responses.
