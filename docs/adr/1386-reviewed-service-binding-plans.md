# ADR-1386: Reviewed service binding plans

- **Date:** 2026-10-16
- **Status:** accepted
- **Context:** Service binding previews are snapshots. Concurrent changes to replacement lists or reliability settings can make a subsequent update differ from what the operator reviewed. A CLI-only comparison leaves a race between comparison and mutation.
- **Decision:** Add `configure --plan-out PATH` and `bindings service apply APP --plan PATH`. Private no-overwrite plans contain the normalized patch, review, API endpoint, account/app identities, a version and checksum. App responses expose an opaque versioned service-settings fingerprint; PATCH accepts an optional expected fingerprint for app-level service-only updates. Existing unguarded requests remain compatible.
- **Atomic enforcement:** Validate the expected fingerprint under the app row lock/memory mutex before any write, production-spec synchronization, activity callback or outbox insertion. Both ordinary and activity-aware PostgreSQL update paths enforce it. Mismatch returns a service-plan conflict mapped to HTTP 409. Include account/app identity, slug, source ownership and all six service settings in the fingerprint, preserving deny-all versus unrestricted semantics. Hashing is content-based and has no expiry or history guarantee.
- **Manifest preservation:** The API prepares manifests before acquiring the store lock. Guarded store updates therefore merge only service settings into the locked current manifest and regenerate platform-owned service URL discovery values, preserving unrelated manifest and environment edits. Requests mixing guarded service updates with unrelated settings or named environments are rejected.
- **Client behavior:** Reject changed plan files, wrong account/endpoint/app identity, stale fingerprints and servers without fingerprint support. Never replan or retry without the precondition. A plan checksum is an integrity check, not a signature or authorization capability. All normal API ownership/source-management checks remain authoritative.
- **Validation:** In-memory/PostgreSQL races require one winner for competing plans, no mutation or activity callback from stale requests, preservation of unrelated concurrent manifest values, and rejection of stale target removal after a concurrent reliability edit. API tests cover guarded success, conflict, mixed-field rejection and explicit null resets. CLI tests cover private no-overwrite publication, exact guarded PATCH, stale/wrong-target/modified plans, old servers and an HTTP conflict after the client pre-read. Update OpenAPI, embedded schema, SDK models, help and generated reference together.
