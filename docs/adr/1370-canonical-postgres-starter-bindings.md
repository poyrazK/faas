# ADR-1370: Canonical PostgreSQL starter bindings

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** The SDK can validate and drain PostgreSQL pool replacements, but the REST starter captures startup environment credentials and the secret-reload starter duplicates an older pool/reload protocol. Generated apps should obtain the same lifecycle guarantees as SDK users without requiring a separately published SDK package.
- **Decision:** Both PostgreSQL starters use canonical vendored `SecretReloadCoordinator` and `PostgresPoolBinding` modules and a shared database adapter. The adapter source lives in `rest-api-postgres/database.js` and is synchronized to `secret-reload-node`. Generate complete static runtime import closures for all binding starters, reject obsolete/unknown runtime files, and retain the old synchronization script as a compatibility entrypoint. Isolated packaging tests and the existing drift gate cover all generated copies.
- **Startup and adoption:** Docker images opt into SIGHUP and required reload readiness. Install the coordinator before asynchronous startup; read one atomic envelope, validate a fresh pool through a bounded read-only readiness transaction, then publish and ACK. The REST validator reads the existing notes schema; the focused secret starter uses `SELECT 1`. Failed adoption/revocation blocks new acquisitions while admitted transactions retain leases. Managed startup requires the complete atomic snapshot/readiness/ACK/generation contract and never falls back to environment or legacy files. The REST starter retains explicit local environment startup when no guest contract is advertised. Serving refuses migration credentials in either environment or snapshots.
- **Transactions:** Preserve certificate/hostname verification, existing pool/admission bounds, five-second SQL deadlines, transaction-local statement timeouts, active/idle error handling, and no automatic SQL/COMMIT replay. Retain each pool lease until its driver connection is released/destroyed, including a connection arriving after request cancellation. Rotation permits admitted work to finish. Shutdown stops acquisition and cancels active work before a bounded retirement wait.
- **Restore:** Preserve the REST starter's loopback/header authorization, two-second platform hook and 1.5-second application budget. Fence pending candidates, abort captured work, reread the latest atomic envelope even at the same revision, validate readiness and drain captured resources before success. Extend Node's manual coordinator `reload(signal?)` with per-attempt cancellation, including queued attempts and ACK transport. Cancellation before admission skips that attempt; after admission it invalidates consumers and fences late publication. Restore timeout keeps readiness closed and cannot later produce an applied ACK from the cancelled attempt. A successful later restore can recover. No guest, hypervisor or platform lifecycle implementation changes.
- **Compatibility:** Updated generated apps require modern guest delivery; older guests must be upgraded and apps redeployed. The focused starter's obsolete standalone secret helper is removed. Runtime/migration role separation and the separate release command remain intact. Existing deployed apps are unchanged until redeployment.
- **Validation:** Canonical coordinator cancellation and queue tests; materialized starter bootstrap, SIGHUP, ACK ordering, shutdown and late-candidate tests; schema readiness, migration isolation, late-connect lease draining, rotation/revocation and concurrent restore cancellation tests. Real TLS/SCRAM PostgreSQL acceptance materializes the CLI starter, rotates credentials while a write is blocked, rejects stale credentials, proves exactly one committed write and deferred pool retirement, then exercises a restore queued behind a blocked SIGHUP reload and subsequent recovery. Existing restore/cancellation/session-termination coverage remains required. Native microVM acceptance is separate from these portable application-hook tests.
