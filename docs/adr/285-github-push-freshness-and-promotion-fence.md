# ADR-285 · GitHub push freshness and promotion fence

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** Before fetching or reconciling a GitHub push webhook, githubd reads the current branch head with the installation token. It ignores a delivery whose `after` SHA is no longer current and retries an unavailable head lookup without changing project state. Release-tag events retain their separate immutable-tag policy. At readiness, imaged uses a store operation that atomically compares a GitHub deployment's per-app revision with all accepted deployments in the same scope. An older candidate becomes superseded instead of live. Explicit operator rollback continues to use the existing promotion operation.
- **Why:** GitHub does not guarantee webhook delivery order. The Action's head check closes a queue-time race for generated workflows, but legacy webhook pushes and parallel build completion can still apply older source or make an older build live after a newer deployment was accepted. A pre-fetch remote check plus the existing monotonic deployment revision closes those two windows without relying on commit ancestry or wall-clock timestamps.
- **Consequences:** A GitHub branch API outage delays push dispatch rather than deploying a possibly stale revision. The app row lock serializes accepted deployment creation with promotion, so the revision comparison and live cutover share one ordering boundary. A newer failed or cancelled intent still supersedes an older in-flight GitHub candidate; the last live deployment remains available until an explicit rollback or a later successful release. Manual source-ref requests are deliberate deploy intents, so their chosen SHA need not equal the current branch head, but they participate in the promotion revision order.
- **Rejected alternatives:** Delivery timestamps cannot prove current branch state after force pushes or redelivery. Comparing only commit ancestry would reject intentional rollback and require more GitHub API calls at promotion. A pre-promotion read without the app lock would race a concurrent deployment insert.
