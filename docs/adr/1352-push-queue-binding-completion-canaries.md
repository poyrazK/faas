# ADR-1352: Push queue binding handler completion canaries

- **Status:** Accepted
- **Date:** 2026-10-14
- **Context:** Queue consumer readiness proves scheduler polling, leaving delivery and handler completion unverified.
- **Decision:** Publish one explicitly consented safe message through the ordinary named push queue path. The exact live deployment declares supported logical bindings using a JSON array in its non-secret `GREGALE_QUEUE_CANARY_BINDINGS` deployment override. Its handler recognizes the `gregale_queue_canary: v1` payload and returns success only after safe test handling finishes. This declaration is customer intent; successful HTTP handling does not prove application-specific business effects.
- **Identity:** Freeze binding and consumer identity/configuration, environment identity, deployment artifacts and capability. Reuse revision-pin eligibility, normal producer queue depth and runtime capacity, claims and gateway routing. The unique invocation ID is the correlation ID. Never change traffic or select a fallback deployment.
- **Evidence:** Publication is not delivery. A claim reports `dispatching` without a confirmed delivery timestamp. Successful gateway handling on the selected deployment and durable queue acknowledgement commit evidence together. Existing attempt, replay-generation and lease fences remain authoritative. One attempt is allowed; replay never qualifies. Shared legacy bindings are limited to production/default; named environments require their scoped binding.
- **Bounds:** One active pending/dispatching canary per binding with a 1–600 second lifetime covering dispatch and evidence. Expiry, cancellation, consumer drift, disabled/replaced environments and revision-pin ineligibility invalidate evidence. Cancellation revokes evidence immediately; an in-flight handler may finish. Normal invocation retention removes the linked record. No new lifecycle controller or capacity exception.
- **Release policy:** `handler_completion` supplements healthy push consumer readiness with fresh exact-deployment evidence. Old servers reject this unknown policy value before mutation. Readiness alone retains partial coverage. Inventory is read-only; CLI verification requires `--queue-publish`, supports dry runs and pending reuse, and preserves final promotion revision/expiry fences. Invocation state, attempt, replay, pin and completion changes also invalidate the app revision under the same transaction, closing observation-to-promotion races. Migration rollback refuses to remove a selected completion requirement.
- **Validation:** Consent/capability rejection, missing/ambiguous consumers, polls without completion, wrong deployment, stale attempt, replay, cancellation, expiry, drift, atomic PostgreSQL completion, API/CLI/SDK contracts and existing readiness behavior.
