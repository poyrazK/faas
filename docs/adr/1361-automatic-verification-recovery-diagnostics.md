# ADR-1361: Automatic verification recovery diagnostics

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Server diagnostics explain blocked receipts, but runner errors and CLI failure reports still require a separate diagnostic request. CI operators need blockers and recovery guidance alongside the original failure and receipt ID.
- **Decision:** Automatically attempt a read-only app or project diagnostic GET after a runner failure. Attach typed optional diagnostics to recovery errors and CLI JSON reports, and show bounded blocker/recovery summaries in terminal output. A lookup failure never replaces the original cause, changes the exit code or makes verification pass. CLI resume delegates its initial control request to the runner so initial resume failures receive the same treatment.
- **Bounds:** Use a two-second enrichment budget, additionally bounded by the caller and confirmed original receipt deadlines. Never detach from cancellation. Skip invalid local inputs, cancelled/deadline-expired calls, local progress callback failures and explicit local stops. `SkipDiagnostics` in Go, `skipDiagnostics` in Node and `skip_diagnostics` in Python disable enrichment. Optional Go diagnostic interfaces preserve clients implementing the original runner interface alone.
- **Identity:** Request the original receipt and app or project/environment selectors. Validate response identity, timestamps, original deployment/scope/expiry and graph member selections whenever a confirmed original observation exists. Preserve partial server diagnostics (`complete=false`) as useful evidence, without treating them as authority. Reject mismatched responses. Go decoding ignores unknown properties; automatic Node/Python enrichment drops unknown fields, including nested model extras.
- **Cancellation:** Go contexts and Node abort signals cancel lookups immediately. Python async task cancellation retains `CancelledError` and `run_id`; async stop events preserve the original failure. Synchronous Python uses a daemon read observer to bound total response latency and honor stop events during a blocked read. That observer performs no callbacks or work mutations and may finish its bounded HTTP read after observation stops. CLI retains its existing explicit owned-work cleanup on interrupt/deadline, including the original receipt deadline learned by the runner.
- **Scope:** No server endpoints, schema, admissions, effect consent, receipt lifetimes or route activation change. Diagnostics remain public observations; runners never execute their suggested recovery actions. Original errors and receipt/resource identities remain recoverable. SDK errors expose app/project diagnostics in Go and a typed app-or-project `diagnostics` value in Node/Python. CLI graph reports include root and per-member diagnostics.
- **Validation:** App/graph error enrichment, incomplete responses, unavailable/forbidden lookups, response identity/selection rejection, original cause preservation, callback/local cancellation skips, cancellation in flight, lookup timeout and private-field filtering; SDK wrapper/recovery contracts; CLI JSON/plain initial resume failures and crash recovery; Go race checks, SDK suites, source synchronization and lint.
