# ADR-1205 · Dependency replacement with external durable write state

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Add a two-scenario dependency replacement suite using existing in-flight staged restart orchestration. Restart payment while the primary caller remains alive; store pending/confirmed operations in an external Postgres ledger with a per-run namespace, composite unique key, immutable canonical payload fingerprint, row locking and monotonic pending-to-confirmed transitions. Supply the runtime connection using a validated `${env.NAME}` secret reference through the existing sealed-secret API; preflight checks presence and omits values.
- **Why:** Caller-only replacement cannot prove recovery when the dependency loses its process and VM-local disk. A stable external ledger is required for meaningful pending/committed recovery checks.
- **Consequences:** Schema migration is a separate operator process. Runtime receives no migration credential and requires explicit disposable-fixture opt-in; the automatic managed developer database binding is deliberately not used to perform DDL. SQL and connection deadlines bound failures. HTTP holds happen after durable acceptance/commit and outside transactions; replacement clears the hold without recreating it for an existing operation. No failed SQL mutation is automatically retried, and database failures cannot select a local fallback ledger. Readiness and before/after assertions verify the surviving ledger; explicit replay verifies one confirmed row and conflicts. Cleanup deletes only the exact run namespace. Native verdict version 5 requires all thirteen cases, exact planned service restart evidence, independent API cleanup and independent Postgres namespace retirement. Portable acceptance uses a disposable real Postgres 16 container, a restricted runtime role, actual provider SIGKILL, concurrent writers, failed commits, schema failures and redaction. Native qualification remains separate and requires KVM plus a migrated reachable external fixture.
- **Rejected alternatives:** Persisting to the replacement VM's writable layer loses the ledger. Granting serving credentials DDL privileges conflates schema migration and runtime access. Resetting or truncating a shared fixture schema could delete another run's data. Retrying a failed COMMIT blindly can obscure an ambiguous outcome; explicit payload-bound replay reconciles it.
