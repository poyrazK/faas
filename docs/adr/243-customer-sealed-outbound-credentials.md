# ADR-243: Customer-sealed provider credentials for outbound integrations

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** An operator-provisioned managed integration declares exactly one credential source: `operator_env` (the existing default) or `customer_sealed`. An account may set, rotate, or revoke the latter's provider Authorization value through MFA-gated `apid` routes. `apid` seals it to the fleet age public recipient and stores only ciphertext in `outbound_integration_credentials`. `outboundd` alone receives the fleet private identity and decrypts the current row at request time. The application can neither read the ciphertext through the API nor obtain the plaintext through a binding.
- **Ownership:** `outboundd` remains the operator policy writer; `apid` writes only customer credential intent. The database checks account/integration ownership and source, and the gateway repeats the checks. An integration cannot silently move accounts during operator reconciliation. Changing away from `customer_sealed` purges its old credential so switching back cannot reactivate a stale key.
- **Fail-closed behavior:** A customer-sealed integration can exist and be bound before a key is configured, but outboundd returns 503 before upstream traffic until it can read, decrypt, and validate a credential. Revocation and rotation are visible to requests that read after the database commit; an already-in-flight request may still use the old value. No plaintext cache or daemon restart is involved. Workload identity, route policy, and shared admission are checked before decryption, so rejected traffic does not trigger a secret read. An admitted request with a missing key still consumes its admission token, but sends no provider call.
- **Limits:** The API accepts one bounded ASCII HTTP Authorization value, not an arbitrary header map. It does not provision the integration origin or route policy; those remain operator-owned. It does not provide transparent egress interception, cost budgets, caching, or retries. Fleet-key rotation must preserve the identity needed to decrypt existing rows or re-seal those rows before retiring the old key. Giving outboundd the shared fleet private identity expands that key's existing platform trust boundary; a dedicated outbound-only identity is future hardening.
