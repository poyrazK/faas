# ADR-239: Verified tenant-surface usage attribution

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Attribute anonymous requests on an active, verified, linked tenant-surface hostname to that platform tenant at request time. Keep these financial facts distinct from API-consumer usage, but price both sources in the same cross-app tenant statement using the app's explicit, versioned request rate card.
- **Why:** ADR-238 can bill linked consumer keys across apps, but a platform's branded customer hostname may serve requests without such a key. Those requests entered only the app's anonymous ledger, so the platform customer's consolidated usage and statement omitted them.
- **Consequences:** The authoritative hostname route supplies tenant and surface IDs; incoming identity headers cannot select either. A consumer key on that hostname must belong to the same platform tenant or is denied, including an unlinked key. Without a key, the gateway stamps the verified tenant claim for the guest and journals a single `anonymous + tenant + surface` event. The app's existing anonymous aggregate still records the request, while the tenant aggregate has an independent `surface` source dimension. Tenant usage reads and statement lines expose exactly one of `consumer_id` or `surface_id`. Surface lines use the app's existing effective rate card, remain unpriced without one, and participate in immutable revisions and late-usage adjustments. A handoff excludes overlapping claims for the same surface across different tenant periods, while same-period adjustments remain allowed. No payment collection or automatic invoice issuance is added.
- **Rejected alternatives:** Infer a tenant from the current hostname when quoting old anonymous app rows (retroactively rewrites ownership); invent an API-consumer row for each surface (conflates credential and route identities); assign the same event to both consumer and surface in a tenant statement (double bills); accept an unlinked key on a tenant hostname (lets a key bypass tenant attribution); use a request-supplied tenant header (spoofable).

The gateway's route lookup already rechecks the current surface binding and suspended state on cached routes. This ADR extends that authoritative route identity to the financial event only when no consumer key was accepted. Key-authenticated requests continue to use the linked consumer as their sole tenant-billing subject. Other anonymous app domains, independent JWT traffic without a bound tenant-surface hostname, and pre-upgrade events remain unassigned; there is no backfill. A tenant-surface hostname is an attribution boundary, not end-user authentication: publicly reachable traffic on it may become the platform customer's usage. Operators should set an explicit app rate card and review the draft before finalization and handoff.

The new outbox payload carries the immutable surface ID. A new apid receipt confirms surface-attribution support; a gateway must not acknowledge or discard a surface event when an older receiver lacks that capability. The schema adds a source kind to the tenant minute key and stores the surface on the event. Existing consumer rows default to `consumer`. Statement participation snapshots surface IDs so a later unlink does not change historical handoff checks. The existing 20,000-line statement cap, single-currency rule, and ADR-234 pre-fsync crash limitation remain. Hard tenant quotas and JWT-claim attribution are separate decisions.
