# ADR-222 · Restored processes reseed their userspace random generators before serving

- **Status:** accepted
- **Date:** 2026-09-23
- **Supersedes:** the §11 "Snapshot uniqueness" clause that left in-app RNG
  state to customers once the kernel reseed was proven.
- **Security advisory:** GHSA-24j2-p895-mwc9.

## Context

The resume hook (ADR-022, V6) reseeds the guest kernel CRNG and steps the
clock, so `/dev/urandom` and `getrandom(2)` differ across restores. A snapshot
also captures every userspace generator in the workload's memory, and the
kernel reseed does not reach them. Production showed it on 2026-09-22:

- A Node app returned the same `crypto.randomBytes`, `crypto.randomUUID()` and
  `Math.random()` for the first request after each of three wakes, while
  `/dev/urandom` read in the same handler differed each time.
- 60 concurrent requests to one app returned 31 unique UUIDs: two restored
  siblings replayed one sequence.
- A Python function repeated `random.random()` across wakes. `secrets`,
  `uuid4` and `os.urandom` stayed unique because they read the kernel on
  every call.

Session tokens, CSRF tokens, JWT IDs, idempotency keys and AES-GCM nonces
generated by customer code, plus OpenSSL's TLS randomness, could repeat across
wakes and across instances. That breaks invariant 5 (§6.2) in practice.

No configuration-only fix exists. OpenSSL refuses `SEED-SRC` as its DRBG, its
fork detection keys on the PID (which a restored process keeps), V8 exposes no
way to reseed `Math.random`, and Node has no JavaScript API that reseeds
OpenSSL.

## Decision

guest-init runs a restore reseed barrier for Node and Python workloads.

1. **Preload injection.** guest-init materializes three read-only assets under
   `/run/guest-init/rng/` and stamps the workload env with
   `NODE_OPTIONS=--require=/run/guest-init/rng/node-reseed.cjs` (appended to
   any customer value), `PYTHONPATH=/run/guest-init/rng/python:…` (prepended)
   and `GREGALE_RESEED_SOCKET`. It stamps only after the assets exist, because
   a `--require` of a missing file stops Node from starting. Function workers
   inherit the env from their runner.
2. **Registration.** Each preloaded process connects to
   `/run/guest-init/reseed.sock` (0660, the workload's group) and says
   `hello <runtime> <pid>`. The connection lives in guest memory, so it
   survives the snapshot. Python registers again in every forked child.
3. **Barrier on resume.** After the kernel reseed and clock step, and before
   the resume ACK that gates readiness, guest-init sends every registered
   process `reseed <32-byte nonce>` drawn from the reseeded kernel and waits
   up to 250 ms for `ok`.
   - **Node:** `RAND_poll()` through a 2.9 KB N-API addon, which reseeds
     OpenSSL's primary DRBG (OpenSSL 3 propagates it to every thread's child
     DRBG). Then it reseeds a xoshiro128** `Math.random` replacement with
     urandom XOR nonce, and drains Node's `randomUUID` (128-entry) and
     `randomInt` (6 KiB) caches so they refill from the reseeded OpenSSL.
   - **Python:** `random.seed()`, `ssl.RAND_add()` when `ssl` is loaded, and
     numpy's legacy global generator when numpy is loaded.
4. **Fail closed.** A registered process that answers late, answers `err`, or
   cannot load the addon fails the barrier. guest-init NACKs the resume with
   code 13, and vmmd cold-boots the instance (ADR-005), which is always safe.
   A process that exited is dropped silently.
5. **Opt-out.** `GREGALE_RESTORE_RESEED=off` in the app's env disables
   injection. The docs mark it unsafe for any app that generates secrets or
   nonces.

The addon is built from `guest/init/rngpreload/reseed.c` with
`zig cc -nostdlib`. It has no libc dependency, so one x86_64 ELF loads under
glibc and musl, and its `RAND_poll`/`napi_*` imports resolve against the node
process. The build is reproducible; `make rng-addon-check` proves the
committed binary matches the source.

## Consequences

- Node and Python apps and functions no longer replay RNG state across
  restores. Restore latency grows by one local round trip per registered
  process: microseconds for an idle event loop.
- Instances whose process cannot confirm a reseed cold-boot instead of
  restoring. `vmmd: resume hook failed (ack=13)` in the vmmd journal names
  this path.
- **Not covered:**
  - other runtimes: Go `math/rand`, Java `SecureRandom`/`Random`, Ruby, PHP;
  - Node worker threads' `Math.random`;
  - generator objects an app created before capture (`random.Random()`,
    `numpy.random.default_rng()`);
  - sidecars chrooted into their own rootfs.

  The docs list the APIs that are safe across restore. These cases stay the
  customer's concern, and each needs its own ADR before the platform takes
  it on.
- A new NACK code (13) joins the fail-closed resume vocabulary; older hosts
  already treat every non-zero value as a NACK.
- Evidence gate: the `test-metal` suite must restore one snapshot twice and
  show distinct userspace randomness from a Node and a Python workload before
  a release carries this change.
