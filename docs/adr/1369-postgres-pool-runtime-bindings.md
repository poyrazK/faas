# ADR-1369: PostgreSQL pool runtime bindings

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Atomic secret adoption and object-storage leases already protect reloads and in-flight work. PostgreSQL applications otherwise need to implement their own validated pool replacement and transaction-safe retirement before acknowledging managed credential rotation.
- **Decision:** Add driver-independent `PostgresPoolBinding` helpers to Go, server-only Node `postgres/runtime`, and synchronous Python. Require fresh exclusive factory results, a readiness validator and a retirement callback. Validate explicit managed PostgreSQL connection URIs before factory invocation, preserve the URI/TLS options, and redact configuration, leases and callback failures. No driver enters SDK runtime dependencies.
- **Lifecycle:** Extract the owned-resource lifecycle shared with object storage. Serialize frozen snapshots; clear new acquisition on admitted adoption, validate outside lifecycle locks, and publish only successful unfenced candidates. Detect tracked aliases before validation without disposing the old borrower's pool. Retire failed/unpublished candidates, including late results and Go nonnil factory results returned with errors. Coordinate applied ACKs only after all consumers succeed; another consumer's failure invalidates the pool. Existing platform verification/promotion requirements do not change.
- **Transactions:** Require leases through transaction completion and driver connection release. Rotation/invalidation retires the old pool only after its final lease releases. Copies share idempotent release state. Cancellation/timeout of shutdown waits does not force-close leased transactions. No credential-validity extension or SQL replay is promised.
- **Callbacks:** Factories own partial allocations until returning a resource. Validators must establish readiness, release validation connections, honor cancellation and bound driver waits; Python rejects async factories/validators. Cancellation fences publication even when callbacks finish late. Retire runs once outside locks after the final lease, can overlap for different pools, and must bound its work. Sticky sanitized cleanup failure is observable without automatic retries. Existing object-storage public behavior is preserved.
- **Delivery:** Include a Node `pg.Pool` service with explicit driver timeouts, idle-error redaction, connection-before-lease release ordering, best-effort rollback/destroy handling and shutdown draining. Export runtime subpaths without generated/browser dependencies; preserve Python runtime modules through regeneration. Synchronize the storage starter's vendored runtime with the extracted shared lifecycle, including its new local module dependency, and retain the runtime drift gate.
- **Validation:** Cross-SDK tests cover validation before publication/ACK, transaction leases across rotation/revocation, failed and late validation, owned alias rejection, URI identity, redaction and cleanup. Existing storage/coordinator suites cover shared lifecycle regressions. A disposable password-authenticated PostgreSQL fixture exercises the actual example, proving stale-credential rejection, replacement-pool use, old-transaction completion, failed adoption/revocation and exactly-once pool retirement. No API, schema, quota or VM lifecycle changes.
