# ADR-20261021220456: Attack mode

- **Status:** accepted
- **Date:** 2026-10-22
- **Related:** ADR-831 amendment 7 (`kind=challenge`), ADR-1191 (app-wide
  rules), ADR-961 (rule expiry and rule-set versions), ADR-973 (bot
  signals), ADR-091 (edge-rule quotas)

## Context

`kind=challenge` asks browsers to solve a short proof of work before they
reach an app. Using it against a flood still means writing a rule: pick the
hosts and paths, the condition that spares search crawlers, a priority, and
remember to remove it afterwards. During an attack that is the wrong amount
of work, and on Free, which has no challenge rules, it is not possible at
all. Vercel ("Attack Challenge Mode") and Cloudflare ("Under Attack Mode")
both offer one switch, on every plan.

## Decision

1. **One switch per app.** `PUT /v1/apps/{slug}/edge-protection/attack-mode`
   (`{"duration_seconds": N}`) switches attack mode on; `DELETE` switches it
   off; `GET` reads it. The dashboard's Edge protection panel and
   `gregale edge-rules attack-mode on|off|status` use them. The scopes and
   MFA step-up are those of an edge-rule write.

2. **It always ends on its own.** The duration is 15 minutes to 24 hours,
   default one hour (`MinEdgeAttackModeSeconds`, `MaxEdgeAttackModeSeconds`,
   `EdgeAttackModeDefaultSeconds` in `pkg/api/limits.go`). Switching it on
   while it is on moves the end to now plus the new duration and keeps the
   start. There is no "until switched off": a forgotten switch would keep
   challenging every visitor indefinitely.

3. **Carried by one managed rule.** Attack mode is a `kind=challenge` rule
   the switch owns, so it reuses the existing challenge gate, fleet
   convergence, expiry, events, summary, simulator and audit trail; the
   gateway is unchanged. The rule is:
   - app-wide (`match_host "@app"`, ADR-1191), path `/**`, every method,
     priority 0, enforced;
   - `verified_bot missing` (ADR-973), so verified search crawlers are not
     challenged; requests with a verified API key, consumer key or JWT
     subject are never challenged (ADR-831 amendment 7);
   - the default challenge (difficulty 16, pass one hour);
   - `expires_at` at the end of attack mode. Gateways drop an expired rule
     on the next request without a notification (ADR-961), so attack mode
     ends on every node on time even if apid is down.

   It is marked by the ownership key `edge_rules.manifest_key =
   'attack-mode'`. The existing unique `(app_id, manifest_key)` index keeps
   it to one per app, and the manifest reconciler (which owns only
   `async-route:` keys) and route-insight fixes (which skip keyed rules)
   already leave it alone. No migration is needed.

4. **What the managed rule is exempt from, and what it refuses.**
   - It is outside every edge-rule quota (the app total and per-kind caps,
     ADR-091), so an app at its cap can still switch attack mode on, and it
     does not take a slot from the app's own rules.
   - It is available on every plan, including Free, which has no challenge
     rules of its own. Attack mode costs one HMAC per request at the edge
     and keeps flood traffic away from wakes, so it protects the platform
     as much as the app.
   - A rule-set rollback (ADR-961) leaves it as it is: the current one is
     kept and the version's one is skipped, so rolling back a bad edit
     during an attack neither ends attack mode nor revives an old one.
   - `PATCH /v1/edge-rules/{id}` refuses it with 409 `edge_rule_conflict`
     naming the switch. `DELETE` on it is allowed and is the same as
     switching off.
   - Listings show it with `managed_by: "attack_mode"`.

5. **Status.** `EdgeAttackModeStatus` (`active`, `rule_id`, `started_at`,
   `expires_at`, `difficulty`, `pass_ttl_seconds`) answers the switch and is
   the `attack_mode` section of the edge-protection summary. It is read from
   the rules, not Prometheus, so it is current even when the counts are
   degraded. Once attack mode has run out the expired rule stays, so the
   summary can say when it last ended; switching on again replaces it.
   Attack mode's challenges count in the summary's `challenge` section and
   record the usual challenge outcome events against its rule.

6. **Audit.** `edge_attack_mode.enabled` (`rule_id`, `app_id`,
   `expires_at`, `extended`) and `edge_attack_mode.disabled` (`rule_id`,
   `app_id`, `was_active`).

7. **Prompting it.** The `edge_rejection_pressure` alert explanation and
   docs suggest attack mode for a flood the app's rules cannot keep up
   with. (`edge_waf_detections` already uses its 512-byte explanation
   budget.)

## Consequences

- Clients that are not browsers and carry no verified credential (uptime
  checks, webhooks from third parties, scripts using the app's own auth)
  get 403 while attack mode is on. The switch's help text, the dashboard
  and the docs say so; a path-scoped challenge rule remains the tool when
  part of the app must stay open.
- Plan availability is a product call made here (every plan). Gating it
  later needs a per-plan limit in `pkg/api/limits.go` and a check in the
  switch, not a schema change.

## Not in this step

- Raising the challenge difficulty while under attack, and a fallback for
  clients without JavaScript (both still open from ADR-831 amendment 7).
- Switching attack mode on automatically from an alert.
- Exempt paths. A path-scoped challenge rule covers that case today.

## Amendment 1 (2026-10-24): released by platform flags

Edge features launch behind platform flags that are off for every account
(ADR-20261023113721). Attack mode gets its own, `edge_attack_mode`.

- **Switching on needs two flags.** Attack mode is a managed challenge
  rule, and the gateway enforces challenge rules only for accounts
  `edge_challenge` includes. So apid switches attack mode on only while
  both `edge_attack_mode` and `edge_challenge` include the account; it
  answers 422 `edge_feature_unavailable` otherwise. Switching it off and
  reading it always work.
- **A kill switch of its own.** The gateway marks the compiled attack-mode
  rule, and leaves it inert for an account `edge_attack_mode` leaves out,
  without touching the account's ordinary challenge rules. The challenge
  solve path is not gated on it: no attack-mode page is served while it is
  inert, and the app's own challenge rules still need the path.
- **The dashboard** says attack mode is not yet available instead of
  offering the switch.
- Attack mode joins the edge security release gate (ADR-20261024082000) as
  a capability when both branches have merged.
