# ADR-284 · Git-driven deployment ownership and preview quotas

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** A project has one production branch-push deploy owner, `webhook` or `actions`. Existing and unconfigured projects use `webhook`. `gregale github setup` selects `actions` when it writes the production workflow; the GitHub App remains connected for PR previews. The generated workflow serializes runs per repository and app, waits for a terminal deployment result, and listens for the configured production branch, branches mapped with `--deploy-branches`, and newly created SemVer release tags. Mapped branches deploy into their configured project environment, or the default app scope when mapped to `default`; manual dispatch is limited to configured branches. The Action checks the live branch head before queuing a branch-push SHA and skips superseded runs; tag pushes deploy only when the tag is newly created and unforced, using the immutable event SHA. A deliberate queue-only Action publishes a separately named queued Check Run. PR previews use a bounded, separate plan allowance (Free 1, Hobby 2, Pro 5, Scale 20) and do not consume production app slots. PR preview app manifests do not inherit production environment values; source-declared service bindings are injected after scan. `github setup` sets preview-to-production service calls to `deny` unless the customer explicitly asks for `allow_marked`. See ADR-289 for branch-to-environment routing details.
- **Why:** A bound repository plus the generated push workflow can enqueue the same commit twice, with different rollout settings. A queue-only workflow can appear successful before the app is live. Counting a preview against Free's single production app makes the advertised preview capability unavailable to a Free user who already has an app. A separate preview allowance gives that user one temporary review environment while keeping an explicit account cap and the existing lease/janitor cleanup.
- **Consequences:** The project policy, database, API, and CLI carry `production_trigger`. GitHub push dispatch checks it before source fetch or reconciliation. Existing rows and missing policy rows retain webhook deployment behavior. The Action workflow is the production deploy authority after setup; PR webhooks still create, update, and close previews. `CountDeployedApps` reports production apps only. The preview batch transaction reserves every workload against the preview allowance or rejects the full set. The account limits API and generated pricing page expose the new allowance. Legacy `allow_marked` policy rows migrate to `deny`, so users who intentionally permit preview-to-production calls must explicitly opt in again. `github setup` also sets `deny` unless `allow_marked` is requested. Existing PR rows have environment values cleared when the next PR head is applied; customers must set up separate preview credentials for external dependencies.
- **Rejected alternatives:** Deduplicating webhook deliveries only by delivery ID does not deduplicate the independent Action request or preserve its rollout mode. A single combined app cap makes Free previews unavailable beside a production app. Marking an asynchronous deployment Check Run neutral under the release Check name gives a passing required check before the deployment has finished.
- **Operational qualification:** The Action push-head check runs before enqueue; a newer push arriving after that check is ordered after the current workflow by concurrency. Manually submitted source-ref deployments and legacy webhook mode still need an authoritative remote-head freshness check before promotion. The generated workflow handles `push` and manual dispatch, not GitHub `merge_group`; merge queue users need a separate CI readiness workflow. Safe rollout remains opt-in until a staging rollout and rollback drill confirms the Pro/Scale path. Managed preview databases and buckets still require separate provisioning; this decision only isolates the Gregale app quota and internal service-call boundary.
