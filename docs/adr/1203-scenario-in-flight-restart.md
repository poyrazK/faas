# ADR-1203 · Restart with a checkpointed in-flight write

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Extend standalone staged restart steps with one optional primary-app JSON write and one to five read-only JSON checkpoints. Poll checkpoint assertions, require the write to remain pending before submission, then use existing submit-once cold replacement, readiness, and storage verification. Cancel and join the write on every exit. Permit restart-only staged scenarios with baseline and subsequent recovery.
- **Why:** A completed-write restart does not test caller replacement while a dependency has accepted an operation whose acknowledgement is pending.
- **Consequences:** The restart timeout bounds all work. Preceding captures are allowed but background requests and checkpoints cannot capture. Evidence records pending submission, verified replacement, checkpoint results, request joining and fixed outcome classifications without response payloads. The original response is diagnostic; recovery must assert business reconciliation. Read-only probes do not freeze an application; the example provider persists a payload-bound pending intent and holds it until matching replay, with a bounded fail-closed timeout. Changed payloads cannot release it. The provider survives caller replacement. Portable SIGKILL tests cover an actual crash; managed native replacement requires separate execution and can fail under draining policies. Native acceptance verdict version 3 requires all nine cases including the in-flight scenario and independent API cleanup.
- **Rejected alternatives:** Free-floating background shell commands obscure cancellation ownership. A mutating release endpoint adds unnecessary control access; matching replay can release the deterministic fixture. Treating runner cancellation as proof of a process crash would misrepresent the evidence.
