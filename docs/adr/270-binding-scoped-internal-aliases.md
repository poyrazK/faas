# ADR-270: Binding-scoped private service aliases

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** A workload with a declared service binding may use `<service>.internal:10080` as an alias for the existing `<service>.svc.gregale:10080` endpoint. The node-local resolver answers the alias only when the source VM maps unambiguously to a live caller whose persisted binding inventory includes that service. Unbound `.internal` queries continue to the configured upstream resolver rather than claiming the customer's entire private-use namespace. The guest service proxy independently requires the same binding for `.internal` Host requests before target lookup or wake, including direct requests that bypass DNS. Both names share the existing target resolver, account boundary, target allowlist, preview policy, routing, and telemetry. Generated binding URLs keep the legacy name until every compute node supports the alias.
- **Why:** ADR-241 makes standalone declarations possible, but callers still see a platform-specific long hostname. A short name should be a discoverable capability, not a new route that weakens the proxy's authorization boundary or hijacks customers' own `.internal` names.
- **Consequences:** Alias availability follows the app's binding inventory, even when its outbound policy is still `account`; legacy unbound same-account calls remain possible only through the existing long name/path. DNS is a convenience gate, not a security boundary. Each alias lookup reads the caller's current manifest after the existing short-lived VM identity cache; authorization at the proxy remains authoritative. Customers can opt into the alias manually; the generated URL changes only in a later rollout-safe stack PR. This change does not add TLS, a portless listener, public ingress, RPC, or a new service registry.
- **Rejected alternatives:** Answer every syntactically valid `.internal` name (would capture customer DNS); rely on DNS alone for capability enforcement (Host-header bypass); change legacy `svc.gregale` semantics (breaking change); combine private TLS certificate/trust rollout with DNS aliasing (too much security-sensitive scope for one PR).
