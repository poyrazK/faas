# ADR-361 · Tenant egress is default-deny: web ports, pinned DNS, per-VM rate limits

- **Status:** accepted
- **Date:** 2026-09-29
- **Amends:** spec §11 tenant egress bullet. ADR-031 allowlist semantics are kept (see Consequences).
- **Context:** On 2026-09-24 Google suspended the production project for traffic that was "seriously impacting the service of other users", and the operators traced it to workloads running inside the platform. Spec §11 already described tenant egress as "default-allow TCP 80/443/53 + UDP 53", but the per-instance forward chain (`pkg/netns/config.go` `NftCommands`) had `policy accept`. It dropped only SMTP (25/465/587) and the lateral-movement ranges. Every other TCP port, all UDP and ICMP left through the node's shared NAT IP. There was no new-connection rate limit, only a 4,096 concurrent-connection cap. With the kernel's 120 s SYN timeout that still allows ~34 new flows/s per VM indefinitely. Guests could also resolve through any public resolver. Scanning, UDP floods and mining on stratum ports were all possible from any Free-plan VM.
- **Decision:**
  1. **Default-deny for guest-originated traffic.** Every packet entering a per-instance netns from `tap0` that is not already accepted by an earlier rule (established flows, the bridge service proxy and resolver, operator exceptions, private networking, ADR-031 allowlisted destinations) must be TCP to a port in the instance's `egress_ports` nft set. Anything else is counted in `faas_egress_denied` and dropped: other TCP ports, all non-DNS UDP (including QUIC; clients fall back to TCP 443), and guest-originated ICMP. The rules match `iifname tap0` only, so gateway and private-network ingress are unchanged. IPv4 and IPv6 chains carry the same rules. The chain policy is not changed.
  2. **Base ports** are TCP 80 and 443 for every plan (`api.TenantEgressBasePorts`). The lateral-movement deny set still runs first, so private, link-local and metadata ranges stay unreachable on every port.
  3. **Pinned DNS.** All guest DNS (UDP and TCP 53, any destination) is DNAT'd to the node's bridge resolver (ADR-170), which answers `*.svc.gregale` and forwards other names upstream. It lives in a dedicated `guest_dns` NAT chain, so the app-port retarget (ADR-149, which flushes `prerouting`) never removes it. Images with their own `resolv.conf` keep working, and builder VMs' `1.1.1.1` fallback is redirected. DNS-over-TLS (853) is dropped by the port policy. DNS-over-HTTPS on 443 cannot be told apart and is accepted.
  4. **Per-VM new-connection rate limit.** Guest-originated new flows over the plan's rate are counted in `faas_egress_rate` and dropped. Rates and bursts are per plan in `pkg/api/limits.go` (`EgressNewConnPerSecond` / `EgressNewConnBurst`): Free 10/s burst 40, Hobby 20/80, Pro 50/200, Scale 100/400. The limit applies before the port policy, so blocked attempts count against it too.
  5. **Extra ports** (Pro and Scale): an app may declare additional TCP ports, for example a managed database, in `apps.egress_ports` (`PATCH /v1/apps/{slug}` `egress_ports`, `gregale app <slug> egress-ports`). The cap is `EgressExtraPortsMax` in `pkg/api/limits.go`: Free 0, Hobby 0, Pro 8, Scale 32. Some ports are never allowed (`api.TenantEgressForbiddenPort`): SMTP (25, 465, 587, 2525); remote admin (22, 23, 3389, 5900); Windows RPC/SMB (135, 137–139, 445); IRC (6660–6669, 6697); well-known mining pool ports (3333, 4444, 5555, 7777, 14433, 14444, 45700); and DNS (53, 853), which is pinned. apid stores the canonical form: sorted, deduplicated, without the base ports. Clearing the list is accepted on every plan because it only narrows egress. vmmd re-applies the forbidden list and the *current* plan's cap when it renders the set, so a downgrade stops enforcing ports the plan no longer allows even though the stored list is kept. The ports ride the ADR-031 convergence path: a change bumps `apps.egress_allowlist_revision`, and schedd pushes allowlist and ports in one `UpdateEgressAllowlist` RPC. That RPC carries an `egress_ports_set` presence flag, so a release-skewed schedd that doesn't send ports never clears them. vmmd swaps the named set (flush plus add, both families) in one `nft -f` per live instance. A prepared network retargets its port set in the same transaction as the ADR-149 app-port DNAT.
  6. **Detection and kill switch.** Every guest-originated new flow to an address not in the instance's dynamic `egress_dsts` set (10-minute element timeout, 65,535 entries) is counted in `faas_egress_new_dst`, and the address is added to the set. The rule runs right after the lateral-movement deny, so blocked and rate-limited attempts count too; pinned DNS and bridge services are accepted earlier and never count. vmmd's 15-second per-namespace poll sums the counter over a trailing minute. It reports the sum in `Stats` and the capacity telemetry stream, together with the instance plan's `EgressNewDestinationsPerMinute` ceiling (Free 120, Hobby 240, Pro 1,200, Scale 3,000; each below 60 × the new-flow rate so a sweep trips it). When an instance reaches its ceiling, schedd's instance-stats poller calls `RecycleForEgressFanout`. That destroys the instance, marks the deployment's warm snapshot stale (it was captured after traffic and may hold a compromised process; the pre-traffic init snapshot is kept), and writes an `egress_fanout` transition. It also increments `schedd_egress_fanout_recycles_total{app}`, which pages through `FaasTenantEgressFanout`. The same poll exports `vmmd_egress_new_destinations_total{app}` and adds `port_policy` and `rate_limit` to `vmmd_egress_denied_total{class}`. The counter reader now also reads the ADR-361 counters and sums same-named counters across the ip and ip6 tables; it used to keep only the last one listed.
     **Account abuse hold.** The `EgressFanoutHoldRecycles`-th recycle (2) on one account within `EgressFanoutHoldWindowSeconds` (1 hour) places an account abuse hold: `accounts.abuse_hold_at` / `abuse_hold_reason` (`egress_fanout`, or `operator` for a manual hold). One recycle can be a compromised instance that a clean restart fixes; a repeat means the account's own code.
     - **Scope.** The hold covers the account, not the app. Jobs and executions are account-scoped and carry no app, and a second app would otherwise bypass an app hold.
     - **Separate from billing.** It lives beside `accounts.status`, so the billing lifecycle (past_due → suspended → deleted_pending and its timers) never sees it, and a release restores the prior state exactly.
     - **Enforcement.** `Account.Active()` and `MayDeploy()` return false while held, so every existing suspended-account gate applies:
       - wakes, jobs, executions, app tasks, crons and warm pools in schedd;
       - the wake outbox SQL;
       - deploys, builds and explicit wakes in apid.
       The gateway answers `account_abuse_hold` (403) before any wake is queued.
     - **Drain.** The reaper parks held accounts' apps like suspended ones, but destroys their running instances instead of snapshotting them, because a release would otherwise restore the offending process.
     - **Visibility.** The customer sees the hold on `GET /v1/account`. schedd audits `accounts.abuse_hold` and pages via `FaasAccountAbuseHold`.
     - **Release.** Only an operator releases it: `DELETE /v1/admin/accounts/{id}/abuse-hold` or `gregale admin abuse-hold release`. The same route with `POST` places a hold by hand. Both use the operator, MFA and step-up gate and are audited.
     - **Known limit.** The escalation count is per schedd and in memory, so a restart forgets it; that costs at most one more recycle before the hold.
  7. **Builders** get the same policy: build steps run tenant code. npm, PyPI, Go modules and apt all work over 80/443.
  8. **No flag.** Enforcement is always on. A default-off security control is the state that caused the suspension.
- **Consequences:**
  - Apps that talk to databases or brokers on other ports (5432, 6379, 27017, 8883) fail until they declare extra ports, which is Pro/Scale only.
  - Guest `ping` fails.
  - ADR-031 allowlisted destinations keep their semantics: any TCP port except 25, so submission ports 465/587 reach an explicitly allowlisted mail provider. They are now rate-limited and TCP-only like everything else. The allowlist rule and its live patch are unchanged. Rule order for guest traffic, after the lateral-movement deny: rate limit, non-TCP drop, allowlist accept, SMTP drop, port policy drop, allowlist terminal drop.
  - Prepared networks carry the plan's rate limit in their policy, at the same per-plan granularity as the existing egress rate.
  - Existing instances pick the rules up on their next wake; a release drain re-renders every instance.
- **Rejected alternatives:**
  - Flipping the forward chain to `policy drop`. The chain also carries gateway and private-network ingress, which would each need explicit accepts.
  - Host-namespace filtering. Per-plan and per-app policy already lives in the per-instance chain.
  - Proxy-only egress. It breaks raw TCP clients and TLS pinning.
  - A feature flag.
