# ADR-20261021101117 · Release diff

- **Status:** proposed
- **Date:** 2026-10-21
- **Uses:** config revisions ([ADR-1451](1451-guarded-reversible-config-changes.md)), build SBOMs ([ADR-038](038-build-attestation.md)), release commands ([ADR-1448](1448-releases-that-change-the-database.md)), release approvals ([ADR-20261020085706](20261020085706-release-approvals.md))
- **Decision:** `GET /v1/deployments/{id}/diff` compares a release with the one before it, or with any other release of the same app (`?against=`). It reports what changed between the two:
  - the code: commits, a GitHub compare link, the image;
  - the configuration: which env and secret keys were added, removed or changed;
  - the packages: from the two builds' SBOMs;
  - the runtime settings;
  - the release command, which is the database migration step.

  `gregale deployment diff` prints it. The approval page shows it, and approval requests in Slack and email carry a one-line summary of it.
- **Why:** An approver asked to let a release past its canary needs to know what the release changes. So does someone deciding whether to roll back, and someone reading an incident timeline. Today they must piece it together from `git log`, `gregale env history` and the build page, and nobody sees that a release also changed a secret or a package. Gregale already stores each piece: the deployment row, config revision snapshots, and each build's SBOM.
- **Rejected alternatives:**
  - **Extending `deployment summary`.** The summary (`GET /v1/apps/{slug}/deployments/{id}/summary`) is the release cockpit: rollout status and rollback target, plus metadata changes against the immediately previous deployment row, failed builds included. The diff reads config history and two SBOMs, and compares with the release that last served. Folding it into the summary would make every cockpit read pay for that. The two stay separate, and the summary keeps its cheap field comparison.
  - **Showing variable values.** The env API never returns values, and a diff shown in Slack must not leak them. The diff names changed keys only, for secrets and plain variables alike.
  - **Listing commits by calling GitHub.** That would add a network dependency and installation scopes to a read path. The diff shows both commit SHAs and, for GitHub sources, a compare link. Git hosting already renders that page.
  - **Comparing the deploy-time manifest.** Deployments do not snapshot the full manifest. The diff compares the fields each deployment row records: handler, runtime base, port, entrypoint, command, probes, minimum instances, sidecars, workflows and env overrides. That covers what a release can change about how it runs.

## Decision

### The two releases

`{id}` is the newer release. Without `against`, the base is its predecessor: the newest earlier deployment of the same app and scope that took traffic, meaning one that completed a rollout, is live, or was superseded. A release with no predecessor is compared with nothing; every section reports it as the first release. `against` must name a deployment of the same app; the CLI accepts `vN` revisions for both.

### Sections

| Section | Source | Reported |
|---|---|---|
| `code` | `commit_sha`, `source_url`, `image_digest` | Both commits; `compare_url` when both come from the same GitHub repository; whether the image changed. |
| `config` | The newest config revision of the release's scope created at or before each release | Variables and secrets added, removed or changed, by key. `known: false` with a note when the retained history (`api.ConfigRevisionsRetained`) no longer reaches a release. |
| `dependencies` | Each build's CycloneDX SBOM | Packages added, removed or changed version, each list capped at `api.ReleaseDiffPackagesMax`. `known: false` when either build has no SBOM. |
| `runtime` | Deployment fields | Each changed field with its before and after values. Env overrides show keys only. |
| `database` | `release_command` | Both commands and whether they differ. |

`summary` is one line, such as "new code, 2 config keys, 5 packages, release command changed" or "no changes found". It is computed from the sections.

### Where it shows

| Place | What it shows |
|---|---|
| `gregale deployment diff <id\|vN> [--against <id\|vN>] [--app <slug>]` | The full diff. |
| The approval page | A "What changed" section, read from the API with the viewer's session. |
| Approval requests ([ADR-20261020085706](20261020085706-release-approvals.md)) | The summary line, computed when the event is recorded. A diff that fails to compute leaves the line out; it never blocks the notification. |

### Access

The route is read-only and goes through the same app access as `GET /v1/deployments/{id}`: an organization's read role is enough. It never returns variable values, secret fingerprints or SBOM files.

## Consequences

- Reading SBOMs costs two object reads per diff. Diffs are on demand and bounded by `api.ReleaseDiffPackagesMax` in their output; the SBOM files themselves are what the build already stored.
- Config history is pruned to `api.ConfigRevisionsRetained` revisions per scope, so very old releases report config as unknown rather than guessing.
