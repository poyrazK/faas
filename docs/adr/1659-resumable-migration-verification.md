# ADR-1659: Resumable migration verification

- **Status:** Accepted
- **Date:** 2026-10-17
- **Context:** Importing a service with sealed configuration proves deployment admission, but does not prove access to existing external dependencies or HTTP behavior after a wake. Managed binding release runs require managed inventory and enforced policies; imported environment URLs cannot truthfully satisfy those contracts.
- **Decision:** Add app-owned migration receipts over the existing task, runtime freshness, park, wake and hosting verification owners. Each receipt freezes the selected live public HTTP deployment, artifact/configuration fingerprint, dependency environment names, one read-only smoke path and explicit cold-wake consent. This creates no managed binding evidence or release-policy waiver.
- **Probes:** Reuse the guest PostgreSQL probe's authenticated `SELECT 1` and the S3 probe's read-only listing. A bounded HTTPS GET checks an optional external API URL resolved from the deployment environment. Guest network policy and ordinary task quotas remain authoritative. Reports contain fixed diagnostic text, stage verdicts and resource IDs; no credentials, URLs, response bodies or gateway challenges.
- **HTTP evidence:** Use the existing short-lived gateway challenge and upstream response proof for the exact deployment. Require 2xx on the customer-selected path, both before and after wake. Synthetic edge health, redirects, other deployments and unproven responses cannot pass. Runtime freshness is evaluated independently of successful task probes.
- **Cold wake:** Explicit opt-in uses conditional parking against the expected deployment, observes a zero-active-instance boundary, publishes a persisted wake identity and waits for that same identity on a running instance of the selected deployment. Repeat HTTP and dependency checks. This exercises normal park/restore or cold boot; it does not invalidate snapshots or change VM lifecycle rules.
- **Durability:** A PostgreSQL receipt and optional task admission commit in one transaction. Versioned leases prevent concurrent advances from duplicating work. ADR-1660 adds a server worker, restart discovery and durable cancellation/restoration; the console reads progress independently of execution. A lost creation response is reconciled by the original caller UUID or receipt discovery.
- **Bounds and drift:** One unfinished receipt per app, including cleanup. The ten-minute deadline bounds checks, task start deadlines prevent late admission, and completed receipts are pruned after thirty days on subsequent creation. Lists return twenty entries. Read-only status checks invalidate changed passed evidence. Pending runs become terminal only after their worker stops work and completes cleanup, as specified in ADR-1660.
- **Customer flow:** Show selected coverage and failures in first-deployment recovery, download the report, and retain the receipt across reloads. Empty dependency selection explicitly covers HTTP only. Production domain changes, old-provider traffic switching, database copying and schema rollback remain separate actions.
- **Validation:** Concurrent admission, transaction rollback after task creation, lost-response discovery, cross-account isolation, configuration drift, incomplete task output, drain/wake ordering, real PostgreSQL guest connectivity, SDK wire contracts and browser reload recovery. Native Firecracker acceptance is required to measure full deployed park/wake behavior.
