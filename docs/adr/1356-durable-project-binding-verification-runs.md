# ADR-1356: Durable project binding verification runs

- **Status:** Accepted
- **Date:** 2026-10-14
- **Context:** Single-app receipts survive admission response loss, but project graph orchestration and exact candidate service targets remain local to the CLI.
- **Decision:** Add opt-in graph receipts with status, resume, cancel and completion. Freeze the complete prepared activation, rollback or deactivation manifest, member review digests, effect consent and one 1–600 second deadline. Create the parent and every member receipt in one transaction. Replays preserve every member ID and deadline. Review every member before persisting the graph; no task or message is created by receipt creation.
- **Targets:** Single-app receipt requests accept validated exact service target selectors. The server captures and rechecks its own target-aware inventory and private task pins. Resumption uses the original service recipient map; ordinary any-replica proof cannot satisfy an exact graph edge.
- **Authority:** Graph-backed member admission locks parent, project, member apps and deployments in a consistent order. Recheck original project membership, routing CAS, service edges, enforced policy revisions, candidate eligibility and all member artifact/configuration/queue snapshots before journaling normal admission. Parent cancellation fences admission even through the single-app API. Existing schedulers, capacity limits and task/canary ledgers remain authoritative.
- **Recovery:** A crash or lost parent/member response resumes committed identities without replacement tasks/messages. The shared CLI concurrency budget covers all member probes. Transient errors preserve work. Explicit cancellation, interrupt or exhausted root wait budget commits the graph fence first, then cancels only unfinished owned member work; every member cleanup is attempted and errors remain retryable. Reused work keeps its original owner.
- **Qualification:** Completion freshly evaluates every member against its frozen review, then commits passed status after authoritative graph checks. Changed membership, routing, targets, private metadata, failed resources or aged evidence block resumption/completion. Passed status remains a current observation. Activation retains its independent atomic traffic-write checks.
- **Bounds:** Existing 100-member graph maximum, 128 steps and eight active receipts per member app. At most eight unfinished unexpired graph receipts per project/environment. Requests are capped at 1 MiB. All member receipts share the original graph expiry. Expired graph receipts and links are pruned after one day on the next graph creation; resources retain their normal retention. GitOps candidate holds are unchanged.
- **Validation:** CLI subprocess termination after committed admission and before its response; exact recipient qualification and graph resumption without duplicates; concurrent PostgreSQL graph creation/admission; forced child-insert rollback of parent and all children; other-member drift and expiry fences; parent cancellation and owned cleanup; API, OpenAPI and Go/Node/Python SDK contracts.
