# ADR 20261114150000 · Flags usability: short commands, attribute targeting, gateway kill switch, lifecycle

- **Status:** accepted
- **Date:** 2026-11-14
- **Amends:** ADR-377 (customer-aware application feature flags)

This record has a date-and-time identifier because numbered ADRs collide
when parallel changes pick the next number.

## Context

Gregale Flags (ADR-377) evaluates versioned, tenant-scoped flag bundles in
the Node, Python and Go runtime SDKs. Four things make it hard to use day to
day:

1. **Every change is a JSON file.** The only write path is `gregale flags
   apply --file` with the whole configuration and its `expected_version`.
   Turning one flag on means `get`, editing JSON by hand and `apply`.
2. **Rules only know who the customer is.** A rule matches a customer list,
   a group, a subject list or a percentage. It cannot say "customers in DE",
   "Safari users" or "accounts on the pro plan", although the gateway already
   resolves country and browser family for analytics and the application
   knows its own user's plan.
3. **Off is slow and easy to get wrong.** A change reaches a running SDK on
   its next refresh: 15 s by default, up to 60 s of staleness. Disabling a
   flag serves its configured default, which may be `true`, so "off" needs
   `default: false` too.
4. **Flags never leave.** Nothing records who owns a flag or when it should
   be removed, and nothing notices a flag that has served one value to
   everybody for weeks.

## Decision

### 1. Short commands

The CLI gains verbs that read the latest configuration, change one thing and
publish it with the version they read. On `409 flags_version_conflict` they
read again and re-apply the same change, at most three times. They are
client-side; the API is unchanged.

| Command | Change |
|---|---|
| `flags list` | Table of key, type, state, default, rules, owner, expiry |
| `flags create KEY [--variants a,b] [--default V] [--description] [--owner] [--expires DATE]` | New flag, enabled. Boolean default `false`; variant weights split evenly, the remainder on the first, default the first unless `--default` |
| `flags set KEY [--default V] [--description] [--owner] [--expires DATE\|never]` | Edits fields of one flag |
| `flags on KEY` / `flags off KEY` | `enabled` true / false. `off` on a boolean flag also sets `default: false` and says so |
| `flags percent KEY PCT` | Upserts the last rule, ID `everyone-percent`, to PCT% of customers (two decimals). Boolean: value `true`; variant: weighted. `0` removes the rule. Refused when that rule has a progression plan |
| `flags rule add KEY --id ID [--customer UUID]... [--group G] [--attr NAME=V1,V2 \| NAME!=V1,V2 \| NAME$=SUFFIX]... [--percent P] [--value V]` | Inserts a rule before `everyone-percent`, or last |
| `flags rule rm KEY --id ID` | Removes one rule |
| `flags rm KEY` | Removes the flag |
| `flags kill KEY` / `flags unkill KEY` | See §3 |
| `flags stale` | See §4 |

`flags apply --file` stays the whole-configuration path. In the CLI command
tree (ADR-20261026145832) the short verbs are `flag enable`, `flag disable`,
`flag rollout set`, `flag rule create`, `flag rule delete`, `flag kill set`,
`flag kill unset` and `flag stale list`; the spellings in the table keep
working.

### 2. Attribute targeting

A rule gains `attributes`, a list of conditions that all must hold
(AND, like the existing constraints):

```json
{"id": "eu-pro", "attributes": [
  {"attribute": "gregale.country", "op": "in", "values": ["DE", "FR"]},
  {"attribute": "app.plan", "op": "in", "values": ["pro", "scale"]}
], "value": true}
```

- **Gateway-verified attributes** are `gregale.country` (ISO 3166-1 alpha-2,
  from the same trusted client-IP chain and geo database as the `geo` edge
  rule) and `gregale.ua_family` (the request-analytics browser family set).
  The gateway stamps them on the guest request as `X-Faas-Client-Country`
  and `X-Faas-Client-Ua-Family`. Both are reserved identity headers: a
  client's copies are removed at ingress, and a value is omitted when it is
  unknown.
- **Application attributes** are `app.<name>` (`name` matches
  `^[a-z][a-z0-9_]{0,31}$`). The application supplies them after it has
  authenticated the user: `flags.withAttributes({plan: 'pro'}, fn)` in Node,
  `flags.for_attributes({...})` in Python, `flags.WithAttributes(ctx, map)` in
  Go. At most 16 per request; a value is printable ASCII up to 128 bytes, and
  an invalid one is treated as missing.
- **Operators:** `in` and `not_in` (exact, case-sensitive) for every
  attribute; `ends_with` for `app.*` only (for example an email domain). A
  condition on a missing attribute never matches, including `not_in`.
  `gregale.country` values must be two uppercase letters.
- A rule may target only by attributes; it counts as targeting. Verified
  customer identity is still required: anonymous requests keep returning
  `customer_missing`, as in ADR-377. Anonymous visitor targeting is a
  separate decision.
- Bounds: 8 conditions per rule, 100 values per condition, values up to 128
  bytes.
- Attribute values are never stored in request evidence or carried in the
  propagation envelope; the decision records only the matched rule ID.
- Bundles that use attributes on an enabled flag need SDK capability
  `attribute-targeting-v1`. Older SDKs get `426 flags_sdk_capability_required`,
  exactly like subject targeting, instead of evaluating the rule without its
  conditions.
- Managed service calls do not carry the gateway attributes. A downstream
  service that needs the same behavior uses the propagated decision
  (ADR-377), which it already prefers over local evaluation.
- `flags inspect` takes `--attr NAME=VALUE` (repeatable) to simulate a
  request.

### 3. Kill switch, stamped by the gateway

A flag gains `killed: true`. A killed flag evaluates to the **application's
fallback**, the value the code passes at the call site, with reason `killed`
and source `fallback`, whatever its default, rules or inherited decision say.
The fallback is the behavior the code had before the flag existed, so a kill
cannot turn something on by accident, which is the trap of `enabled: false`
with `default: true`.

Two paths deliver it:

- **Gateway, next request.** gatewayd-internal stamps
  `X-Faas-Flag-Kills: key1,key2` (sorted, comma-separated) on each guest
  request whose deployment's environment has killed flags. SDKs honor it
  before their cached bundle, for every check in that request. It is a
  reserved identity header; a client's copy never reaches the guest. The
  gateway keeps a per-deployment cache of the kill list, filled by one query
  (deployment → project environment → latest published configuration) and
  emptied whenever a `feature_flags_changed` notification arrives. A trigger
  on `feature_flag_versions` inserts sends that notification, so every
  writer (apply, rollback, promotion, clone, auto-advance) is covered.
  Entries also expire after 30 s in case a notification is missed. A lookup
  that fails or takes longer than 250 ms stamps nothing and is retried after
  5 s; the request is not delayed further.
- **Bundle, next refresh.** `killed` is part of the published configuration,
  so queued work, cron deliveries and any request the gateway did not stamp
  pick it up on the SDK's next refresh, as before.

`flags kill` / `flags unkill` publish a new version, so kills have history,
audit and rollback like every other change. The kill header contains only
flag keys, never targeting data.

### 4. Lifecycle

A flag gains `owner` (free text up to 128 bytes, for example a team or an
email) and `expires_at` (a `YYYY-MM-DD` date).

`GET /v1/projects/{project}/environments/{environment}/flags/lifecycle`
(and `gregale flags stale`) reports for every flag:

- `owner`, `expires_at`, `last_changed_at` and `last_changed_version`: the
  newest version whose definition of this flag differs from the one before,
  looking back at most 200 versions;
- `serves_one_value`: the flag serves the same value to everybody: it is
  disabled or killed, has no rules, or its first rule has no customer, group,
  subject or attribute constraint and no percentage below 100%;
- `evaluated_requests`: requests with a decision for this flag in the last
  7 days, when the plan keeps request telemetry; otherwise absent with
  `evidence: "unavailable"`;
- `attention`: zero or more of `expired`, `expires_soon` (within 7 days),
  `stale` (serves one value and unchanged for 14 days), `never_evaluated`
  (enabled, evidence available and zero requests), `no_owner`.

An apid reconciler checks every environment with a published configuration
once an hour. When a flag enters an `attention` state it emits one audit
event, `flags.lifecycle_attention`, deduplicated per environment, flag,
reason and configuration version. Sending it to notification channels
(Slack, email, PagerDuty) is left for later: each existing channel consumer
(release approvals, budgets) has its own outbox, and flags would need a
third.

## Consequences

- `pkg/flags` gains `Condition`, `Rule.Attributes`, `Flag.Killed`,
  `Flag.Owner`, `Flag.ExpiresAt`, an `EvaluationContext` evaluator, the
  `killed` reason and shared decision vectors in `testdata` that the Go,
  Node and Python SDK tests read.
- Three new reserved guest headers (`X-Faas-Client-Country`,
  `X-Faas-Client-Ua-Family`, `X-Faas-Flag-Kills`) on `PlatformIdentity`.
- One migration: the `feature_flag_versions` insert trigger for
  `feature_flags_changed`.
- The configuration JSON stays backward compatible: every new field is
  optional. An older SDK refuses an attribute bundle with 426. SDKs advertise
  `kill-v1`; for one that does not, the runtime endpoint leaves killed flags
  out of the bundle, so the older SDK reports `flag_missing` and serves the
  same application fallback on its next refresh (it does not read the
  gateway header).
- Nothing here changes who can use Flags. It stays behind the
  `customer_flags` platform flag (ADR-1700).
