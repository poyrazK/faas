# ADR-1355: Durable single-app binding verification runs

- **Status:** Accepted
- **Date:** 2026-10-14
- **Context:** Parallel qualification reuses compatible evidence but its reviewed plan and ownership only exist in the CLI process. A crash or lost admission response must not create another task or queue message on restart.
- **Decision:** Add opt-in single-app verification receipts with caller-selected UUIDs, status, resume, cancel and completion APIs. The server and CLI use one policy planner. Creation compares a SHA-256 review digest of the selected deployment, scope, enforced policy, configuration stamp and stable binding metadata; the server persists its own inventory and plan. Private pins, commands, artifact fingerprint and queue consumer snapshots remain internal.
- **Admission:** Lock the owning app and run, check the original policy/configuration/artifacts and private metadata, then admit through the existing task or queue path and journal its resource ID in the same transaction. One resource per run step is immutable. Retries return the recorded resource. Failed journal writes roll back normal admission and its notifications. Run IDs support recovery when even the creation response is lost; middleware idempotency is supplementary.
- **Ownership:** A preexisting task or canary can be observed and recorded without becoming owned by this run. Cancellation commits its admission fence first and cooperatively cancels only unfinished owned resources, including queue messages whose consumer drifted. A running handler may finish. Completed evidence is not revoked by cancelling its receipt. Domain catalog metadata remains restricted by its existing scopes.
- **Resume:** Reuse the original plan, compatible pending work and fresh results. Reconfirm exact deployment, policy revision, configuration, artifact identity and private binding pins before admission. Missing, failed, cancelled or changed resources do not authorize a replacement. Expired or invalid reused evidence blocks qualification and requires a newly reviewed run. Transient HTTP errors preserve durable work; explicit cancellation, interrupt and wait-budget exhaustion request owned cleanup. No background execution controller is added.
- **Bounds:** Fixed 1–600 second run lifetime, at most 128 steps and 8 unfinished unexpired runs per app. Queue canaries receive at most the remaining original lifetime; task start deadlines use the original run expiry. Existing queue depth and runtime admission remain authoritative. Create replays, resume and status do not extend deadlines. Expired receipts older than one day are pruned on the next creation for that app; resources retain their existing retention policies.
- **Evidence:** Publication, task admission and a queued/running status never qualify a run. Completion requires every owned resource to succeed and a fresh server-side policy preflight against the original review. Passed status is a current observation and becomes blocked/expired when proof changes or ages out. It never replaces atomic traffic-write checks.
- **Scope:** API, CLI and Go/Node/Python clients for one app. Release graphs and GitOps run orchestration remain follow-ups. Legacy verification remains available; dry runs create no receipts or resources. No lifecycle/capacity owner is bypassed.
- **Validation:** Actual CLI subprocess termination after committed task and queue admission but before the HTTP response; resume without duplicates or renewed deadlines; concurrent PostgreSQL admission retries; rollback on journal failure; owned/reused cancellation; policy/configuration/artifact/consumer drift; expiry, private pin changes, queued false-pass rejection, redaction, API/SDK contracts and existing verification regressions.
