# ADR-592: Managed PostgreSQL portable reader contract and capability discovery

Status: accepted · 2026-10-05

## Context

ADR-155 defines provider-neutral credential access. ADR-461 established
restricted runtime and migration SQL roles, but the Neon adapter still rejected
read-only bindings. Connection delivery also required a replica endpoint even
though a restricted reader can use primary compute. Customers need to discover
regional support, and future adapters must qualify the same observable behavior.

## Decision

Implement `read_only` as a distinct deterministic SQL role with no ownership,
role memberships or administrative flags. Grant SELECT on existing public
tables/sequences and future objects created by the stable non-login schema owner.
Sequence USAGE/UPDATE, data writes, DDL and RLS bypass remain denied. Issuance
and cutover verification reject observed column, PUBLIC, customer-schema,
sequence, SECURITY DEFINER and future-object write grants. They return conflict
without stripping customer permissions. A privileged owner can alter grants
later; issuance and verification are observations, not continuous enforcement.

Prefer an explicitly supplied read-only endpoint, then pooled/direct primary.
Permission semantics belong to the credential role. Read-only does not promise
replica capacity, compute isolation or replica consistency. Preserve the
existing durable binding, secret delivery, rotation and revocation workflows.
Restore adoption must disable inherited reader roles as well as runtime and
migration logins and terminate their sessions.

Qualification artifact version 4 records advertised credential modes and
requires `ReadOnlyCredentialProber` evidence when `read_only` is advertised.
A shared SQL probe tests existing/future tables, sequence inspection, denied
mutations/DDL/escalation and RLS with writable client settings. Adapter probes
also prove stable password recovery on retry, data-preserving replacement and
retired session/login rejection. Unsupported reader capability needs no reader
proof. Registry verification rejects mismatched credential declarations, and
older artifacts/environment approvals cannot authorize the new release.
Operators must rerun live qualification and lifecycle smoke before opening
the gate. Local SQL tests do not prove the Neon password API or branch behavior.

Add authenticated `GET /v1/postgres/capabilities` with `postgres:read` and the
existing MFA policy, optional portable region and contract version 1. Project
the default placement's capabilities through plan limits without provider I/O.
Return support, database/storage/restore limits and a separate qualification/
canary provisioning gate. Reservation still checks usage, budget and current
quota. Exclude backend IDs, fingerprints, credentials, endpoint hosts and costs.
Existing databases stay pinned; default discovery cannot override their backend
capabilities. Expose the route in Go, generated Node/Python SDKs and the CLI.

No catalog migration or plan entitlement change is required. External SQL role
and probe DDL follows ADR-461's quoted-identifier convention; platform metadata
probing remains generated by sqlc. Durable resizing, preview cloning/expiry,
read replicas and cross-provider migration remain separate increments.

## Validation

TLS/SCRAM PostgreSQL regressions exercise real reader permissions, RLS, future
grants, stable role passwords, rotation/revocation and restored login retirement.
Privilege drift tests cover columns, PUBLIC, sequences, default ACLs, explicit
definer execution, other schemas, ownership and memberships. Qualification
tests reject missing proof, old approvals and changed capability declarations.
API tests cover authentication/scope, malformed queries, plan/provider limits,
closed canary visibility and secret exclusion. CLI and generated SDK contract
checks accompany the new route. Live Neon qualification remains a rollout gate.
