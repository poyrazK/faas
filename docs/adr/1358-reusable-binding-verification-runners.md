# ADR-1358: Reusable binding verification runners

- **Status:** Accepted
- **Date:** 2026-10-14
- **Context:** Server reviews and receipts remove client planning and hashing, but CI and SDK users still have to reconstruct the CLI's admission, polling, recovery and qualification workflow.
- **Decision:** Extract a Go receipt coordinator into `pkg/bindingrun`, use it for durable CLI execution, and publish the identical source in the leaf Go SDK with a synchronization gate. Add Node and synchronous/asynchronous Python adapters using the same recovery contract vectors. Runners accept an existing receipt ID; review, consent and creation remain explicit API operations.
- **Execution:** Resume and freeze the returned selection, deadline, plan and public review. Count unfinished task and queue resources across the whole graph before admitting new frozen step indices. A single invocation defaults to two unfinished resources, configurable from one to eight. Already existing work above the budget is observed without replacement or cancellation. Server admission, capacity and scheduling remain authoritative. This client budget is not a distributed lease between concurrent drivers.
- **Qualification:** Poll sanitized receipt resource status, not guest stdout or probe command configuration. Preserve known resource identity and ownership. Fail closed on changed membership, selections, review, deadlines, plans, unknown status or failed/missing resources. Ask the server to complete even previously passed receipts; only a confirmed passed response and passed graph members produce success. No route activation is performed.
- **Recovery:** Transport errors, local observation stops and progress callback errors return the original receipt identity without cancelling server work. Resume that ID after uncertainty, including admission or completion response loss. Original expiry is never renewed. Python task cancellation retains asyncio cancellation semantics and carries `run_id`; other failures use a typed recovery exception. Explicit API cancellation continues to fence admission and clean only owned work. The CLI retains its existing interrupt/deadline cancellation policy.
- **Progress:** Serial change notifications contain root/member IDs, app, step index, resource kind/ID and status. A persisted passed receipt is reported as qualifying until completion is reconfirmed. Callback failures stop observation; callbacks do not grant consent or authority.
- **Compatibility:** Deployment state can expose compact UUIDs. Normalize those selectors when comparing graph members while retaining strict canonical receipt and resource identities. Durable CLI reports expose sanitized resource IDs/status rather than reconstructing guest stage reports. Legacy verification stays available.
- **Validation:** Shared Go/Node/Python recovery vectors cover tasks, queue canaries, graph budgets, reused work, compact deployment selection, lost responses, changed authority, failed resources and false completion. Stop during committed admission then resume without duplication or renewed expiry. Go race checks and CLI subprocess crash recovery remain required.
