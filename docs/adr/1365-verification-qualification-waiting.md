# ADR-1365: Verification qualification waiting

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Successful probes can precede application acknowledgment, runtime refresh or queue consumer readiness. Treating every final preflight blocker as a permanent completion conflict forces callers to abandon otherwise usable receipts.
- **Decision:** App and graph completion return HTTP 202 with the original pending receipt and a typed `qualification` observation only when every blocker is a recognized temporary condition. Conditions contain public selectors and stable codes, without raw acknowledgment payloads or messages. Completion returns HTTP 200 only after the existing authoritative final checks pass.
- **Conditions:** Runtime refresh starting/stale, queue consumer not observed/stale, and application acknowledgment missing/stale/candidate not observed can qualify. Application acknowledgment requires complete, internally valid application-ack observations and a known reload-capable roster. Failed, malformed, unknown or contradictory evidence remains a conflict. Any permanent blocker wins, including in another graph member. Conditions are bounded to 12,800 across the response.
- **Runner behavior:** Go, Node and Python validate conditions against the frozen receipt, publish `waiting_for_qualification` progress with typed conditions, wait for the configured polling interval, read status, and retry completion. The CLI inherits this behavior through its shared runner. Every wait uses the original receipt expiry and caller deadline/stop controls. Waiting never creates another receipt, renews expiry, admits replacement work or changes traffic. Status GET retries retain their existing bounded policy; uncertain completion writes still require explicit recovery.
- **Compatibility:** Qualification observations are ephemeral completion responses, not persisted authorization or new receipt states. Stored status remains pending/passed/cancelled. Older runners stop on pending completion rather than infer success. New runners stop on unknown conditions, selector drift, callback failure or cancellation. Passed receipts still undergo the existing fresh validation.
- **Validation:** Server classification, queue readiness settlement and graph drift; all three runners for app and graph settlement, malformed conditions, callback failure and bounded stopping; HTTP 202-to-200 settlement without queue publication; generated OpenAPI and SDK parity.
