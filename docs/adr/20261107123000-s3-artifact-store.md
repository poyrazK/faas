# S3-compatible artifact store for bare-metal fleets

Status: Accepted

Date: 2026-11-07

Related: ADR-054 (shared artifacts), ADR-1135 (extent encoding), ADR-1344 §8
(OVH launch topology), ADR-20261024225612 (CPU templates)

## Context

The shared artifact store holds kernels, bases, layers, rootfs images and VM
snapshots for every compute node. Production uses `FAAS_STORAGE_BACKEND=gcs`,
which authenticates only with the VM's attached service account through the
GCP metadata server. The public release moves to OVHcloud bare metal
(ADR-1344 §8), where no metadata server or machine identity exists. The only
other remote backend, an OCI registry, would mean running or renting a
registry for multi-GB blobs. OVHcloud, Hetzner, Cloudflare R2 and MinIO all
offer an S3-compatible API.

## Decision

1. Add `FAAS_STORAGE_BACKEND=s3` (`pkg/storage/s3.go`), configured by
   `FAAS_S3_BUCKET`, `FAAS_S3_ENDPOINT`, `FAAS_S3_REGION`,
   `FAAS_S3_ACCESS_KEY_ID`, `FAAS_S3_SECRET_ACCESS_KEY` and optional
   `FAAS_S3_PATH_STYLE`. The bucket must already exist; daemons never create
   or reconfigure it.
2. Authenticate with a static access key pair from the environment file.
   `imaged-storage.env` may override the pair for imaged and vmmd, the same
   split OCI uses for its lifecycle login, so request-serving daemons need not
   hold delete authority.
3. The endpoint must be HTTPS. Plain HTTP is accepted only for a loopback host
   (a local MinIO under test).
4. Objects use the GCS backend's encoding exactly: zstd or zstd-extents for
   compressible keys, named by the `gregale-storage-encoding` and
   `gregale-storage-uncompressed-size` user metadata. A bucket copied from GCS
   with its metadata reads back unchanged. A GetObject response carries body
   and metadata together, so there is no generation pin to take.
5. Uploads of unknown length go up as one PutObject when they fit in 16 MiB
   and as a multipart upload otherwise (up to 10,000 parts, 156 GiB). Every
   request carries Content-MD5; the SDK's trailing CRC checksums are off
   because compatible stores disagree on them. A failed multipart upload is
   aborted.
6. The backend implements `Exists` (HeadObject) and `CopyObject`
   (server-side, up to 5 GiB; larger objects report `ErrUnsupported` and
   callers stream).
7. `FAAS_STORAGE_FALLBACK_BACKEND` may be `gcs` or `oci` under `s3`: missing
   reads consult the old store during a migration, and writes go only to S3.
   A GCS fallback outside GCP authenticates through
   `GOOGLE_APPLICATION_CREDENTIALS`.
8. The join, admission and compute-service gates accept `s3` with the same
   strict shared-artifact contract (`FAAS_STORAGE_LOCAL_PREFIXES=none`,
   `FAAS_REQUIRE_SHARED_ARTIFACTS=1`, no stale cache) plus the five S3
   settings.

## Not in this change

- Exclusive (create-only) publication and its receipts, used by native
  snapshot recovery qualification, stay GCS-only; S3 reports
  `ErrExclusivePutUnsupported`, as OCI does. S3 `If-None-Match: *` can carry
  it once the target provider's support is verified.
- The bucket itself, its lifecycle rules and keys are operator setup.
- No metal or provider test yet: unit tests run the real SDK against an
  in-process S3 server. Run the artifact lifecycle check
  (`gregalectl artifact lifecycle-check`) and a cross-node snapshot restore
  against the real OVHcloud bucket before admitting nodes.

## Consequences

- Bare-metal fleets have a shared artifact store without GCP credentials.
- Artifact access keys live in `storage.env` (root:faas 0440), readable by
  every storage daemon. Scope them to the one bucket.
- GCS-to-S3 migration can be lazy (fallback) or a bulk copy that preserves
  object metadata (for example `rclone copy --metadata`).
