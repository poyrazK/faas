# ADR-289 · Tenant-scoped hostname verification webhooks

- **Status:** accepted
- **Date:** 2026-09-27
- **Decision:** Add `platform_tenant.hostname.verified` as an opt-in event for platform-tenant webhook subscriptions. Emit it only when a hostname attached to a tenant surface explicitly linked to that platform tenant transitions from unverified to DNS-verified. Enqueue one durable delivery per matching subscription and hostname in the same database transaction as the verification update. Include tenant identity, the stable external reference, surface and app identity, hostname identity, and verification time; never include the DNS challenge token.
- **Why:** A platform needs to correlate customer-owned domains with its external customer records and start its own onboarding flow without polling every surface. App lifecycle events are a poor substitute because an app can serve multiple tenants and do not establish which customer-owned hostname changed.
- **Consequences:** DNS verification proves control of the hostname only. It does not mean certificate issuance succeeded or that the hostname is routable. Events are emitted only for explicitly linked surfaces, are durable and retryable, and are delivered at-least-once. Existing subscriptions that omit `event_filter` continue to receive only `platform_tenant.statement.finalized`; event filters are selected at creation and immutable. The shared account webhook quota, URL validation, signing, and retry controls continue to apply.
- **Rejected alternatives:** Emit app-scoped hostname events to all app webhooks, which could disclose one tenant's activity to other customers sharing the app; infer tenant identity from a surface name or current link after the fact, which is ambiguous across relinks; include the TXT challenge token, which is a short-lived proof secret; or describe the event as “ready”/“routable,” which would overstate what DNS verification proves.
