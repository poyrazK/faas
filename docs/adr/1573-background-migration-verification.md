# ADR-1573: Background migration verification and service recovery

- **Status:** Accepted
- **Date:** 2026-10-17
- **Context:** ADR-1572 saves migration checks but initially relies on client advances. Closing a browser during parking can leave the service parked, and a read-only expiry does not discharge the run's recovery obligation.
- **Decision:** Start a bounded verification worker with apid. Poll an indexed durable due queue at startup and every second; process up to 32 receipts with four workers. Existing receipt versions and 55-second leases claim steps. Successful/waiting steps schedule another attempt after two seconds; infrastructure errors back off to at most thirty seconds. No process-local queue, browser connection or LISTEN delivery is required for discovery. Retain `/advance` for compatibility; the console only reads reports and submits creation/cancellation.
- **Fences:** Cancellation commits the caller's intent with an optimistic version change and preserves an active worker lease. A stale step cannot enqueue a task or overwrite cancellation. Cleanup waits for that lease to end or expire, so it cannot overtake a park still in flight. Persist a restoration obligation in the lease claim before attempting park. All side-effect work ends before its lease's final five-second persistence allowance. A lost task response uses the original journaled task; a lost wake publication reuses the saved wake identity.
- **Stopping:** Cancelled, expired, invalidated and failed runs stop their recorded dependency tasks through the existing task owner. Pending status includes cleanup. The ten-minute checking deadline does not terminate restoration. Queued tasks are cancelled; running tasks must reach a terminal state before the run completes. Failed check evidence and its original stop reason remain available.
- **Restoration:** For an interrupted park, wait for the existing drain, then republish the original wake identity through the existing scheduler notification path. Require a running instance of the selected deployment before recording `restored`; publication success is insufficient. A replacement deployment or deleted app records `superseded` without waking the former deployment. An inactive account or security quarantine records `blocked` and requires customer/operator action. Normal successful cold-wake evidence still requires its exact wake identity; availability recovery can accept another already-running instance of the same deployment. No scheduler, instance-state, webhook outbox or VM owner is bypassed.
- **Bounds:** Every unfinished run, including overdue cleanup, counts against the app's one-active-run bound. Retention never deletes pending cleanup. The nullable indexed `next_attempt_at` column schedules pending work and becomes null on terminal save; an active lease postpones discovery until expiry. Cancellation and cleanup continue when public task admission is disabled. Transient restoration failures remain discoverable beyond the checking deadline with bounded retries.
- **Observability:** Reports expose cancellation time, cleanup phase, fixed retry diagnostics and restoration outcome, with no credentials, URLs, task output, gateway challenges or private leases. The console keeps saved reports visible when polling fails and does not equate cancellation intent with completed cleanup. Worker warnings are sanitized.
- **Validation:** Worker progress without client advances; lease expiry and original task identity after restart; cancellation racing an in-flight park; no task admission after a cancellation version change; task shutdown before completion; timeout recovery beyond the checking deadline; repeated wake identity until a running instance; replacement-deployment protection; PostgreSQL queue discovery/retention and atomic task journaling; API authorization and disabled-admission cancellation; console reload, polling failures and recovery outcomes. Native Firecracker park/wake and leak acceptance remain required on a dedicated x86_64 KVM host before shipping.
