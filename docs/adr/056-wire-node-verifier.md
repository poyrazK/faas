- **Decision:** Add a generic, audit-friendly mTLS handshake-layer
  verifier that binds a peer's leaf-`Subject.CommonName` to a
  registered `compute_nodes.name` row. The verifier augments
  (never replaces) stdlib chain + RFC 6125 SAN + EKU trust and
  runs in `tls.Config.VerifyPeerCertificate` so the rejection
  happens BEFORE any RPC dispatch. The handler-layer
  `wire.PeerCN(ctx)` (ADR-052) stays untouched as defense-in-depth.

## Why

The current trust model is sound: PR #445 (ADR-052) shipped the
stdlib verifier (chain + SAN + EKU) and a handler-layer peer-CN
helper. The remaining gap is that leaf-CNs are **role-shaped**
(`vmmd.faas`, `schedd.faas`) — every vmmd box carries the same
CN, so the leaf alone cannot prove "this is *the* compute-01 we
provisioned" vs. "this is *some* vmmd". Per-daemon cert material
DOES prove a peer holds a real leaf (the stdlib chain is intact),
but a misconfigured-but-real-cert vmmd claiming any role could
dial any other daemon's mTLS leg today.

The PR-B verifier closes the role-forgery gap by binding
**leaf-CN → `compute_nodes.name`** — a peer presenting `vmmd.faas`
is accepted iff a `compute_nodes` row with `name='vmmd'` exists.
This proves "the peer is a vmmd that's been registered" without
requiring per-node leaf certs (which a future ADR may add).
Per-node authentication for capacity reports is partially covered
by the Tier 1 Phase 2 `node_signature` field (PR #457), so PR-B
does not need to close the per-node-for-CapacityReport gap — it
closes the role-forgery gap for every cross-box mTLS leg,
including gatewayd→vmmd (which has no signature story today).

## Composition with stdlib trust (load-bearing detail)

`tls.Config.VerifyPeerCertificate` is invoked by `crypto/tls`
AFTER `verifyServerCertificate` (client) or `processCertsFromClient`
(server) succeeds. The hook receives the already-parsed
`[]*x509.Certificate` chain in `verifiedChains[0]`. If stdlib
rejects the chain (chain-trust failure, SAN mismatch, EKU
violation), the hook is NEVER consulted. Our verifier therefore
CANNOT see an untrusted leaf.

- `InsecureSkipVerify` stays `false`. ADR-052 §Rejected
  alternatives flagged `InsecureSkipVerify=true + custom verifier`
  as CodeQL alert #58; PR-B does not touch that field.
- The verifier reads `verifiedChains[0][0].Subject.CommonName`
  directly. It does NOT call `x509.ParseCertificate` on
  `rawCerts` (those are raw DER; `verifiedChains` is
  already-parsed and trusted).

## Locked decisions

- **Leaf-CN → `compute_nodes.name` binding.** The friendly label
  is the operator's mental model (matches `gregalectl pki status`),
  and the leaf-CN IS a friendly label. `compute_nodes.id` is a
  UUID auto-generated by Postgres and not what operators see
  in the wire material. UUIDs flow through `ComputeNode` into
  the gRPC payload as today.
- **Both schedd and vmmd wired, gated on multi-box.** Schedd gates
  on `cfg.NodeName != ""` (the multi-box TOML field that mirrors
  vmmd's `cfg.ComputeNode.NodeName`). vmmd gates on
  `cfg.ComputeNode.NodeName != ""` — same gate the egress
  watcher (ADR-055) uses. Single-box dev paths keep the
  verifier off entirely; stdlib chain + RFC 6125 SAN + EKU
  alone run.
- **Defense-in-depth.** `wire.PeerCN(ctx)` stays untouched. PR-B
  adds the verifier at the handshake layer so a future RPC that
  forgets the handler-layer CN check is still safe.
- **Reuse `db.NotifyComputeNodesChanged`.** Post-00276 the verifier
  subscribes to the dedicated nodes-only channel
  (`db.NotifyComputeNodesChanged`); the pre-split unified channel
  `db.NotifyComputeNodeChanged` was retired by migration 00276 (Tier-2
  gap #12). The keys-table writes that used to piggyback on the
  unified channel now route via `db.NotifyComputeNodeKeysChanged`,
  consumed by schedd's node-key registry only.

## Three implementations

1. `AllowAllNodeVerifier` — the no-op default for single-box dev
   and pre-slice-3 paths. A nil receiver is also nil-safe.
2. `InmemNodeVerifier` — map-backed CN-set for tests and
   operator-override flows. Strict-nil returns
   `ErrNodeVerifierCNMismatch` so a forgotten wire in a test
   fails loudly.
3. `PGNodeVerifier` — production implementation. Holds a snapshot
   of `(name → id)` refreshed on every `compute_node_changed`
   notification. **Loader failure keeps last-known-good** (a
   transient Postgres blip must not de-sync the verifier to
   "allow nothing" and brick every mTLS leg).

## Rejected alternatives

- **Push the verifier down into gRPC interceptors.** Handlers
  can read `peer.AuthInfo`, but the rejection would happen
  AFTER the TLS handshake completes. The handshake-layer
  verifier rejects BEFORE any RPC dispatch, so an attacker
  can't even probe for handler-layer side-effects.
- **Bind leaf-CN → `compute_nodes.id` (UUID).** Per-node CNs
  (`vmmd-fsn-2.faas`) would require a leaf-cert re-issue
  (a future ADR). PR-B ships with role-shaped CNs and the
  friendly-label binding; per-node attribution is partly
  covered by `node_signature` (PR #457) for capacity reports.
- **Wire the verifier from `pkg/state`.** State is the wrong
  layer for a TLS-handshake primitive — the verifier is hot
  on the wire path and must not depend on the state-machine
  imports. Splitting it into `pkg/wire/pgverifier.go` keeps
  the dependency direction clean (`pkg/state` is the data
  layer; `pkg/wire` is the transport layer).
- **Custom chain verification in the verifier.** CodeQL #58
  (ADR-052 §Rejected alternatives) flagged the original
  `InsecureSkipVerify=true + custom verifier` shape. PR-B
  keeps stdlib chain trust and only ADDS the CN-binding
  hook. The `InsecureSkipVerify=false` invariant is pinned by
  the existing test at `pkg/wire/grpc_test.go:510` and
  reaffirmed in `LoadServerTLSConfigWithVerifier`'s doc.
