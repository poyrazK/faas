# ADR-217 · Application inbox and outbox facades

- **Status:** accepted
- **Date:** 2026-09-22
- **Decision:** Add two explicitly addressed, durable API facades over Gregale's existing delivery machinery. `POST /v1/apps/{slug}/inbox` wraps arbitrary JSON in a CloudEvents 1.0 envelope and enqueues it as an `InvocationQueue` row for the target app. `POST /v1/apps/{slug}/outbox` resolves a webhook id or exact registered URL owned by the source app and enqueues an arbitrary event type in `app_webhook_deliveries`. The CLI exposes these as `gregale send` and `gregale deliver`; first-party SDKs expose matching methods. Repeating either POST can enqueue another delivery; consumers must deduplicate event IDs before non-idempotent side effects.
- **Why:** Straightforward API-to-worker, service-to-service, webhook-to-service, cron-to-service, and customer-webhook delivery currently makes application developers assemble lower-level queue, event-subscription, and webhook primitives. Gregale already owns the hard reliability mechanisms—durable acceptance, wake, retry/backoff, signing, logs, dead-letter, and replay—but lacks a small application-facing contract that composes them.
- **Consequences:** Inbox delivery is at least once, plan-gated by the existing queue capability, capacity-checked by `MaxQueueDepth`, and visible/replayable through the invocation and unified DLQ surfaces. The delivered payload is the normalized CloudEvents envelope, not only its `data`. Outbox delivery requires a pre-registered, enabled app webhook; that preserves the existing SSRF validation and sealed signing secret. Explicit outbox delivery bypasses the subscription's platform-event filter, while automatic fan-out remains restricted to the producer-backed event allowlist. The delivery-ledger event constraint becomes a non-empty 256-character bound so custom types remain durable and replayable. Neither facade is a streaming log, partitioned broker, ordering service across queues, or Kafka replacement.
- **Rejected alternatives:** A new message table and dispatcher would duplicate queue retry/DLQ/wake behavior and create two operational truths. Accepting arbitrary URLs and secrets on every outbox call would weaken SSRF controls, complicate secret rotation, and make replay unsafe. Routing inbox calls through content-based subscriptions would add reconciliation latency and make an explicitly named target depend on manifest matching. Expanding automatic webhook filters to arbitrary strings would imply platform producers exist for events they cannot emit.
