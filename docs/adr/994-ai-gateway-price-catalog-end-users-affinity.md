# ADR-994 · AI gateway phase 4: built-in price catalog, per-end-user limits and key affinity

- **Status:** accepted
- **Date:** 2026-10-12
- **Relates to:** ADR-988 (AI gateway), ADR-990 (price lists and cost limits), ADR-991 (hard caps, key pools, request log), ADR-982 (apid domain packages)
- **Decision:** Extend the AI gateway with:
  - a built-in price catalog that prices the models an integration's own price list does not name;
  - per-end-user attribution and UTC-day token and cost limits, keyed by an app-supplied `X-Gregale-AI-User` header;
  - key-pool affinity: a call with a session or end user picks its key by rendezvous hash instead of round robin.

  The AI gateway's apid endpoints move from `pkg/apid/apidserver` into `pkg/apid/outboundai` (ADR-982). `apidserver` keeps the routes and the release gate.
- **Why:**
  - Cost limits and spend reporting only worked after a customer typed in a price list. Every competing gateway ships list prices, so without them "hard cost caps" were empty for most integrations.
  - Apps that serve their own users had no way to stop one user from spending the shared budget, or to see who spent it.
  - Pooled keys rotated round robin. A conversation's calls therefore landed on different provider accounts, and keys from different accounts do not share prompt caches.
- **Consequences:**
  - An AI integration with no price list now reports and limits cost at catalog prices. Before this ADR its cost was zero.
  - Catalog prices are list prices at the base tier, converted to euros at a recorded rate. They ignore batch, priority and long-context tiers and negotiated discounts. A customer who needs exact numbers keeps setting a price list. A `"*"` entry in that list, even at zero, turns the catalog off for the integration.
  - End-user IDs are customer data. They are stored in a rollup for 31 days and, when the request log is on, in the log for 7 days. They are never metric labels. The docs ask for opaque IDs or hashes rather than e-mail addresses.
  - Per-end-user limits are exact only for the first 10,000 distinct end users of an integration per UTC day. Later users aggregate under `~other`, and only integration and app budgets limit them.
- **Rejected alternatives:**
  - **Fetch prices from a provider or LiteLLM at runtime.** That makes admission depend on a third-party endpoint and lets a remote file change what customers are charged against their caps. A reviewed, versioned file changes only with a release.
  - **Hand-maintain the catalog.** There are hundreds of models across six providers. A pinned generator run from LiteLLM's MIT-licensed data, with the rate and source recorded in the file, is reviewable and repeatable.
  - **Bill in USD.** Every Gregale budget and price list is in euro millicents. Converting once, at generation, keeps admission integer-only.
  - **Derive the end user from the request body** (the OpenAI `user` field, Anthropic `metadata.user_id`). Not every format has one, and reading it needs a buffered body. A header works for every provider and for streamed bodies, and never reaches the provider.
  - **Unbounded per-user rows.** A caller choosing the header value could grow the table without limit, as with provider-chosen model names in ADR-988. The per-day cap and the overflow row bound it.
  - **Sticky sessions through a shared table.** Rendezvous hashing needs no state and no coordination between replicas. Adding or removing a key moves only the sessions on that key.

## Built-in price catalog

`pkg/outbound/aiprices/catalog.json` is generated by `scripts/gen_ai_price_catalog.py` from LiteLLM's `model_prices_and_context_window.json` at a pinned commit (MIT, attribution in `pkg/outbound/aiprices/NOTICE`). The generator:

- keeps only `chat`, `completion`, `responses` and `embedding` models of the six gateway providers;
- drops region- or tier-scoped keys (`azure/eu/...`, `bedrock/us-east-1/...`) and free entries;
- converts USD per token to EUR millicents per million tokens at the ECB reference rate it records, rounding up;
- keeps the dearer entry when two LiteLLM providers name the same model.

The file records its source commit, generation date, rate and rate date. It is embedded in outboundd and apid. Refreshing it is a regular PR: rerun the generator with a new commit and rate, and review the diff.

**Lookup.** For a call's model, outboundd tries:

1. the integration's price list (longest prefix; `"*"` matches everything);
2. the catalog for the integration's provider:
   - the exact name;
   - the name without a `models/` prefix, a Bedrock ARN path or a Bedrock cross-region prefix (`us.`, `eu.`, `apac.`, `global.` and so on);
   - the longest catalog model that the name extends at a `-`, `@` or `:` boundary, so `gpt-4o-2024-08-06` prices as `gpt-4o` when the snapshot is missing, while `gpt-4` never prices `gpt-4o`.

Reservations (ADR-991) and settlement use the same lookup. `GET /v1/outbound/ai-price-catalog?provider=` lists a provider's catalog; `&model=` returns the entry that would price that model. The CLI command is `gregale ai catalog`.

## Per-end-user attribution and limits

An app may send `X-Gregale-AI-User` on an AI call:

- The value is 1–64 letters, digits or `. _ : @ + = / | -`.
- An invalid or repeated header is rejected with `400 outbound_ai_user_invalid`.
- The `~` of the overflow row is not an allowed character, so no header can name that row.
- Like every `X-Gregale-*` header, it is not forwarded.

The value is trusted only as the app's own attribution. An app can already spend its whole binding budget, so mislabeling users cannot raise any app or integration limit.

Two integration settings cap each named end user per UTC day: `user_daily_token_limit` and `user_daily_cost_limit_millicents`. They are part of `PUT /v1/outbound/integrations/{id}/ai` and require a provider.

Admission enforces the user limits like the other hard caps:

- The lease records the call's end user.
- A call is rejected when the user's settled day, plus that user's live reservations, plus this call's reservation, exceeds a limit.
- The response is `429` with reason `user_daily_token_limit` or `user_daily_cost_limit`, and `Retry-After` set to the next UTC midnight.
- Calls without the header are not limited per user.

Settlement adds the call to `outbound_ai_user_usage_daily`, one row per integration, UTC day and end user, with requests, error requests, input and output tokens, and cost. A new user gets its own row only while the day has fewer than `OutboundAIUsersPerDay` (10,000) rows; later users go to `~other`. Rows are pruned after `OutboundAIUserUsageRetentionDays` (31). The request log stores the call's end user.

`GET /v1/outbound/integrations/{id}/ai-usage/users?date=&end_user=&limit=` lists a day's users by cost, then tokens. The CLI command is `gregale ai users`.

## Key-pool affinity

A call's affinity key is its `X-Gregale-AI-Session` header (same rules as the user header), or else its end user. With an affinity key, the call ranks the integration's keys by `FNV-64a(affinity, 0, key ID)`, highest first, instead of round robin. Cooling keys still go last, and rotation on a 429 still moves to the next key in that order. A call without an affinity key keeps round robin.
