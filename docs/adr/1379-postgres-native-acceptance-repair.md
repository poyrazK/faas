# ADR-1379: PostgreSQL native acceptance repair

- **Status:** Accepted; native execution pending
- **Date:** 2026-10-15
- **Context:** The thirteen-phase PostgreSQL harness has three blockers: its Node starter CA is outside the unchanged Dockerfile's COPY paths; its scratch probe and Node Dockerfile app are looked up as function-runtime releases; and its evidence parser assumes a complete identity in one Go JSON Output event. Portable fixture tests do not catch these native-path mismatches. ADR-1378 corrected equivalent provenance and log-fragmentation assumptions for storage.
- **Decision:** Put only the public fixture CA at `runtime/fixture-ca.pem`, already covered by the shipped Node starter's Dockerfile, and select `/app/runtime/fixture-ca.pem` through ordinary `NODE_EXTRA_CA_CERTS` configuration. Preserve all shipped application, dependency, migration, readiness and restore files. Use shared full-OCI provenance validation for PostgreSQL and storage acceptance: require a successful build with a pinned OCI output, matching deployment/build source hashes, the retained exact archive, actual deployed drive1 app layer and shared minimal drive0 base. Keep each source archive alive through the whole journey, require unchanged shared base bytes across workloads, and rehash artifacts after workload shutdown. No production API, SQL schema, application, provider or VM behavior changes.
- **Evidence compatibility:** Upgrade the PostgreSQL guest manifest, suite and report to version 2. Replace `probe_base`/`node22_base` with `deploy_base`, `probe_app_layer`, `probe_source_archive`, `node22_app_layer` and `node22_source_archive`. Keep the existing thirteen phases. Require distinct app-layer/source evidence per workload, ordered phase completion, a final cleanup identity before parent/package completion, and bounded 16 KiB reassembly of fragmented Go identity output. Reject missing, skipped, failed, reordered or overlapping phases, premature/duplicate/truncated identities and old/partial runtime artifacts. Atomic private no-overwrite publication and the native-host/clean-source/leak requirements remain in force.
- **Consumers:** Combined rollout verification and opted-in staging admission require version-2 guest evidence and an independently approved matching version-2 manifest. Version-1 documents cannot silently qualify or migrate; regenerate and review them. Provider/durable qualification v8 and the combined result's outer schema are unchanged. Provisioning and rollout gates remain disabled unless already configured through their existing policy.
- **Capture continuity:** The starter's fresh-capture helper accepts an absent eligible snapshot after failed-hook fallback or rolling credential rotation. Ordinary park creates the next init snapshot; other lookup errors still fail acceptance. This changes only the fixture's assumptions, not production snapshot behavior.
- **Validation:** Compare every packaged Node starter file, including Dockerfile/runtime helpers, and require the fixture CA to be covered by the unchanged runtime COPY. Exercise full-OCI provenance, exact source changes, unknown/legacy artifacts, ordered/fragmented transcript handling and Python-to-Go report compatibility. Verify old guest evidence is rejected by combined readiness, retain storage regressions for the shared helper, and compile both native binding harnesses together. Supported native KVM execution and host leak qualification remain required; portable checks cannot claim these. Live-provider and public-network qualification remain separate.
