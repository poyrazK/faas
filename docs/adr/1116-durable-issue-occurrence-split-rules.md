# ADR-1116 · Durable issue occurrence split rules

- **Status:** accepted
- **Date:** 2026-10-11
- **Decision:** Add immutable, ordered exact-match routing rules to an original fingerprint identity. Creating a rule makes an open branch with the canonical source owner, moves currently retained matching occurrences still assigned to the source, and routes future matches to that branch. At most eight rules, including disabled rules, may exist per source. Oldest priority wins for future captures and eligibility during a new split; existing retained source occurrences matching an earlier enabled rule are left in place. Derived branches cannot have nested rules.
- **Provenance and retries:** Occurrence routing identity may change; original fingerprint provenance, payload, payload hash, event ID, occurrence ID, attribution, timestamps, and original grouping explanation do not. Nullable provenance supports old writers; readers use the current identity until an occurrence is moved. Exact retries return the occurrence's current canonical destination and never re-evaluate rules or increment counters. Retry guarantees remain bounded by occurrence retention.
- **Accounting:** Transfer only known retained matches and their deployment counts. Subtract those counts from the source lifetime/release totals and add them to the branch. Expired history and historical regressions remain on the source. Preserve source historical first/last bounds because expired evidence cannot reconstruct tighter bounds; branch bounds are derived from moved occurrences, or rule creation time when empty. A rule records initial moved and unavailable counts. Conservation applies across source and branch, including merged families.
- **Controls:** Creation is idempotent for the same source and exact selectors. Rules can be enabled or disabled without replaying or moving prior evidence; their priority and matcher never change. Re-enabling affects future captures only. Existing merge/split controls can combine and detach branches, but do not disable routing rules. Apply reads current retained evidence under the app lock; preview counts may change before application.
- **Concurrency and quotas:** Creation, toggling, captures, retention maintenance, and manual regrouping share the existing app lock. Branches count toward issue storage limits. Database keys scope rules and branches to the same app/environment; guards prohibit nested rules and definition edits. Mutations reuse write scopes, MFA, API idempotency, and dashboard CSRF. Actor-attributed audit is written on source and branch; no new webhook type is emitted.
- **Scope:** Selectors remain exception type, error code, route, and source kind against sanitized evidence. No regular expressions, raw stack matching, automatic precedence edits, destructive history reconstruction, or chained routing. Rules are returned in issue detail and can be managed on both source and branch.

- **Migration replay:** ADR-1114 is still an unmerged migration in this change. Its replay preserves the additive branch-source view column and newer audit vocabulary when split-rule tables already exist. Down migrations preserve routing data.

- **Environment cloning:** Issue group links, split rules, and occurrence provenance are operational state tied to original observed identities. Register their tables and columns as operational so configuration cloning remains complete and never copies issue evidence or cross-environment identity references.
