# ADR-525: Binding runtime configuration freshness

- **Status:** Accepted
- **Date:** 2026-10-02
- **Context:** Durable task-guest verification (ADR-524) can pass while a resident application still holds earlier environment or secret values. Existing app configuration stamps and runtime-configuration rolling restarts already fence old instances and snapshots. Operators need those observations alongside binding metadata without changing VM lifecycle.
- **Decision:** Extend binding inventory with an app-wide, scope-filtered timestamp projection grouped by deployment. Read the configuration stamp, selected deployments and resident app instance timestamps in one SQL statement or one MemStore lock. Report disjoint current/stale/unknown serving and resident counts, plus starting count. Include live deployments with no residents and superseded deployments retaining residents. Exclude task guests, jobs, mirrors, parked and terminal rows. At-or-before timestamps are conservatively stale; missing stamps or timestamps are unknown. A deployment remains stale while any stale resident, including warm or draining instances, remains.
- **Consequences:** This is configuration freshness inferred from instance admission times, not guest acknowledgement, readiness, per-binding credential adoption or connectivity. App-wide changes conservatively affect every binding. Freshness stays independent of canary outcomes. Bounded app-scoped reads preserve partial inventory on failure. Runtime counts are internally consistent at their read; resource metadata, canary evidence and restart status are separate best-effort reads and the overall inventory is not atomic.
- **Refresh progress:** Safe PostgreSQL and object-storage metadata reads carry pending rotation wake IDs internally. One permission-filtered batch reads their existing notification-outbox handoffs and returns only correlation IDs, bounded statuses, timestamps, attempts and stable failure reasons. No secret rows, raw diagnostics or outbox payloads enter inventory. Missing retained records are `not_queued`; failed reads are `unknown` and make inventory incomplete. Completed handoffs never override freshness or verification. Once rotation cleanup removes the pending marker, inventory omits its historical refresh.
- **Alternatives rejected:** Inferring adoption from a passing task guest, counting task guests or mirrors as serving instances, adding another rollout engine, and interpreting a later instance timestamp as a guest credential acknowledgement.
