# ADR-269: Standalone outbound service bindings

- **Status:** accepted
- **Date:** 2026-09-25
- **Decision:** Let standalone apps declare outbound `service_binding_targets` and an explicit `service_binding_policy` (`account` or `declared`) at create or PATCH time. The platform canonicalizes target app slugs, derives read-only service bindings and `GREGALE_SERVICE_<NAME>_URL` values, and stores them in the existing app manifest. Omitted PATCH fields retain their prior values; `[]` clears the target list. A standalone app remains on the legacy `account` policy until it explicitly opts in to `declared`. Project-managed and preview apps cannot mutate source-owned bindings through this API.
- **Why:** ADR-239 enforces declared project edges, while ADR-240 lets standalone targets restrict callers. Standalone callers also need a way to declare and discover targets without a Compose project. Keeping the authorization switch separate from target declaration avoids unexpectedly narrowing reachability for existing apps.
- **Consequences:** The existing gateway authorizer enforces standalone declarations under the `declared` policy immediately. The bound target list is a same-account name-based reference; a target need not exist at declaration time, but calls fail until it exists. URLs retain the existing internal `svc.gregale:10080` form, not a new DNS alias or public endpoint. The `GREGALE_SERVICE_*_URL` namespace is platform-owned; changed URLs reach already-running callers on their next start or redeploy, not by mutating process env. Updates use normal app change propagation and audit old/new policy and bindings. No schema migration is needed.
- **Rejected alternatives:** Change all standalone apps to `declared` automatically (breaking change); accept arbitrary binding keys or URLs (would allow spoofing the read model); resolve target IDs at write time (prevents forward references and complicates recreation); expose a new `billing.internal` DNS name in this stack (separate routing/TLS design).
