# ADR-966: Live delivery-health alert acknowledgements

## Status
Accepted. Amends ADR-965 acknowledgement semantics.

## Context
Checkpointed delivery-health watches required stopping before freeing notification queue space. Notification consumers need to acknowledge processed transitions during long-running watches and safely retry batches after interruption.

## Decision
Add synchronous Go watch PollAcknowledgements(context, checkpoint), receiving a detached checkpoint between observations. Require DurableAlerts and OnProgress when this callback is enabled. Validate its bounded exact incident_id/sequence pairs using the existing acknowledgement helper. Stage the updated checkpoint through OnProgress with no new alerts and no new health observation before replacing the in-memory queue. Callers must atomically persist this progress; failure stops with callback_failure while preserving the prior in-memory queue. Poll or acknowledgement validation errors stop with acknowledgement_failure, preserving the queue and live incident evidence. Cancellation retains the existing timeout/cancelled stop conventions. Acknowledgements never resolve or confirm an incident, change sequence, or release an active closing reservation.

Persist optional acknowledged_alerts in version-1 checkpoints, retaining the complete records of the most recent 1,024 removals in removal order. Existing checkpoints without this optional history remain valid. Validate the combined pending and acknowledged history for unique sequences, identity bindings, metric/threshold consistency and incident lineage, while separately requiring pending notification order. History does not consume pending/closing capacity, is not replayed, and has its own central bound. Duplicate exact pairs, within a batch or across batches/resumes, are idempotent while their records remain in this history. Foreign, future, fabricated, conflicting or older evicted pairs fail transactionally. Never infer an acknowledgement merely from an unused sequence. The offline acknowledgement helper uses the same semantics; it does not accept old removals absent from a legacy checkpoint's history.

Poll before health reads so removals free capacity before evaluating new openings. If a read reaches the opening capacity guard, emit/persist its progress, poll acknowledgements once more, and continue only if opening and closing reservations are available. Otherwise keep the bounded outbox full-stop behavior. No queue eviction or unbounded waiting is introduced.

Add CLI --ack-inbox PATH requiring --watch and --checkpoint. The watch retains exclusive checkpoint ownership and reads the separately owned inbox between polls. The producer writes a JSON array of exact processed pairs to a temporary regular file and atomically replaces the inbox. The watch neither edits nor deletes this file; an unchanged batch can be retried safely within the bounded history. A missing inbox means no acknowledgements. Empty files, malformed JSON, invalid pairs and read failures stop without removing pending notifications. Reject checkpoint/lock path aliases, hard links to those files, symlinks and non-regular inbox files. Resolve and pin the parent directory, reuse the existing bounded JSON reader, and check checkpoint ownership before each read. Inbox replacement must be atomic; this is not an append-only log. Supply recent bounded batches rather than permanent cumulative history.

## Consequences
CLI and Go SDK watches can free notification capacity without stopping. Checkpoint updates still precede notification output and remain atomic under the existing stable sidecar lock. Offline queue operations continue to require exclusive ownership. Printing or replaying a notification never acknowledges it. SDK callbacks may observe progress without a new health sample; they must not treat every callback as fresh evidence. Older SDKs do not preserve the new optional retry history when rewriting checkpoints, so writers should use the updated version. No backend queries, migrations, server alert rules, external notification delivery, local tests or compliance registry edits are introduced.
