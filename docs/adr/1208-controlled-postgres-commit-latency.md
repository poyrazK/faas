# ADR-1208 · Controlled PostgreSQL COMMIT latency and bounded stalls

- **Status:** accepted
- **Date:** 2026-10-12
- **Decision:** Extend ADR-1206/999's opt-in loopback fixture with one-shot simple-query COMMIT delay/stall plans. Select request or response direction; response selection requires successful COMMIT completion and idle ReadyForQuery. Delay forwards held frames after an integer 1–5000 ms duration; stall closes both ends at that bound. Default arming retains immediate successful acknowledgement loss. Pause frame relays while holding, preserve order/backpressure, bound buffered bytes and evidence, and cancel holds/timers on socket closure or shutdown.
- **Why:** Lost replies do not establish how a caller behaves when a dependency eventually responds after its deadline. A slow COMMIT request and a slow successful acknowledgement also have different independently observable database states.
- **Consequences:** Monotonic fault evidence reports configuration, elapsed duration and release/timeout/cancellation without SQL, keys or credentials. At most 100 arm operations bound retained evidence. Real TLS PostgreSQL tests compare 400 ms caller deadlines with 1200 ms request/response holds and test a delay beyond the existing four-second database-client query timeout. Independent SQL proves committed data behind held replies and pending intent behind held requests. Unknown outcomes, no hidden write retry, conflict rejection, explicit concurrent reconciliation, encrypted recovery and zero stuck transactions/work/timers/connections are required. Rejected/rollback COMMIT replies do not create positive response-fault evidence. The fixture remains local and opt-in; native restart qualification, remote fault routing, arbitrary-query latency, bandwidth limits and production request cancellation remain separate work.
- **Rejected alternatives:** Sleeping in an HTTP handler does not exercise database wire latency. Holding a reply before verifying successful COMMIT cannot prove the transaction committed. Unbounded stalls or abandoned timers would turn the fault fixture itself into a resource leak. Treating a caller timeout as rollback would risk repeating a committed operation.
