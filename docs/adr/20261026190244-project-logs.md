# ADR-20261026190244: `gregale logs --project` reads every service of a project together

- **Status:** accepted
- **Date:** 2026-10-26
- **Decision:** `gregale logs --project SLUG` streams the runtime logs of every live service of a project in one output, each line prefixed with its service (`[api] …`). This is what `docker compose logs` gives.
  - **Selection.** The project's workloads come from `GET /v1/projects/{slug}`. Deleted ones are skipped. `--service a,b` narrows the set and matches service names in their DNS form (ADR-20261026170512).
  - **Streams.** The CLI opens one runtime log stream per service, the same `StreamAppLogs` call `gregale logs <app>` makes, and writes whole lines under one lock.
    - With `--follow`, a service without a running instance is asked again every 5 seconds, so its lines appear once it wakes. A 4xx is reported once and that service stops.
    - Without `--follow`, each running service prints its recent lines, and a parked one is named with the command that reads its retained logs.
  - **Flags.** `--since`, `--grep` and `--level` apply to every service. Selectors that name one app or deployment (`--deployment`, `--source http`, `--view`, `--archive` and the others) are refused with `--project`. `--json` adds `service` to each JSON line, or wraps a text line as `{"line", "service"}`.
- **Why:** Debugging a multi-service request meant one terminal per service or switching apps. `--trace` correlates one request's access logs; it does not show the services' own output side by side.
- **Consequences:**
  - The API is unchanged and there is no server-side merge, so lines from different services are ordered by arrival, not by timestamp.
  - Each service is its own stream and counts like a separate `gregale logs --follow`.
- **Rejected alternatives:**
  - **A server-side project log stream.** It needs a new API and fan-out in apid for the same result.
  - **Sorting by timestamp.** Followed streams have no end to sort against, and runtime lines carry no common timestamp format.
