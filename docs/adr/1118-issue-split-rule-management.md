# ADR-1118 · Issue split-rule management

- **Status:** accepted
- **Date:** 2026-10-11
- **Decision:** Preserve raw split-preview matching counts, and add priority-aware eligible counts and samples. Earlier enabled rules exclude matches from a new rule's transfer. A repeat matcher, derived branch, or exhausted eight-rule capacity reports a distinct application status and zero eligible transfer; repeated creation still returns its existing rule without replay or re-enable. Preview is a read-only consistent snapshot; ingestion, retention, policy, and plan capacity can change before apply.
- **Branch labels:** New branches have a bounded title prefixed by immutable rule priority and the most specific supplied selector, followed by the source title. Existing branch titles are preserved. Rule rows also show selectors and priority, so users can recognize older branches without rewriting history.
- **Undo:** Add a reviewed dashboard operation and API endpoint that atomically disables one rule and merges its isolated branch into the source's current canonical group, under the shared app lock. Require the caller's reviewed canonical source ID; reject changes to that destination. Reject branches linked to an unrelated group or carrying additional merged members. Already-merged branches can disable routing without changing membership. Repeating a completed undo is a no-op.
- **Preservation:** Undo combines group views; it never rewrites occurrence provenance, event IDs, payloads, original counters, or releases. Destination lifecycle and owner win as in manual merges. Other enabled rules continue routing by existing priority. Existing retry destinations resolve through the canonical group. Disabling and merge audit reuse existing actor-attributed activities; no migration or webhook vocabulary is needed. Failures roll back both operations. MFA, write scopes, idempotency, and CSRF apply.
